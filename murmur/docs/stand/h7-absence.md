# H7 の手順: absence（欠勤連絡）をスタンド主導で回す

murmur-dev で、`fixtures/absence` の流れを Cowork（スタンド）主導で回す。人がするのは、Claude への指示と送信の確認だけ（H7 の合否基準）。
受信は直樹が手元の `npm run send` で Webhook に流す。LINE の実物はないので、送信は「送ったことにして記録する」（`record_sent`）。

## 準備（直樹の手元）

```sh
cd murmur && git pull                 # main の最新。git log --oneline -1 で確かめる
set -a; . ~/.config/murmur/dev.env; set +a
npm run seed absence -- --user u_kimura=entra_6f043b7f-9709-4e71-bfa1-bd38a935316b_a86eed80-97f7-41a9-b7cc-2c6849408afb
```

- seed はイベントも投影も空にする。管理画面は `https://murmur-dev.nose-0d2.workers.dev/admin?token=<TIMELINE_TOKEN>`（テナント ubs）で見られる
- Cowork に `api-gateway` と `nvt-api-gateway`（0.3.0）が入っていること。新しい会話で始める
- 最初にスタンドに「これはテストのシナリオなので、ビルメンNEXT などの外のサービスには書かない。送信は送ったことにして記録だけする」と伝える（1 回目でビルメンNEXT の割当を付け替えようとした）
- 受信時刻は本体の時計（今）になる。シナリオの時刻（10/16 20:00 など）は目安。期限（返事期待）は今からの時刻で決める

## 流れ

各段で、左の操作をしてから、スタンドの結果が右のとおりかを見る。食い違ったら止めずに「気づいたこと」に書く。

| # | 直樹がすること | スタンドに起きてほしいこと（Murmur から見た期待） |
| --- | --- | --- |
| 1 | `npm run send absence s01`（山本さんの欠勤の連絡） | — |
| 2 | Cowork に「自分の番のものを見せて」 | `list_threads filter=my_turn` に欠勤のスレッドが出る（読者が木村 1 人なので、持ち主なしでも木村の番）。内容を要約して見せる |
| 3 | 「これは私が持つ。代わりの人を探す」 | `claim_thread`。ボールが木村（`user`）に |
| 4 | 「伊藤さんに LINE で、明日朝 7〜10 時に入れるか打診して。返事は 1 時間以内で」 | 文面・宛先（U_ito）・返事期待を見せて確認を求める。確認したら「LINE は送れないので送ったことにして、sentMessages の id は `line:sent-2001` で記録して」と伝える → `record_sent`（`data_source: ds_line_oa`、`to: ["U_ito"]`、`sent_ref: line:sent-2001`、`source_thread_id` に欠勤のスレッド、`reply_expected_by`）。打診のスレッドができ、欠勤のスレッドと経路 sent で結ばれる |
| 5 | `npm run send absence o01`（打診がデータソースで観測された分。スタンドが別の sent_ref で記録したら `--sent-ref <それ>`） | 打診のスレッドに統合され、シグナルは増えない（H5）。管理画面で 1 本のままか見る |
| 6 | `npm run send absence o02`（LINE の管理画面から山本さんへ直接返した「お大事に」） | AI が欠勤のスレッドに区切る。ボールは山本さん（相手）に |
| 7 | `npm run send absence s02`（伊藤さんの「入れます！」） | 返事待ちの規則で打診のスレッドに入る（欠勤のスレッドに付かない。v1 の取り違えの対策）。「求めていない」で返事期待が消える |
| 8 | 「伊藤さんから返事来た？」 | 打診のスレッドの承諾を読んで答える。欠勤のスレッドとのリンクを辿って、欠勤の件が片付いたことも分かる |
| 9 | `npm run send absence s03` `s04`（佐々木さんの遅刻とスタンプ） | 遅刻は知らせだけ（「求めていない」）。スタンプは同じスレッドに区切られる |
| 10 | 「佐々木さんの件は対応不要、片付けて」 | `dismiss_thread`（理由つき） |
| 11 | `npm run send absence s05` `s06`（山本さんの回復の連絡と、洗剤の補充依頼） | 回復の連絡は返事待ちの規則で欠勤のスレッドに。補充依頼は AI が別のスレッドに区切り、「求めている」 |
| 12 | 新しい会話で「前回から何が動いた？」（`since` を使ってほしい） | セッションが切れたあとでも、補充依頼が自分の番に出ていることを見つけられる（H10 の「続きから入れるか」の下見） |

期限超過（H4）も見るなら、4 の返事期待を短くして、7 の `npm run send absence s02` を期限のあとにする。Cron は 5 分おきに見回る。

## 記録すること

- 各段で、スタンドが呼んだツールと回数、ユーザーへの確認の回数、取り違え（違うスレッドに入った・違うスレッドを結んだ）
- 期待と違ったところと、その場で直樹がどう判断したか（v1 の「明日（17日）」のような読み替えも）
- 終わったら、`fixtures/absence/` をこの記録で固め直す（`scenario.json` の status を `stand-recorded` に）。H10 で「Murmur なし」と比べるときの基準にもなる

## 気づいたこと

### 2026-10-21 の 1 回目（Cowork、直樹）

- 1: `npm run send absence s01` で欠勤のスレッドが 1 本できた。件名は dev の Claude が付けた「山本さん 明日(17日)朝シフトの欠勤連絡(発熱)」。ボールは「こちら」、誰の番は木村（根拠 `reader`）
- 2: 「自分の番」に欠勤のスレッドが出た。ただしスタンドは、受信が 21 日なのに本文が「明日（17日）」であることに気づかず、17 日として報告した（v1 と同じ）。受信時刻と本文の日付を照らすのはスタンドの仕事（Murmur は本文の日付を読まない）。スキルに「受信時刻と本文の日付が合わなければユーザーに確かめる」を足すかは保留
- 直樹が「17 日は書き間違い、明日 22 日の朝のこと」と読み替えを伝えた
- 3: 「これは私が持つ」で `claim_thread`。ボールと誰の番が木村（根拠 `owner`）に。スタンドは読み替えを持ち主の理由（「代わりの人を探すため直樹が持つ（22日朝シフトの欠勤として対応）」）に書き、「件名は変えられないので理由を見て」と言った。
  件名を直す手段がないのは 0014 の未決 2（件名）に関わる。メモ（`add_note`）に書く手もあるが、軽い運用（メモのスレッドを作らない）では理由かメモのどちらかになる。
  直樹: 件名は属性の 1 つとして畳めるべき（0014 の未決 2 に書いた）
- 4: スタンドは LINE を送る手段がない（ゲートウェイに LINE の送信先がない）ことを自分で言い、文面だけ作って直樹に送ってもらう形にした。送れていないものは記録しなかった（スキルどおり）。返事期限は文面の「16 時ごろまで」に合わせた
- 4: **スタンドが伊藤さんの宛先を引けなかった。** `record_sent` は `to`（アドレス）か `to_party_ids` を受けるが、スタンドに見えるのは読めるスレッドに出てきた相手だけで、やりとりのない伊藤さん（`p_ito`・`U_ito`）はマスタにあっても見えない。
  推測で `U_ito` を入れずに止まって聞いてきた（正しい振る舞い）。直すなら、自分のテナントの相手（Party と Address）を名前で引く API（例: `GET /parties?q=伊藤`）。H7 のあとで決める
- 4: 持ち主の理由に「直樹が持つ」と書いたが、Murmur のユーザーは木村（seed で木村を直樹のゲートウェイの User に付け替えている）。理由の文言も後から直せない
- 4: `record_sent` で打診のスレッドができ、欠勤のスレッドと経路 sent で結ばれた。ボールは伊藤さん、返事期限 16:00。打診のスレッドの件名は本文の頭（改行込み）。LINE に件名がないため。件名を属性として直せる話（上）と同じ
- 5: `npm run send absence o01`（打診の観測）は打診のスレッドに統合され、シグナルは 1 件のまま、スレッドも 2 本のまま（H5）。本文は記録とシナリオで違ったが、sent_ref で 1 本になった
- 6: `npm run send absence o02`（山本さんへ管理画面から直接返した「お大事に」）は AI が欠勤のスレッドに区切った（`by: ai`）。ボールは山本さん（相手）に移った。持ち主（木村）は残る
- 7: `npm run send absence s02`（伊藤さんの「入れます！」）は返事待ちの規則で打診のスレッドに入った（`by: awaiting`、「求めていない」）。欠勤のスレッドには付かない（v1 の取り違えは実環境でも起きなかった）。ボールは「なし」、返事期限も消えた
- 8: 「伊藤さんから返事来た？」に、承諾を読んでリンクを辿り「明日朝の清掃は伊藤さんで埋まりそう」まで答えた。山本さんへの返信（o02）が綴じられていることも自分で見つけた。
  さらに「次は伊藤さんへのお礼と、ビルメンNEXT で割当を付け替える」と自分から次の一手を出した。**ビルメンNEXT のスキルは本物（urban-b）につながっているので、テストのシナリオでは止めた。** H7 を回すときは、スタンドに「テストのシナリオなので外のサービスに書かない」と最初に伝える
- 9: `npm run send absence s03 s04`（佐々木さんの遅刻とスタンプ）は新しいスレッドに（s03 は `no_match`、s04 は `ai`）。どちらも「求めていない」で、誰の番もボールも「なし」
- 10: 「佐々木さんの件は対応不要、片付けて」で `dismiss_thread`（理由「対応不要（ユーザー判断）」）。誰の番でもないスレッドを自分で探し出した。ただし説明に誤りが 2 つ:
  - 「誰の番でもない仕分け待ちになってた」→ 仕分け待ち（triage）ではない。誰の番でもない（ボール「なし」）
  - 「また佐々木さんから何か来たら、スレッドが開き直って上がってくる」→ **Murmur は自動で開き直さない**（0014。`activeSinceDismissed` が立つだけで、自分の番にも仕分け待ちにも出ない。`filter=all` か `since` でだけ見える）。
    スキルには「閉じたメモを勝手に開き直さない」はあるが、片付けたあとにシグナルが来たときの見え方が書いていない。スキルに足す（H7 のあと）
- 11: `npm run send absence s05 s06`。s05（山本さんの回復の連絡）は返事待ちの規則で欠勤のスレッドに（`awaiting`、「求めていない」）。ボールは「なし」、持ち主は木村のまま。
  s06（洗剤の補充依頼）は AI が別のスレッドに区切った（`ai`、「求めている」）。件名「3階倉庫の洗剤補充のお願い」、誰の番は木村（読者が 1 人）、ボールは「こちら」
- 12: 新しい会話で「前回から何が動いた？」。前回を「佐々木さんの件を片付けた 15:35 ごろ」と置いて、そのあとに動いた 2 本（山本さんの回復の連絡、補充依頼）を挙げた。`since` を使ったか、前回の時刻をどう知ったか（片付けの時刻から取ったか、Cowork の記憶か）はこちらから見えない。
  さらに結んだ先まで読んで、2 つ気づいた。
  - 「明日朝は伊藤さんが引き受けたのに、山本さんも出られると言っている。二人入ることになる」: 日付の読み替え（17 日 → 22 日）で生まれた食い違い。シナリオでは回復の連絡は 10/17 の夕方で、翌日以降の話。それでも、リンク先の状態を合わせて業務の判断に必要な点を拾えている。
    なお Murmur は s05 を「求めていない」と判定し、欠勤のスレッドのボールは「なし」。食い違いを拾うのはスタンドの仕事で、Murmur の判定の誤りではない（本文だけ見れば知らせ）
  - 「伊藤さんの『入れます』のあと、こちらから返した記録がない」: 打診のスレッドのボールが「なし」でも、礼と確定の連絡が要るかを促した

### 1 回目のまとめ（2026-10-21）

12 段を最後まで回した。Murmur の側（区切り・「求めているか」・統合・リンク・誰の番か）は期待と全部一致した。人が口を出したのは次のところ。

| 段 | 何をしたか | 原因 | 直す候補 |
| --- | --- | --- | --- |
| 2〜3 | 日付「明日（17日）」を 22 日に読み替えるよう伝えた | シナリオの本文に日付があり、受信時刻が今になる | H10 で繰り返すなら、シナリオを日付なしにする。スタンドが受信時刻と本文の日付の食い違いに気づかなかった（スキルに足すかは保留） |
| 4 | LINE を送る手段がないので「送ったことにして sent_ref はこれ」と伝えた | ゲートウェイに LINE の送信先がない（試験の都合） | なし（実運用では LINE の送信スキルが要る） |
| 4 | 伊藤さんの宛先 `U_ito` を教えた | スタンドがやりとりのない相手の宛先を引けない | 自分のテナントの相手を引く API（例: `GET /parties?q=`）。計画にないので、入れるなら ADR に案を書く |
| 8 | ビルメンNEXT の割当の付け替えを止めた | テストのシナリオなのに、本物につながったスキルで次の一手を打とうとした | 回す前に「テストなので外のサービスに書かない」と伝える（手順書の準備に足す） |
| 10 | 片付けの説明の誤り（開き直って上がってくる）を訂正した | スキルに、片付けたあとにシグナルが来たときの見え方が書いていない | スキルに足す |

ほかに分かったこと: 件名を直す手段がない（Ingest の件名に日付の誤り、LINE は本文の頭が件名になる）→ 件名は属性の 1 つとして畳めるべき（直樹、0014 の未決 2）。持ち主の理由も後から直せない。

H7 の合否基準（人の操作は Claude への指示と承認だけ）に照らすと、宛先を教えたところ（4）だけが「指示と承認」を超えている。ほかは試験の都合（日付・LINE）か、スタンドの側の注意（ビルメンNEXT・説明の誤り）。
