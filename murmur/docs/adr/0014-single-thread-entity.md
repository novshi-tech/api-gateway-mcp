# 0014 エンティティはスレッドの 1 種類。用件とマイリストは「個人のメモ」というデータソースのスレッドになる。結ぶのは人とスタンド

- 状態: 採用（2026-10-20、直樹と合意。計画 v2（`docs/PLAN.md`）と `CLAUDE.md` に同日反映した）。
  2026-11-04: リンクの可視性は 0033 で改めた（リンクは両端のスレッドを読める人にだけ見える。見えない先へのリンクは、あることも出さない）
- 関連: 0013（外部リストとマイリスト。その 2 層をここで 1 つに畳む）、0012（判断の台帳、外には書かない。「綴じる 3 種類」はそのまま）、0010（黒子。「正は 1 つ」の読み方を直す）、0008（業務の知識を持たない）、0009（2 層のリスト。用件の層はここで完全に消える）

## 背景

0013 を反映した計画 v2 を直樹がレビューし、Claude Docs 上のコメントで議論した。問いは 4 段で進んだ。

1. **個人のメールボックスや Slack の DM はどこに入るのか。** 外部リスト（データソースの写し）でよい。読者が本人 1 人のデータソースにすぎず、「テナントで 1 つの共有の実体」は「人ごとのコピーを作らない」という意味で、読者が複数という意味ではなかった
2. **「受け皿のない用件」という概念は要るのか。** LINE も Jira も、正はデータソースの側にあり、外部リストはその写し。違いは「ソースが用件の構造（区切り・状態）を元から持つか、Ingest が切るか」という変換の程度だけ。Jira の状態は写し（`ThreadMirrored`）があり、LINE には写しがないだけで、「Murmur が正」の用件は存在しない
3. **用件のボールや open / closed を、結んだスレッドからどこまで伝播させるのか。** 伝播させない。Murmur の責務はリンクを張る・外すことと外部リスト側の状態の追跡（ボール・持ち主・写し）まで。マイリスト側（開く・閉じる・属性・メモ）はユーザーとスタンドが面倒を見る。結んだ先が動いたら、Murmur はその事実を返すだけで、開き直すかはスタンドが判断する
4. **伝播を切ったあと、用件とスレッドの違いは残っているか。** 残っていない。残る違いは「シグナルがデータソースから来るか、本人が書くか」の 1 点で、それは「本人のメモ帳というデータソース」として表せる。最上流で導入した概念はコードに反映されるので、エンティティは 1 種類にする

途中で検討した「用件を薄い入れ物として残す（名前・状態・属性・メモ・束ねたスレッド）」案は、4 の問いで消えた。

## 決定

### 1. エンティティはスレッドの 1 種類

- スレッドは、データソース・シグナルの列・ボール（こちら / 特定のユーザー / 相手 / なし）・持ち主・アンカー・属性・open / closed（片付け）・リンク（他のスレッドへの辺）を持つ
- リストはデータソースごとに 1 つ（機械的に作る。テナントで 1 つの共有の実体、人ごとのコピーは作らない）。可視性の単位。`List.kind`（external / personal）はなくなる
- 読者はそのデータソースを読める人。1 人のこともある（個人のメールボックス、Slack の DM、個人のメモ）
- fold は 1 段。スレッドの fold はそのスレッドのイベントとリンクのイベントだけ読む。リンク先の状態は fold に持ち込まず、クエリ層で合わせる

### 2. 「個人のメモ」はデータソースの 1 種類

- ユーザーごとに 1 つ、自動で作る。読者は本人だけ
- シグナルは本人・スタンドが `add_note` で書く（電話や対面の記録、判断の記録、スタンドとのやりとりの控え）。0012 の「綴じる 3 種類」の 3 つめ（メモ）はここに入る
- 「この件」として追いたければ、個人のメモのデータソースにスレッドを作り（最初のメモがそのシグナル）、関係するスレッドを結ぶ。LINE の 1 本だけで済む件なら、メモのスレッドを作らず持ち主だけ追ってもよい（軽い運用）
- 属性の定義（`AttributeDef`）はデータソースに付く。外のサービスのスレッドの属性は写し（`ThreadMirrored`。Murmur は書き換えない）、個人のメモのスレッドの属性は本人が付ける（`ThreadAttributeSet`）。違いは「写すか、書くか」だけ
- 0013 の「マイリスト」は個人のメモのデータソースのリスト、「用件」は個人のメモのスレッド。どちらも別のエンティティとしては持たない

### 3. 結ぶのは人とスタンド。Murmur は候補を出すだけ

- リンクは `ThreadLinked { a, b, route: sent | anchor | manual, by, reason }`（unlink で外す。追記で、元の判断は消さない）。**無向**で、1 つのイベントが両方のスレッドの投影に載る。経路 sent の「元 → 送った」は由来の属性で、辺の向きではない
- Murmur が自分でリンクを張るのは、`record_sent` の副作用（経路 sent）だけ。これはスタンドの操作の一部
- アンカーの一致（Jira キー・PR 番号・チケット番号・`sent_ref`）は、本人の見えるスレッドの中から**結び候補**としてクエリ層で出す。自動では張らない。アンカーをついでに書いただけの連絡（DEV-12 と DEV-30 を同時に触れた Slack）で別の件が溶けないようにするため
- 0013 の「つなぎ」（経路 ball / anchor で用件を自動で作る）はなくなる。「誰の番か」（ボールが特定のユーザーに来る）は Murmur が構造で決めるが、そこから先にスレッドを作ることはしない

### 4. マイリスト側の状態は Murmur が自動で変えない

- 片付け・開き直し（`ThreadDismissed` / `ThreadReopened`）、属性、メモは、本人とスタンドが付ける
- 結んだ先のスレッドにボールが来ても、閉じた件を自動で開き直さない。Murmur は「閉じた件に結ばれたスレッドにボールが来た」という事実をクエリで返し、開き直すかはスタンドが判断する
- 外部リストと「マイリスト」の状態は独立。Murmur の責務はリンク張りと外部リスト側の状態の追跡まで、という分担

### 5. シグナルのイベントは 1 つ

- `SignalReceived` と `SignalObservedSent` を `SignalObserved` に統合し、`direction`（inbound / outbound）で区別する。direction は from がデータソースの送信元（こちら）かどうかで、コネクタが機械的に決める
- ボールの向き、Ingest で「返事を求めているか」を判断するか、記録した送信との統合（H5）は direction で分岐するだけ
- 個人のメモのシグナルも `SignalObserved`（データソースが個人のメモ、from が本人、置き先は本人が指定する `SignalThreaded`、by: self）

### 6. 黒子（0010）の読み替え

- 「用件ごとに正を 1 つ」は「状態の正を Murmur 側で複製しない」の意味に読み替える。スレッドはどれもデータソースの写しで、正は常にデータソースの側。ソースが状態を持てば写し、持たなければ写しがないだけ
- 「受け皿のある用件 / ない用件」「Murmur が正の用件」という言い方はやめる。「正が外にある用件」の節は「状態の写しを持つデータソース（Jira）」になる
- チームの共有は既存のツールに任せ、Murmur はチームリストを持たない（0013 の 1 はそのまま）。LINE の件をチームで追いたければ起票して結ぶ。追わなくてよければ持ち主だけで済ませる。この柔軟性は利点として認める

## 代案

- **用件を薄い入れ物として残す**（名前・open / closed・属性・メモ・束ねたスレッド。結合だけ切る）: 残る違いが「シグナルの出どころ」だけになり、それはデータソースで表せる。エンティティが 2 つあると fold・投影・API・可視性の規則が 2 系統になり、コードが厚くなる
- **用件を連結成分として導出する**（スレッド + 無向の辺だけで、用件はクエリ層の連結成分）: アンカーをついでに書いた連絡で別の件が溶ける（辺を外すイベントが要る）、件の名前と open / closed を書く場所がない（代表を 1 本決める運用になる）。個人のメモのスレッドを「この件」の置き場にすれば、どちらも解消する
- **0013 のまま**（外部リストとマイリスト、つなぎで用件を自動作成、2 段の fold、自動の開き直し）: 自動作成とアンカーの自動つなぎが、業務の知識なしに正しく束ねられる保証がない。開き直しの自動化は、外部リスト側の状態をマイリスト側へ伝播させる規則を Murmur に持たせることになり、「何をするかは判断しない」（0012）と食い違う

## 影響（計画 v2 と `CLAUDE.md` に 2026-10-20 に反映した）

- **ステップ 2（データソースのスレッド）は無傷**。`SignalReceived` → `SignalObserved` の改名と direction の追加だけ
- **ステップ 3** は「個人のメモのデータソース（`add_note`）、『自分の番』ビューと結び候補、リンク（`ThreadLinked` / unlink）、持ち主、本人が付ける属性、片付けと開き直し、導出したボールとタイムライン（クエリ層）」。用件・つなぎ・2 段の fold・開き直しの自動化が落ちる
- **ステップ 5（API）**: `list_threads` / `get_thread` / `add_note` / `link_threads` / `unlink_threads` / `set_attribute` / `dismiss_thread` / `reopen_thread` / `move_signal` / `claim_thread` / `record_sent`。スキルの API 表は作り直し
- **仮説**: H1（fold は 1 段、リンク込み）、H2（状態は属性と導出で足りる。本人の側の状態を Murmur が自動で変えない）、H3（持ち主とリンクはスレッドが見える人に見えるが、結び先の中身はその先の可視性）、H8（構造と持ち主だけで「自分の番」が決まり、アンカーの一致が結び候補として正しく出る）、H9（状態の写しを持つデータソース。起票でリンクが付く）を書き直した
- **シナリオ**: absence はメモのスレッドなしで持ち主だけ追う軽い運用、development に DEV-12 / DEV-30 の結び候補の例を足した
- **0013**: 2 層の構成（2）、つなぎ（5）、fold の依存（4）、言葉（8）はここで置き換わる。チームの共有は既存のツール（1）、持ち主とリンクは共有の層の事実（3）、権限（6）、外すもの（7）はそのまま生きる。未決 2（用件を自動で作る範囲）は、自動では作らないことにして解消
- **0012**: 定義文は「連絡から対応の要る件を拾い、その経過を追跡する。エンティティはスレッドの 1 種類」。「綴じる 3 種類」はそのまま
- **0010**: 「用件ごとに正を 1 つ」は上の 6 のとおり読み替える
