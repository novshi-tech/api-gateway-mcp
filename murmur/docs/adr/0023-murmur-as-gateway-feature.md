# 0023 Murmur をゲートウェイの機能にする（1 つのデプロイ）

- 状態: 採用（2026-11-04、直樹とのディスカッション。総称の単語は保留）。2026-10-28 の構想（リポジトリだけまとめて Worker は分ける）を書き直した。実装は「移し方」の段取りで進める。実装が終わるまでは、下の「採用したら直すもの」の ADR と CLAUDE.md の今の書き方が実装の正
- 関連: 0020（チーム単位でセルフホストする。ゲートウェイとは 1 対 1）、0021（決定 4: ゲートウェイの `deploy` スキルで一緒にデプロイする）、0024（本体はゲートウェイの OAuth クライアントになる）、0026（自分専用の Murmur は作らない）、0003（identity）、0012（本体は書き換えない）、api-gateway-mcp の `docs/adr/0004`（1 つのデプロイ = 1 つの組織）・`docs/background-access.md`

## 背景

### これまで 2 回見送った

1. **リポジトリだけをまとめる**（2026-10-28 より前）: 「リポジトリだけをまとめるなら、今のままでよい」として見送った
2. **Webhook の管理をゲートウェイに置く／一緒にする**（2026-10-28、0024 の代案と 0023 の構想）: ゲートウェイの性格（HTTP と OAuth2 だけを知り、サービスを足してもコードを変えない）が崩れ、ゲートウェイから本体へ処理を投げ返すことになって密に結合する、として見送った。0023 の構想は「まとめるのはリポジトリだけ、Worker は分けたまま」とし、ゲートウェイは Murmur なしでも使える（業務の自動化）ことを理由に挙げた

### 今回、蒸し返す理由（直樹、2026-11-04）

**Murmur は利用者にとって存在が分かりにくい。** 従来のタスク管理の概念から外れていて、実態は「スタンドのために構造化されたタスクの記憶」になっている。ただ、それは「Murmur は黒子」という設計の意図どおりでもある。記憶のように、利用者があまり意識せずに使えるなら、それに越したことはない。その方向を追う。

目指す使われ方:

- 利用者は Murmur を意識せずに、スタンドに「いまやるべきことは？」と聞く。スタンドは裏で Murmur を読んで、「Outlook に○○さんからメールが来ていて、この件は Jira の XXX-123 として課題になっていて……」と答える
- Jira になっていない Teams や LINE の件も、誰かが着手すれば `ThreadClaimed` が付き、ほかの人のスタンドは「この件は○○さんが対応しています」と答えられる。外の人には、その状況をスタンドが要約してメールできる

そう考えると、**Murmur に個別のデプロイが要ること自体が変**。記憶のように、有効にしたり無効にしたりできる機能の 1 つとして、ゲートウェイと一緒にあるほうが自然。

### 別々であることのコスト（2026-11-04 の 1 日の実績）

- 本体の HTTP API を変えるたびに、ゲートウェイのスキルを同時に直す約束がある。1 日でスキルの版を 0.1.1 → 0.1.6 まで上げ、PR は毎回 2 本（api-gateway-mcp#35〜#38 と murmur#17〜#21）、出し直しはゲートウェイ 3 つと Murmur の順番付きで往復した
- 配線: 認証方式 `identity`（`IDENTITY_SIGNING_KEY`・`GATEWAY_JWKS`・`IDENTITY_ISSUER`・`IDENTITY_AUDIENCE`）、Service Binding（ゲートウェイ → Murmur と、Murmur → ゲートウェイの `GATEWAY_WEB`。共有の箱のための `Background` の入口もゲートウェイにはある）、CIMD（Murmur がゲートウェイの OAuth クライアントになる。`/oauth/client.json`・`/oauth/callback`、リフレッシュトークンを `TOKEN_KEY` で暗号化して保存）、Murmur 自身の `PUBLIC_URL`
- 配線のコードは両側で約 1,300 行（Murmur の `src/connectors/gateway/`・`src/auth/`・`src/app/connections.ts` で約 720 行、ゲートウェイの `background.ts`・`identity.ts`・`web/connections.ts`・`web/grants.ts` で約 540 行）
- デプロイの設定のリポジトリが 2 つ（api-gateway-deployments と murmur-deployments）
- 利用者から見ると、ゲートウェイのコネクタとは別に、Murmur への同意（OAuth の画面）がもう 1 回ある

### 前回から変わった前提

- **境界が一致した**: ゲートウェイは 1 つのデプロイ = 1 つの組織にした（api-gateway-mcp の 0004、2026-10-30）。Murmur は 1 チームに 1 つで、ゲートウェイとは 1 対 1（0020）。デプロイを分けても、表している境界は同じ。分けていることは境界を何も表さず、コストだけを生んでいる
- **ゲートウェイのない Murmur はない**: 自分専用の Murmur は作らない（0026、案）。Murmur は必ずチームのゲートウェイと対で置かれる
- **守りの境界はもともと同じ**: 0024 で「ゲートウェイに置いても同じアカウントの中なので、守りの境界は変わらない」と認めた。`client_credentials` の入口（`Background`）は、同じアカウントの Worker なら使える（background-access.md）。信頼の単位はすでに Cloudflare のアカウントで、Worker を分けても境界は増えていない

## 見送った理由を見直す

| 見送った理由 | いまも成り立つか | この案での扱い |
| --- | --- | --- |
| ゲートウェイの性格（HTTP と OAuth2 だけを知る）が崩れる | コードの性格の話で、デプロイの単位の話ではない | ゲートウェイの中核は Murmur を import しない。まとめるのは Worker の入口だけ（決定 2） |
| ゲートウェイは Murmur なしでも使う | 成り立つ | Murmur は機能として無効にできる。無効なら、Murmur の束縛（D1・キュー）がなくても動き、テストも通る（決定 1） |
| Webhook の管理をゲートウェイに置くと、本体へ投げ返して密に結合する | 中核に Murmur の仕事をさせる話としては成り立つ | Webhook の管理は Murmur のモジュールが持つまま。同じ Worker の中で、Murmur のモジュールが受ける（決定 2） |
| 運用の違い（ゲートウェイは本番で PR、Murmur はプロトタイプで main に直接） | 成り立つ。いちばん重い | Murmur も PR に寄せる。UBS ではもう本番に近い使い方をしている。プロトタイプの変更がゲートウェイを壊さない仕掛けを置く（「危ないところと抑え方」） |

## 決定（案）

### 1. Murmur はゲートウェイの機能。1 つの Worker、1 つのデプロイ

- Murmur はゲートウェイの Worker の中のモジュールになる。デプロイは 1 回、設定は 1 つ（`deployments/<名前>.jsonc`）
- 有効にするのは 2 段:
  - **デプロイ（管理者）**: デプロイの設定に D1・キュー・cron を足し、`ANTHROPIC_API_KEY` を入れる。束縛がなければ Murmur は無効で、ゲートウェイは今のまま動く
  - **利用者（本人）**: ゲートウェイの画面で、自分の接続（Outlook・Jira など）を Murmur の取り込みに使うことを有効にする。これが 0024 の「本人の同意」の代わりになる。記憶のオン・オフと同じ感覚で、いつでも外せる
- チームの単位は 0020 のまま（1 つのデプロイ = 1 つのチーム = 1 つの組織）。部署やプロジェクトを単位にしたいときは、同じ組織の中でゲートウェイのデプロイを分ける（api-gateway-mcp の 0004 の範囲でできる）

### 2. コードの境界はモジュールで守る

- Murmur は `src/murmur/`（またはワークスペースのパッケージ）に置く。依存の向きは Murmur → ゲートウェイの中核の狭い口（下）だけ。ゲートウェイの中核は Murmur を import しない。Worker の入口（`fetch`・`scheduled`・`queue`）で、有効なときだけ Murmur のハンドラにつなぐ
- Murmur の中の Functional Core / Imperative Shell（0001）はそのまま。`src/murmur/domain/` は Workers の API にも、ゲートウェイの中核にも依存しない
- ゲートウェイの中核が Murmur に渡す口（仮に `GatewayPort`）:
  - サインインしている人（今の JWT の `sub` の代わり）
  - 本人の接続で上流を **読む** ための fetch（GET と、取り込みの購読の管理に要る口だけを通す）
  - 共有の箱の `client_credentials` の接続（`Background` の入口の代わり。Murmur の側は未実装）
- 境界の守り方は決定 7

### 3. 消える配線

- Murmur のための `identity`（`IDENTITY_SIGNING_KEY` の Murmur 向けの使い道、`GATEWAY_JWKS`・`IDENTITY_ISSUER`・`IDENTITY_AUDIENCE`）。`identity` 自体は boid の逆接続（api-gateway-mcp の 0003）が使うので残る
- Service Binding（ゲートウェイ ↔ Murmur）。`Background` の名前付きエントリポイントも、ほかの Worker が使わなければ要らなくなる
- Murmur の CIMD（`/oauth/client.json`・`/oauth/callback`）、Murmur が持つゲートウェイのリフレッシュトークンと `TOKEN_KEY`、Murmur 自身の `PUBLIC_URL`（Webhook はゲートウェイのオリジンで受ける）
- murmur-deployments（デプロイの設定はゲートウェイの側に 1 つ）
- Murmur のための 2 回目の同意の画面

### 4. 「本体は上流のトークンを持たない」と「読み取りしかしない」の読み替え

- Murmur のモジュールはトークンを持たない。上流を読むときは、中核の口（決定 2）に頼む。トークンが Murmur のコードに渡らない形にする
- 読み取りしかしないこと（0012・0024）は、今より強く保証できる。今は Murmur が本人の `graph` の接続（読み書きの権限）のトークンをそのまま受け取り、Murmur のコードで書かないことを保証している（background-access.md）。まとめれば、中核の口が GET と購読の管理の決まった口しか通さないので、Murmur のコードに誤りがあっても書けない

### 5. スタンドからの見え方: MCP のツールは足さない。スキルと REST で使う

- Murmur の API は、普通の REST としてゲートウェイのオリジンの下（例 `/murmur/api/*`）に生やす。認可は、ゲートウェイの MCP の `issue_token` で発行した短命のトークン（ほかのサービスと同じ、ゲートウェイ自身が署名するもの）。Murmur のスライスはそのトークンを中核の口で検証する。今の `identity:murmur`（Ed25519 の JWT と JWKS）はなくなる
- MCP のツールは `list_credentials` と `issue_token` の 2 つのまま（直樹、2026-11-04）。理由:
  - ゲートウェイ自体がスキルを前提にしている。どのサービスも「スキルを読み、`issue_token` でトークンをもらい、REST を呼ぶ」で使う。Murmur だけ別の形にする理由がない
  - Murmur をゲートウェイなしで使うことはない。Murmur を使うスタンドは、必ずゲートウェイのコネクタとプラグインを持っている
  - ツールを足すと、ツールの説明と API の表の二重持ちになる。スキルなら、API を変えたのと同じ PR で直せる
- 本人が Murmur を有効にしているときは、コネクタの instructions（またはゲートウェイの共通の `api-gateway` スキル）に「『いまやるべきことは？』のような問いには、Murmur のスキルを読んでから答える」と載せる。利用者が Murmur という名前を知らなくても、スタンドが裏で読む
- スキルはゲートウェイのプラグインに同梱したまま（今と同じ）。本体の API とスキルが同じリポジトリ・同じ PR・同じ版で動く

### 6. リポジトリは 1 つ

- デプロイを 1 つにする以上、リポジトリも 1 つにする（ゲートウェイのリポジトリに Murmur を入れる。名前を変えるかは未決）
- 運用はゲートウェイに寄せる（PR で回す）。Murmur の main への直接の push と、murmur-dev への自動デプロイはやめる

### 7. 秘密は構造で隔てる（vertical slice）

Worker を分ければ isolate で隔てられる。同じ Worker の中では、ランタイムは隔ててくれない。代わりに、コードの構造で隔てる。脅威を 3 つに分けて考える。

| 脅威 | 例 | 構造で防げるか |
| --- | --- | --- |
| T1 Murmur 自身のコードの誤り | 鍵を読んでログに出す、書き込みの口を叩く、ゲートウェイの実装を直に呼ぶ | 防げる（下の 1〜4） |
| T2 依存の乗っ取り（悪意のあるコード） | Murmur が足したパッケージが env や `globalThis` から鍵を盗む | Murmur が依存を足さなければ、増分はなくなる（下の 5・6） |
| T3 信頼できない本文 | メールの本文によるプロンプトインジェクション | 構造とは関係なく、今と同じ（AI の出力は検証したデータで、コードとしては動かない） |

1. **スライスを縦に切る**: `src/gateway/`（保管庫・OAuth・プロキシ・MCP）と `src/murmur/` は互いの実装を import しない。共有してよいのは `src/contracts/`（口の型だけ。実装を持たない）。アーキテクチャのテストで import のグラフを検査する（Murmur の `test/architecture.test.ts` の延長）
2. **env を全体に見せない**: 全部の env を受け取るのは Worker の入口（`src/main.ts`）だけ。入口がスライスごとの env を組み立てて渡す。Murmur には Murmur の束縛と秘密（D1・キュー・`ANTHROPIC_API_KEY`）だけ。`import { env } from "cloudflare:workers"`（どこからでも env に届く口）は入口のほかで使うのを禁じ、テストで検査する
3. **秘密ではなく能力を渡す**: ゲートウェイの中核は、Murmur にトークンも鍵も渡さない。渡すのは関数（「この人の接続で、この口を GET する」）だけで、トークンはゲートウェイのスライスの中で使って捨てる。読み取りだけに絞るのもこの関数（決定 4）
4. **グローバルを書き換えない**: スライスのコードが `globalThis`・`fetch`・`crypto` を差し替えるのを禁じる（lint）
5. **Murmur は実行時の依存を足さない**: ゲートウェイがもう持っているもの（`zod` など）だけを使う。今の Murmur の実行時の依存は `@anthropic-ai/sdk`（2 ファイル）・`hono`（1 ファイル）・`drizzle-orm`（5 ファイル）。前の 2 つは fetch とゲートウェイの経路の仕組みで置き換えられる。`drizzle-orm` は D1 を直に使う形に置き換えるか、残すかを決める（未決 6）。`drizzle-kit` のような開発時だけの道具は、バンドルに入らないので構わない
6. **バンドルを検査する**: Workers は `eval` も `new Function` も許さないので、動くコードは全部バンドルに入っている。CI でバンドルに入ったパッケージの一覧を許可リストと比べ、`cloudflare:workers` を読むモジュールが入口と許したものだけかを確かめる。静的に確かめられるのは、Workers の性質のおかげ

**残るもの**: 許したパッケージ（ゲートウェイがもともと持っている `@modelcontextprotocol/sdk`・`@cloudflare/workers-oauth-provider`・`jose`・`zod`）が乗っ取られれば、同じ isolate の鍵には届く。これは Murmur を入れる前から同じで、まとめても増えない。それでも足りなくなったら、隔てる向きを逆にする: Murmur を外に出すのではなく、鍵を持つ部分（保管庫の暗号と署名）だけを小さな Worker に分け、本体からは RPC で使う。こうすると、Murmur に限らず、ゲートウェイの依存が乗っ取られても鍵そのものは持ち出せない（使われることは防げない）

## 危ないところと抑え方

- **プロトタイプの変更が本番のゲートウェイを巻き込む**: 1 つの Worker なので、Murmur の変更でデプロイが落ちたり、起動の例外が出たりすると、ゲートウェイ（業務の自動化）も止まる。抑え方: Murmur のハンドラは入口で例外を閉じ込め、ゲートウェイの経路に漏らさない。Murmur を使っていないデプロイは無効のまま。CI でゲートウェイと Murmur の両方のテストを通す。リクエストごとの失敗は Workers がリクエスト単位で隔てるので、壊れるのはデプロイと起動の段だけ
- **秘密とサプライチェーン**: 同じ Worker なので、Murmur のコードと依存が、ゲートウェイの `ENCRYPTION_KEY`・`SIGNING_KEY` と同じ isolate で動く。今は別の Worker なので、Murmur の側からゲートウェイの鍵には届かない。決定 7 の構造で、Murmur 自身のコードの誤りはほぼ防げ、依存から来る増分も消せる。残るのは、ゲートウェイがもともと持っている依存の乗っ取りで、これは今と同じ（決定 7 の「残るもの」）
- **信頼できない本文を AI に渡す**: メールの本文を Claude に渡す（プロンプトインジェクションの余地）のは今と同じ。AI の出力は zod で検証したデータで、コードとしては動かない。同じ Worker になっても変わらない
- **バンドルの大きさ**: コードはゲートウェイ約 3,200 行・Murmur 約 7,700 行。Workers の上限（有料で圧縮後 10 MB）には遠いが、まとめるときに測る
- **後から分けたくなったとき**: 0022（Murmur 間連携）や負荷で分けたくなっても、決定 2 のモジュールの境界があれば、口を Service Binding に差し替えて分けられる

## 代案

- **A. リポジトリだけまとめる**（前回の構想）: スキルと API の版の往復は減るが、配線・同意の 2 回目・デプロイの設定の 2 つは残る。利用者から見て別物のまま
- **B. 1 つのリポジトリ、1 回のデプロイ操作、Worker は 2 つ**（0021 の決定 4 をリポジトリをまとめて実現する）: 配線は `deploy` スキルで自動にできるが、なくはならない。秘密の隔離（isolate）は保てる。いちばん強い対抗案。この案を採らない理由は、利用者の体験（2 回目の同意、別の機能としての見え方）と、配線のコード約 1,300 行の保守が残ること。隔離で得られるもののうち、Murmur のコードの誤り（T1）と Murmur の依存（T2 の増分）は決定 7 で埋められ、残る差は小さい
- **C. ゲートウェイを Murmur に取り込む（逆向き）**: ゲートウェイを Murmur なしで使っている組織がある。採らない
- **D. 今のまま**: 上の「別々であることのコスト」が続く

## 採用したら直すもの

- 0020 の決定 1（Service Binding で結ぶ）・決定 2（`deploy` スキルで一緒にデプロイ）、0021 の決定 4、0024（本体はゲートウェイの OAuth クライアントになる → 中核の口）、0003（Murmur の identity）、0029（デプロイの設定はゲートウェイの側だけ）
- CLAUDE.md の「ゲートウェイとは 1 対 1」「本体は上流サービスのトークンを持たず」「本体の API は `Authorization: Bearer <JWT>` が必須」の書き方
- api-gateway-mcp: 新しい ADR（Murmur を機能として持つ）、`docs/background-access.md`・`docs/redesign.md` の Murmur の扱い、README のデプロイ

## 移し方（段取りの見通し。実装は採用してから）

1. **リポジトリをまとめる**: ゲートウェイのリポジトリに Murmur を入れる（履歴の残し方、npm と pnpm のどちらに寄せるか、プラグインのマーケットプレイスを壊さないこと）。この段ではまだ Worker は 2 つ
2. **中核の口を作る**: Murmur の側で、ゲートウェイを呼ぶところを `GatewayPort` の後ろにまとめる。実装は今の Service Binding と CIMD のまま差し替えられる形にする。あわせて実行時の依存を減らす（決定 7 の 5）
3. **1 つの Worker にする**: 入口で Murmur をつなぎ、口の実装を中核の直接呼び出しに差し替える。機能の有効化（決定 1）と画面の同意を作る。テスト用のデプロイで確かめる
4. **既存のデプロイを移す**: UBS では D1 は同じアカウントにあるので、ゲートウェイの Worker に同じ D1 を束縛すればデータは移さなくてよい。Outlook のサブスクリプションと Jira の Webhook は通知先の URL が変わるので作り直す。Murmur への同意（CIMD）は画面の有効化でやり直す。古い Murmur の Worker を消す

## 実装の記録

### 段取り 1（2026-11-04）: リポジトリをまとめた

novshi-tech/murmur の main を api-gateway-mcp の `murmur/` に `git subtree add` で取り込んだ（履歴つき）。`murmur/` は別のパッケージで、pnpm から npm に移した。ルートの CI に murmur のジョブを足し、ルートの vitest から外した。ゲートウェイ側の ADR は api-gateway-mcp の `docs/adr/0005`。

### 段取り 2（2026-11-04）: 中核の口と、実行時の依存の削減

- **口**: `src/ports/gateway.ts`（型と取り決めだけ。何も import しない）。`authenticate`（API のトークン → User）、`credentials`（本人の接続。同意がなければ `ConsentRequired`）、`upstream`（本人の接続で上流を呼ぶ関数。トークンは口の実装の中だけで使う）、`consent`（`begin` / `complete`）。今の実装は `src/connectors/gateway/remote.ts`（CIMD・MCP・REST）で、段取り 3 でゲートウェイの中核が同じ口を直に実装する
- **読める口（決定 4）**: 種類（`graph` / `jira`）ごとの許可リストを入口で固定して口の実装に渡し、口の実装が送る前に断る（`UpstreamRefused`）。Graph は `/v1.0/me` の下の GET とサブスクリプションの作成・延長・削除だけ（`src/connectors/graph/scope.ts`。GET は広めにした: 読み取りは安全側で、delta の続きのリンクの形を固定しないため）。Jira は 0034 の許可リスト（`JIRA_SCOPE`）。メールの送信・起票・コメントは口を通らないことをテストで確かめた
- **挙動の変更 1 つ**: 同意は有効で、選んだ接続がゲートウェイで「つなぎ直し」を要るときは 409 にした。前は Murmur の同意を捨てて取り直させていたが、それでは直らない
- **依存（決定 7 の 5）**: `@anthropic-ai/sdk` を fetch に（ヘッダーと本文は SDK が送っていたものと同じ。API の版も 2023-06-01 のまま。429・5xx・通信の失敗は 2 回まで試し直す）、`hono` を `src/http/router.ts`（`app.ts` が使う口だけ）に置き換えた。実行時の依存は `zod` と `drizzle-orm` だけ。バンドルは gzip 376 KiB → 214 KiB
- **境界のテスト（決定 7 の 1・2・4・5）**: `test/architecture.test.ts` に、口の実装を import してよいのは入口と口の実装だけ、`ports/` は何も import しない、`env` と `cloudflare:workers` は入口だけ、実行時の依存の許可リスト、グローバルを書き換えない、を足した
- 決定 7 の 6（バンドルの許可リストの検査）は、1 つの Worker にしたとき（段取り 3）にルートの CI で行う
