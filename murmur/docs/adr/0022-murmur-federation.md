# 0022 Murmur 間連携: チームごとの Murmur が、要約したスレッドを送り合う（構想）

- 状態: 構想（将来像。2026-10-23、直樹）。実装しない。設計に入るときに、この ADR を案に書き直す
- 関連: 0020（チーム単位でセルフホストする。チームの境界を越えることを最初から想定する）、0012（外には何も書かない。送信はスタンド、本体は事実を記録する）、0013（要約レベルの違うものを結ぶ）、0014（個人のメモは読者が本人だけのデータソース）、0018（1 人のユーザが複数の組織にまたがる対応はしない）、0006（act-as）、0008（要約を書くのはスタンド）

## 背景

0020 で、Murmur はチームごとにデプロイし、チームの境界を越えることを最初から想定する、とした。
最もうまくいった将来像は、大きい組織でチームごとに Murmur がいて、互いにタスクを送り合う形。

あわせて、1 人が複数のチームに属する問題を、個人の側から解く案も出た（2026-10-23）。
本人専用のツールを各チームのゲートウェイにつなぎ、各チームの Murmur から要約を書き込んで、チームをまたいで俯瞰する。
これは組織の管理者から見ると情報の脱出口になるので、実現は後回しにした。ただし、個人の Murmur をつなぐオプションがあることは大事（0020 の 4）。

この ADR は、その 2 つを同じ仕組みの上に置く構想を書き残す。

## 構想

### 送る: スタンドが送り、本体は記録する（0012 のまま）

- ほかのチームにタスクを送るのは、スタンドが人の確認を取り、ゲートウェイ経由で相手の Murmur に送って、`record_sent` で記録する。本体には送信の経路を足さない
- 外向けの要約を書くのはスタンド（0008）。1 件ずつ、人が確認して送り、記録が残る。自動では何も出ていかない。何を出すかは送る側のチームが決める
- 受ける側の Murmur にとって、届いたものは「要約レベルの違うデータソース」の受信（0013 の延長）。ふつうに Ingest して、誰の番かを決める

### 戻す: 状態は読み取りで返す。書くのは明示的に、読むのは自動で

- 送ったあとの相手側の状態（片付いたか、こちらの返事待ちか）を、相手の Murmur が自動で押し返すと 0012 に反する
- 相手は、共有したスレッドの状態だけを読み取り専用で公開する。こちらの Murmur はコネクタとしてそれを取り込む（取り込みは本体の仕事で、0012 の範囲内）。受け方はステップ 7 の状態の写し（`ThreadMirrored`）の延長
- これでチームをまたいでもボールを導出できる（リンク先から導出したボール、`turn.ts`）

### 共有する単位: 要約レベルのスレッド

- 1 件につき「要約、誰の番か（どちらのチームか）、期限、状態」くらい。生の連絡や本文は共有しない
- セルフホストなので、相手は別のバージョンで動いている。内部のイベントの形とは切り離した、小さくて安定した共有の約束（プロトコル）を決める
- 送り合うのは「ある要約レベルのスレッド」で、担当の割り当てやワークフローではない。タスク管理ツールや、Jira を連合させたものにはしない（0012「何でないか」）

### 相手の確かめ方と宛先

- 大きい組織で IdP が 1 つなら、送り手が誰かは署名で検証できる
- 会社をまたぐなら、相手の Murmur を登録して許可した相手だけ受け付ける形から始める。メールのような「誰からでも届く」にはしない（スパムの問題を抱え込む）
- 宛先（どの Murmur のどのリストか）は、最初は手で登録した相手の一覧。チームのディレクトリ（どこにどのチームの Murmur があるか）はそのあと

### つなぎ方

- 最初は HTTP（送るのはゲートウェイ経由の API、戻すのは読み取りの API か webhook）で足りる
- 互いの状態を近い時間で追い続けるなら、将来は Murmur 同士を WebSocket などで結合する仕組みが要るかもしれない。Durable Object の WebSocket（ハイバネーション）は、この形に合う（0021 の候補）

### Murmur を入れていないチームとも、今までどおり

- 相手が Murmur を持っていなければ、スタンドはメールや Jira で送り、`record_sent` で記録する（今の運用）。全員がそろうまで待たなくても、入れたチームから順に便利になる

### 個人の Murmur

- 自分専用の Murmur を「1 人のチーム」として立て、チームの Murmur と同じ約束でつなぐ。チームの側は、相手を許可するかどうかで制御できる
- 守ること
  - 読者は本人 1 人だけ。共有した瞬間に、チームをまたぐ共有の道具になり、0018 の問題が戻ってくる
  - チームの Murmur のスレッドを動かす操作（持つ・片付ける・送った記録）は、そのチームの接続で、そのチームの Murmur にする。個人の Murmur から書き戻さない
  - 持ち出すのは要約と、元のチームでの開き先だけ
  - **読む側の境界**: チームの境界を越えた俯瞰は、個人の経路（個人の Murmur の画面、スマホなど）だけで見る。
    あるチームのスタンド（そのチームの Claude のアカウント）から、そのチームのゲートウェイ経由で個人の Murmur を読むときは、そのチームの分だけを返す（ほかのチームについては、中身のない件数程度まで）。
    全部を返すと、ほかのチームの要約がそのチームの Claude のワークスペースに入る。呼び出し元のチームは、identity の JWT の発行者で分かる
- 個人の Murmur は複数のゲートウェイの JWKS を信頼し、発行者ごとにチームを決めることになる。0018 が共有の Murmur に入れなかった仕組みだが、読者が本人 1 人の個人の Murmur の中なら問題ない
- 当面は、チームごとのスタンドでそれぞれの Murmur を巡回する（0020 の 4）

## 設計に入るときの論点

1. **個人の Murmur に要約を入れるのは誰か**: 構想の元の形は「各チームの Murmur から要約を書き込む」。本体が外に書くことになるので、0012（外に書かない）と 0003（上流のトークンを持たない）に引っかかる。
   筋のいい解き方は、本体がゲートウェイを「本人として」呼ぶ経路（0006 の act-as）で、ゲートウェイが本人の資格情報を注入して中継する。これは実データの取り込みで未解決の「本体からゲートウェイを呼ぶ経路」（0016）と同じ仕組み。
   act-as ができるまでのつなぎは、各チームのスタンドの定期実行が、その Murmur を読んで個人の Murmur に書く形（0012 のまま）
2. **ゲートウェイの接続先がユーザーごとに違う**: 個人の Murmur の URL は人ごとに違うが、ゲートウェイの `SERVICES` の `base_url` はデプロイで 1 つ。接続先の URL も資格情報と一緒にユーザーが登録する認証方式が要る。
   任意の URL へ中継できると持ち出し口になるので、許可するホストを管理者が決められるようにする
3. **組織の管理者の制御**: 個人の Murmur やほかのチームの Murmur への送信・読み取りを許すかどうかを、チームの管理者がゲートウェイで決められること（許可する相手、許可するパスとメソッド）。外に出してよいかを本人ではなく組織が決める形にする
4. **共有の約束の中身**: 要約・誰の番・期限・状態の形、バージョンの扱い、相手の登録の手順
5. **0012 の「連携基盤ではない。メッセージを配送しない」との関係**: 送るのはスタンドで、本体は配送しない。戻すのは読み取り。この線を保てるかを、設計で確かめる
