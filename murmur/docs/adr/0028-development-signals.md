# 0028 開発のシグナル（PR・CI・レビューの依頼）を取り込むなら Murmur で（構想）

- 状態: 構想（2026-10-29、直樹とのディスカッション）。実装しない。0016 の次の段階の候補。設計に入るときに、この ADR を案に書き直す
- 関連: 0010（黒子。用件ごとに正を 1 つ）、0016（次の段階）、0024（外部コネクタ。Webhook は本体が持つ）、0012（boid からの系譜: シグナルの出どころ）、0027（オーケストレータ）、H9
- 発端: novshi-tech/boid の `docs/plans/split-and-shrink.md` §2.2

## 背景

boid の signal inbox には、開発者宛てのシグナル（Slack のメンション、Jira の担当課題、PR のコメント）が入っていた（0012「boid からの系譜」）。boid を縮退させ、card・signal inbox・triage を退役させるので、開発のシグナルの置き場が問いになった。

選択肢は 2 つあった。

- Murmur のデータソースにしない。PR の世話は Claude Code のクラウドセッションの PR の購読などに任せ、台帳には人との連絡だけを載せる
- GitHub・Bitbucket のコネクタを Murmur に足し、PR も 1 本のスレッドにする

## 構想

**取り込むなら Murmur に統合する**（直樹、2026-10-29）。boid では取り込まない。

- GitHub・Bitbucket のリポジトリをデータソースにし、PR を 1 本のスレッドにする。Jira の課題と同じく、PR が正で（0010）、状態（open / merged / closed、レビューの状態、CI の結果）は状態の写し（`ThreadMirrored`）でスレッドの属性に写す（H9 の延長）
- コメント・レビューの依頼はシグナルとして Ingest する。誰の番かは、レビューの依頼先・担当者・メンションの構造で決める（H8）
- 購読の管理（GitHub の Webhook、Bitbucket の Webhook）は本体が持つ（0024）
- PR と、それを生んだ連絡（Jira の課題、Slack の依頼）のスレッドは、アンカー（課題キー、PR の URL）の一致を結び候補として見せる
- PR の世話（CI を直す、レビューに答える）は実行で、スタンド（0027 のオーケストレータと、boid の job などの実行のスタンド）の仕事

## 設計に入るときの論点

1. 量: PR のイベント（CI の結果、自動のコメント、bot のレビュー）は人の連絡より桁違いに多い。どこまでシグナルにするか、状態の写しだけにするか
2. 「返事や対応を求めているか」の判断の多くが機械的に決まる（レビューの依頼、CI の失敗）。Ingest の AI の判断に回すものと、構造で決めるものの線
3. bot の発言（CI、レビューの bot）を誰のシグナルとして扱うか
4. Bitbucket はゲートウェイの git の接続先（api-gateway-mcp の ADR 0002）と同じ資格情報で読めるか
