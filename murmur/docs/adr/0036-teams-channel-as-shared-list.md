# 0036 Teams のチャネルを共有リストとして取り込む

- 状態: 採用（2026-11-05、実装とともに。下の「実装の記録」）。共有リストの作り方（単位・読者・経路・作れる人）は 0037（採用）に移した。この ADR は Teams の形（区切り・誰の番・アドレス・通知）を持つ。2026-11-05 に S0 を回した（`docs/research/2026-11-05-teams-jira-s0.md`）。結果を決定 5・6 に反映した。決定 4（メンションなし → 仕分け待ち）は 0038 の名指し（リスト宛て）と担当で言い直した（2026-11-06）
- 関連: 0037（共有リストはスペース単位で、読者はソースから写す）、0013（チームリストは持たない。誰の番は構造と持ち主で決める）、0014（スレッド 1 種類）、0005・0006（区切り）、0023（ゲートウェイの機能。口と読める口）、0024（Webhook は本体が持つ。通知はヒントで正は delta。個人の箱は本人の権限、共有の箱はアプリの権限）、0030（Contact とアドレス、誰の番はクエリ層）、0033（共有リストは共有の状態を持たないデータソースのためにある）、0035（アクションの範囲）、H3・H8

## 背景

次の段階の試用（0016 の段階 5）の前に、共有リストの実例を 1 つ実物で確かめておきたい（2026-11-04、直樹）。

- 0033 で、共有リストがいちばん効くのは共有の状態を持たないデータソース（LINE 公式アカウント ＞ チャット ＞ 共有メールボックス）と整理した。ここまで実物でつないだのは、個人リスト（Outlook の本人の箱、Jira）だけ
- チャットは区切りが緩く、誰が持っているかを表す場所がない。Murmur の `ThreadClaimed` と誰の番が「ほかにない共有の状態」になるのは、ここから
- 目指す姿（0023 の背景）: Jira になっていない Teams の件も、誰かが着手すれば `ThreadClaimed` が付き、ほかの人のスタンドは「この件は○○さんが対応しています」と答えられる
- 業務では Teams のチャネルでやりとりすることが多い

## 決定

### 1. 単位・読者・経路・作れる人は 0037 のとおり

- Teams のチャネル（標準・プライベート）1 つが 1 つのスペース、1 つの共有リスト
- 読者はチャネルのメンバーのうち Murmur の User。ゲートウェイのサインインが同じ Entra なら、ゲートウェイの User ID に入っているオブジェクト ID（`entra_<tenant>_<oid>`）で、メンバーの一覧の `userId` とそのまま対応が付く
- 経路はつないだ人の委任（ゲートウェイの `graph` の接続）。アプリの権限（保護された API）は使わない
- 作れるのはチャネルのメンバーなら誰でも。デプロイの設定で Teams の共有リストを許しているとき
- チャット（1 対 1・グループ）は今回は入れない。参加者だけの会話で、Outlook の箱と同じく個人リストの形になる

### 3. 区切り: Teams のスレッド（投稿と返信）を構造で 1 本にする

- チャネルの投稿と、その返信は、Teams の上で 1 つのスレッドになっている。投稿の ID をアンカー `threadTs`（Slack のスレッドと同じ意味）にし、返信は構造で投稿のスレッドに入れる
- 新しい投稿（返信でないもの）は、アンカーが新しいので、Slack と同じく AI の区切りに回す（前の話を新しい投稿で続けることがある）
- 投稿の編集・削除・リアクションは取り込まない（シグナルは追記だけ。0005）

### 4. 誰の番: メンションを宛先にし、なければ仕分け待ち

- 個人へのメンション（`@○○さん`）を宛先（`to`）にする。メンションされた人の番になる（構造。H8）
- チーム・チャネル・タグへのメンション（`@チャネル` など）は個人に落とさない（宛先なしと同じ）
- メンションがなく、AI が「返事や対応を求めている」と判断したものは、誰の番でもない（仕分け待ち）。誰かのスタンドが `ThreadClaimed` で持つと、その人の番になり、ほかの人のスタンドには「○○さんが対応している」と見える。これがこの ADR で確かめたいこと
- チャネルのメンバーはみな「こちら側」になる（0030 の sides: 読者の Contact のアドレス）。チャネルに外部のゲストがいれば、その人は相手側

### 5. アドレス: チャネル `teams`、値は Entra のオブジェクト ID

- `Channel` に `teams` を足す（`src/domain/entities.ts`。イベントの zod・fold のテスト・リプレイを同じ PR で直す）
- アドレスの値は `<tenantId>/<oid>`（投稿者・メンションの `user.tenantId` と `user.id`）。別のテナントのゲストが来ても衝突しない（S0）
- メンバーの同期のときに、読者の User の Contact に、その人の `teams` のアドレスを付ける（User ID から oid が分かるので、名寄せは要らない）。メンバーでない投稿者（ゲスト・外部）は、0035 のとおりスタンドが表示名を引いて Contact を作る（投稿に表示名が入っているので、コネクタが名前の候補を持たせてもよい）

### 6. 通知と同期: 通知はヒント、正は投稿の一覧の走査（S0 で決めた）

- チャネルのメッセージの変更通知（`/teams/{team}/channels/{channel}/messages`、`created,updated`、リソースのデータなし）を、Murmur の受け口（`/murmur/webhooks/graph`）で受ける。委任で作れ、期限は 3 日まで取れる（S0）。見回りで延長する
- **返信は delta では取れない**（delta は投稿の作成・編集だけ。返信が付いても投稿の `lastModifiedDateTime` は動かない。S0）。正は投稿の一覧（`$expand=replies`）を新しい順に読む走査にする。最後に動いた時刻（投稿と返信の時刻の大きいほう）が前回の同期から重なり（1 日）を引いた時刻より古いページまで辿る。一覧の並びは厳密ではない（数時間の逆転がある）ので、重なりで吸収し、`sourceRef` の重複排除で二重を防ぐ
- 通知も見回り（保険）も、同じ走査をする
- 読める口（0023 の決定 4）に `teams` の種類を足す。ゲートウェイの接続は `graph` のまま、読めるのは `GET /v1.0/teams/{team}/channels/{channel}/messages`（返信・`$expand=replies` を含む）と `/members`、つなぐときの `/v1.0/me/joinedTeams`・`/v1.0/teams/{team}/channels`、サブスクリプションの作成・延長・削除だけ。投稿・返信の口は通らない
- ゲートウェイの `graph` の権限に `ChannelMember.Read.All`（管理者の同意が要る）を足す。今の権限ではメンバーの一覧が 403（S0）

### 7. つなぎ方

- スタンドから `POST /connections/teams`（チームとチャネル）。つなぐ人が読めるチームとチャネルの一覧から選ぶ（`choose` と同じ形）
- データソースの名前はチームとチャネルの名前。窓口（connector owner）はつないだ人
- つないだら、スタンドがチャネルに知らせる（0037 の決定 4）

## 代案

- **A. アプリの権限で読む**（0024 の共有の箱の形。0037 で使わないことにした）: 読者を管理者が宣言でき、人の出入りに左右されない。ただ Teams のメッセージのアプリの権限は保護された API で、申請と従量課金がありうる。リソース固有の同意（RSC）でチームごとに絞る手もあるが、Teams のアプリを作ってチームに入れる作業が要る。試用の前にやることが重すぎる
- **B. チャットも一緒に入れる**: 1 対 1 のチャットは個人リスト、グループのチャットは参加者のリストになり、性格が混ざる。まずチャネルで共有リストを確かめる
- **C. チーム全体を 1 つのデータソースにする**: チャネルごとにメンバーが違う（プライベートチャネル）ので読者の境界が引けない

## 実物で確かめたこと（S0、2026-11-05）

`docs/research/2026-11-05-teams-jira-s0.md`。要点: メンバーの一覧は `ChannelMember.Read.All` が要る（403）、delta は返信を含まない、返信が付いても投稿の更新時刻は動かない、`$expand=replies` で返信が付く、委任で変更通知が作れて期限 3 日、メンションは個人の `user`（Entra の oid と tenantId）で本文の `<at id>` と対応する。

まだ見ていないこと: チャネル・タグへのメンション（このチャネルになかった）、ライフサイクルの通知、別のテナントのゲスト、プライベートチャネルのメンバー。

## 帰結

- ドメイン: `Channel` に `teams`（イベント・fold のテスト・リプレイを同じ PR で）。リストの読者を実行時に入れ替える操作（マスタの書き換え。0030 の変更の記録に残る）
- コネクタ: `src/connectors/teams/`（正規化・差分・サブスクリプションの計画は純関数、Outlook の形に合わせる）
- 口: `UpstreamKind` に `teams`、読める口 `TEAMS_SCOPE`（ゲートウェイの入口で固定）
- スキル: 「Teams のチャネルをつなぐ」と、共有リストで持つ・手放す（`ThreadClaimed`）の案内（`api-gateway-murmur`）
- シナリオ: Teams のチャネルを模した fixture を 1 つ足すか、development（Slack）の形で足りるかは実装のときに決める

## 実装の記録（2026-11-05）

- ドメイン: `Channel` に `teams`、接続先 `{ kind: 'teams', teamId, channelId }`、スペースのキー `teams:<team>/<channel>`、アドレス `<tenantId>/<oid>`。`connectTeamsChannel`（`src/domain/connection.ts`）は 0037 の `connectSharedSpace` の Teams の形
- 誰の番（`src/domain/turn.ts`）: ボールが Contact で、その Contact がリストの読者の User なら、その人の番（`by: 'addressed'`）。チームの中でのメンションは「相手の番」ではなく「その人の番」になる
- 正規化（`src/connectors/teams/normalize.ts`）: 投稿の ID を `threadTs`、返信は構造で投稿のスレッドに。個人へのメンションを `to`、本文の HTML はテキストに
- 同期（`src/connectors/teams/sync.ts`・`plan.ts`）: 投稿の一覧（`$top=50&$expand=replies`）を新しい順に、最後に動いた時刻が前回から 1 日引いた時刻より古いページまで（1 回の仕事で 10 ページまで）。サブスクリプションは Outlook と同じ台帳（フォルダ `messages`）で、通知は同じ受け口（`/murmur/webhooks/graph`）。期限は 3 日から 10 分引いたもの。読者の同期は 60 分ごと（と setup で）、メンバーの一覧の Entra の ID → `entra_<tenant>_<oid>`
- つなぐ: `POST /connections/teams`（`team`・`channel`。省けば `choose_team`・`choose_channel`）。Entra でサインインするゲートウェイだけ（User ID からテナントと oid を取る）。既にあれば、その場でメンバーを読者に写し、止まっていればつなぐ人の委任でつなぎ直す（Jira と同じ）。作った直後はその時点から取る
- 口: `UpstreamKind` に `teams`。ゲートウェイの入口で `graph` の接続と `TEAMS_SCOPE`（`src/connectors/teams/scope.ts`。メールの口は通らない）に結ぶ
- スキル: `api-gateway-murmur` 0.1.9（Teams をつなぐ、`connect_teams`）
- シナリオの fixture は足していない（正規化と同期はコネクタのテストで、誰の番はクエリ層のテストで確かめた）。試用で足りなければ足す
