# 0036 Teams のチャネルを共有リストとして取り込む

- 状態: 案（2026-11-05）。実装の前に「実物で確かめること」（S0）を回す
- 関連: 0013（チームリストは持たない。誰の番は構造と持ち主で決める）、0014（スレッド 1 種類）、0005・0006（区切り）、0023（ゲートウェイの機能。口と読める口）、0024（Webhook は本体が持つ。通知はヒントで正は delta。個人の箱は本人の権限、共有の箱はアプリの権限）、0030（Contact とアドレス、誰の番はクエリ層）、0033（共有リストは共有の状態を持たないデータソースのためにある）、0035（アクションの範囲）、H3・H8

## 背景

次の段階の試用（0016 の段階 5）の前に、共有リストの実例を 1 つ実物で確かめておきたい（2026-11-04、直樹）。

- 0033 で、共有リストがいちばん効くのは共有の状態を持たないデータソース（LINE 公式アカウント ＞ チャット ＞ 共有メールボックス）と整理した。ここまで実物でつないだのは、個人リスト（Outlook の本人の箱、Jira）だけ
- チャットは区切りが緩く、誰が持っているかを表す場所がない。Murmur の `ThreadClaimed` と誰の番が「ほかにない共有の状態」になるのは、ここから
- 目指す姿（0023 の背景）: Jira になっていない Teams の件も、誰かが着手すれば `ThreadClaimed` が付き、ほかの人のスタンドは「この件は○○さんが対応しています」と答えられる
- 業務では Teams のチャネルでやりとりすることが多い

## 決定（案）

### 1. 単位: チャネル 1 つ = データソース 1 つ = 共有リスト

- Teams のチャネル（標準・プライベート）を 1 つのデータソースにし、リストを共有にする
- **読者はチャネルのメンバーのうち、Murmur の User（ゲートウェイにサインインしたことがある人）**。見回りでチャネルのメンバーの一覧を読み、リストの `ListMember` に写す（足す・外す）。Teams で見えない人には Murmur でも見えない
  - ゲートウェイの User ID は Entra のオブジェクト ID を含む（`entra_<tenant>_<oid>`）ので、メンバーの一覧の `userId`（oid）からそのまま対応が取れる
  - メンバーから外れた人は `ListMember` から外れ、そのリストのスレッドは見えなくなる（0033 のリンクの可視性もそれに従う）
- チャット（1 対 1・グループ）は今回は入れない。チャットは参加者だけの会話で、Outlook の箱と同じく個人リストの形になる。必要になったら別に決める

### 2. 経路: つないだ人の委任の権限で読む

- スタンドから「このチャネルをつなぐ」を頼んだ人（チャネルのメンバー）の、ゲートウェイの `graph` の接続（委任）で読む。同意はほかのコネクタと同じ（ゲートウェイの画面で Murmur を有効にする）
- その人がチャネルから抜けたり、Murmur を無効にしたりすると、データソースは broken になる。別のメンバーがつなぎ直せば、同じデータソースの資格情報だけが入れ替わる（スレッドとリストはそのまま）
- **0024 の約束の改め**: 0024 は「個人の資格情報は読者 1 人のデータソースにだけ使う」（`seedProblems`）とした。共有の箱はアプリの権限にする、が前提だった。Teams では、**委任の資格情報で共有リストを作ってよいのは、読者がそのデータソースのメンバーの部分集合であることを、データソースのメンバーの一覧で確かめ続けられるとき**に限る、と改める。読者を管理者の宣言ではなく、ソースのメンバーの一覧から機械的に決めるので、つないだ人が見せてよい範囲を越えない
- アプリの権限は使わない。Teams のメッセージを読むアプリの権限は保護された API で、Microsoft への申請が要り、従量課金の対象になりうる。管理者の作業も重い（代案 A）

### 3. 区切り: Teams のスレッド（投稿と返信）を構造で 1 本にする

- チャネルの投稿と、その返信は、Teams の上で 1 つのスレッドになっている。投稿の ID をアンカー `threadTs`（Slack のスレッドと同じ意味）にし、返信は構造で投稿のスレッドに入れる
- 新しい投稿（返信でないもの）は、アンカーが新しいので、Slack と同じく AI の区切りに回す（前の話を新しい投稿で続けることがある）
- 投稿の編集・削除・リアクションは取り込まない（シグナルは追記だけ。0005）

### 4. 誰の番: メンションを宛先にし、なければ仕分け待ち

- 個人へのメンション（`@○○さん`）を宛先（`to`）にする。メンションされた人の番になる（構造。H8）
- チーム・チャネル・タグへのメンション（`@チャネル` など）は個人に落とさない（宛先なしと同じ）
- メンションがなく、AI が「返事や対応を求めている」と判断したものは、誰の番でもない（仕分け待ち）。誰かのスタンドが `ThreadClaimed` で持つと、その人の番になり、ほかの人のスタンドには「○○さんが対応している」と見える。これがこの ADR で確かめたいこと
- チャネルのメンバーはみな「こちら側」になる（0030 の sides: 読者の Contact のアドレス）。チャネルに外部のゲストがいれば、その人は相手側

### 5. アドレス: チャネル `teams`、値は Entra のオブジェクト ID

- `Channel` に `teams` を足す（`src/domain/entities.ts`。イベントの zod・fold のテスト・リプレイを同じ PR で直す）
- アドレスの値は投稿者・メンションの `user.id`（oid）。テナントが違うゲストもいるので、値は `<tenant>/<oid>` にするかは S0 で決める
- メンバーの同期のときに、読者の User の Contact に、その人の `teams` のアドレスを付ける（User ID から oid が分かるので、名寄せは要らない）。メンバーでない投稿者（ゲスト・外部）は、0035 のとおりスタンドが表示名を引いて Contact を作る（投稿に表示名が入っているので、コネクタが名前の候補を持たせてもよい）

### 6. 通知と同期: Outlook と同じ形（通知はヒント、正は差分）

- チャネルのメッセージの変更通知（`/teams/{team}/channels/{channel}/messages`、作成）を、Murmur の受け口（`/murmur/webhooks/graph`）で受ける。中身は使わず（リソースのデータは受けない）、差分を取りに行く
- 正は差分の取り込み（チャネルのメッセージの delta と、投稿ごとの返信）。見回りでも取る（保険）
- サブスクリプションの寿命は Outlook より短い見込み（S0）。見回り（5 分ごと）で延長する
- 読める口（0023 の決定 4）に `teams` の種類を足す。ゲートウェイの接続は `graph` のまま、読めるのは `GET /v1.0/teams/{team}/channels/{channel}/...`（メッセージ・返信・delta・メンバー）と、`/v1.0/me/joinedTeams` などのつなぐときの一覧と、サブスクリプションの作成・延長・削除だけ。投稿・返信の口は通らない
- ゲートウェイの `graph` の権限に、メンバーの一覧を読む権限（`ChannelMember.Read.All` など。S0）を足す

### 7. つなぎ方

- スタンドから `POST /connections/teams`（チームとチャネル）。つなぐ人が読めるチームとチャネルの一覧から選ぶ（`choose` と同じ形）
- データソースの名前はチームとチャネルの名前。窓口（connector owner）はつないだ人
- 同じチャネルを別の人がつなごうとしたら、同じデータソースを返す（資格情報は今のものが broken のときだけ入れ替える）

## 代案

- **A. アプリの権限で読む**（0024 の共有の箱の形）: 読者を管理者が宣言でき、人の出入りに左右されない。ただ Teams のメッセージのアプリの権限は保護された API で、申請と従量課金がありうる。リソース固有の同意（RSC）でチームごとに絞る手もあるが、Teams のアプリを作ってチームに入れる作業が要る。試用の前にやることが重すぎる
- **B. チャットも一緒に入れる**: 1 対 1 のチャットは個人リスト、グループのチャットは参加者のリストになり、性格が混ざる。まずチャネルで共有リストを確かめる
- **C. チーム全体を 1 つのデータソースにする**: チャネルごとにメンバーが違う（プライベートチャネル）ので読者の境界が引けない
- **D. 読者を宣言で持つ**（seed や管理画面）: 人の出入りのたびに手が要り、Teams の見え方とずれる

## 実物で確かめること（S0）

- 委任の `ChannelMessage.Read.All` で、チャネルのメッセージの変更通知を作れるか（リソースのデータなし）。寿命の上限と、ライフサイクルの通知
- チャネルのメッセージの delta が返信を含むか。含まなければ、返信をどう差分で取るか（投稿の `lastModifiedDateTime` が返信で動くか、返信の一覧を `lastModifiedDateTime` で絞れるか）
- メンバーの一覧を読む最小の権限（`ChannelMember.Read.All`・`TeamMember.Read.All`）と管理者の同意。プライベートチャネルのメンバー
- メンションの形（`mentions[].mentioned.user.id`、チャネル・タグへのメンションの見分け方）と、本文（HTML）からメンションの部分を落とした文の取り方
- ゲスト・共有チャネル（別のテナントの人）の `user.id` と `tenantId`
- ゲートウェイの `graph` の接続（UBS）に今ある権限で足りるか。足りなければ同意をやり直す範囲

## 帰結

- 0024 の決定 3 の約束（個人の資格情報は読者 1 人）を、決定 2 のとおり改める。`seedProblems` は「委任の資格情報の共有リストは、読者をソースのメンバーから写す」形に直す
- ドメイン: `Channel` に `teams`（イベント・fold のテスト・リプレイを同じ PR で）。リストの読者を実行時に入れ替える操作（マスタの書き換え。0030 の変更の記録に残る）
- コネクタ: `src/connectors/teams/`（正規化・差分・サブスクリプションの計画は純関数、Outlook の形に合わせる）
- 口: `UpstreamKind` に `teams`、読める口 `TEAMS_SCOPE`（ゲートウェイの入口で固定）
- スキル: 「Teams のチャネルをつなぐ」と、共有リストで持つ・手放す（`ThreadClaimed`）の案内（`api-gateway-murmur`）
- シナリオ: Teams のチャネルを模した fixture を 1 つ足すか、development（Slack）の形で足りるかは実装のときに決める

2. つないだ人が抜けたときに、ほかのメンバーへ知らせるか（broken はスタンドが `GET /connections` で見る）
3. メンバーの同期の間隔（見回りのたびか、もっと間を空けるか）
