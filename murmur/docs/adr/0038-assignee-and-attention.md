# 0038 誰の番は「担当」と「名指し」の 2 つの軸で決める。ボール・どちら側か・読者が 1 人をやめる

- 状態: 採用（2026-11-06、直樹とのディスカッション。未決 1〜4 は同じ日に決めた。実装の記録は末尾）
- 関連: 0008（業務の知識を持たない）、0010（黒子）、0012（抽出と追跡）、0013（誰の番は構造と持ち主で決める）、0014（スレッド 1 種類、fold は 1 段）、0030（Contact とクエリ時の解決。この ADR で改める）、0031（タスクはメモのスレッド、写しは決まった形。この ADR で改める）、0033（リストの性格）、0035（状態を持つデータソースのアクションの範囲。この ADR で改める）、0036（Teams。この ADR で改める）、0037（共有リストはスペース単位。この ADR で改める）、H6・H8・H9

## 背景

チームの中で運用している Jira のプロジェクトの共有リスト（0037）で、担当者でも起票者でもない読者の「自分の番」に課題が出た（2026-11-06 の実測）。

- 課題の担当者と起票者は、どちらもチームのメンバーだが Murmur の読者ではない（Jira のアカウントが Contact に結ばれていない）。共有リストの読者は、つないだ 1 人だけだった
- 起票のシグナル（起票者 → 担当者）を AI が「返事や対応を求めている」と判断した。同じ形の別の課題は「求めていない」と判断され、誰の番でもなかった。**誰の番が AI の判断で分かれていた**
- 原因（コード）:
  1. ボールの解決（`sides.ts` の `resolveBall`）が、求めたシグナルの**送り主**がこちらでなければ一律に `us` にしていた。宛先（担当者）を見ていない。0030 の「こちらのアドレスがなければ相手」が実装されていなかった
  2. 写しの holders（担当者）が Contact に解決できないので、`holderTurn` が効かずシグナルのボールに任せた（0030 の追記・0035 の決定 4 のとおり）。**Contact があるかどうかで誰の番がひっくり返る**
  3. `us` のスレッドを「読者が 1 人」の規則で、その読者に割り振った（0013・0030）。共有リストの読者の数は、名乗った人の数で変わる（0037）

直したい点を詰めていくと、対処療法では足りないことが分かった。今のモデルは LINE 公式アカウント・共有メールボックス（お客さん ↔ チームの 2 者の会話）を念頭に作られている。

- 2 者の会話では、送り主の側が分かれば受け手の側も決まる。だから「どちら側か」を送り主で決め、こちらなら次に「こちらの誰か」（turn）を決める 2 段で足りた
- チームの中の会話（Jira・Teams・Slack）は、送り主も受け手もチームの人で、参加者が 3 人以上いる。2 者の前提が成り立たない
- 「こちら」が 2 つの意味で使われていた: チーム（`us`・仕分け待ち。0013・0030 の背景）と、そのリストの読者のアドレス（0030 の「こちら」）。共有リストでは チーム ⊋ 読者 で、名乗っていないチームのメンバーは「あちら」に落ちる
- 状態のソースでは、ボールの出所が 2 つ（写しの holders とシグナルのボール）あり、0031 の優先順位で混ぜていた
- ボールの移り方は、AI の「求めているか」（needsResponse）で補っていた（求めないシグナルは上書きしない）。それでも 0030 の「分かっている代償」（同じ側の別の人の一言でボールが空になる）があった

## 考え方

知りたいのは「いま、このスレッドに対処する責任を誰が負っているか」。それを 2 つの独立した事実に分ける。

- **名指し**: 送り主が「少なくとも読んでほしい」と思った人。宛先が存在すれば機械的に決まる。アクションの要求か FYI かは、名指しされた本人かスタンドが読んで判断する。Heddleway は意味を判断しない（0008）
- **担当**: このタスクを進める人。名指しだけでは、複数の人が名指しされたときにお見合いになって進まないことがあるので、1 人に絞れる必要がある。Jira では担当者がそれにあたり、LINE・Teams・Slack ではユーザーが明示的に持つ（claim）

どちらも**人（アドレスか User）を指す**。スレッドの状態（仕分け待ち・相手待ち・期限超過）は、この 2 つから導く見え方にする。

## 決定

### 1. 担当の出所は、データソースの種類で 1 つに決める

| データソース | 担当の出所 | Murmur での claim |
| --- | --- | --- |
| 状態を持つソース（Jira、将来の PR） | 写しの `holders`（Jira は担当者。アドレスのまま） | 断る（担当はソースで移す。スタンドはそのサービスのスキルで行う） |
| 状態を持たない共有リスト（LINE 公式アカウント・共有メールボックス・Teams・Slack） | `ThreadClaimed` | 持つ・引き継ぐ・手放す（今のとおり） |
| 個人リスト（Outlook など、読者が本人だけ） | 本人（暗黙。claim は要らない） | 要らない |

- スレッドごとに優先順位で選ぶ（0031 の「持ち主 ＞ holders ＞ シグナルのボール」）のをやめる
- 担当は原則 1 人。ソースが複数持つもの（PR のレビュアー）はそのまま複数を許す
- 担当がアドレス（Murmur にいない人）でもよい。そのアドレスが読者のものなら、その読者の担当として見える

### 2. 名指しは、シグナルの宛先から溜まる

- 名指しはアドレスの集まり。シグナルの宛先（`to`）が、そのシグナルで名指しされた人。送り主は除く
- 宛先の決め方はコネクタが今のとおり写す（Jira の起票は担当者、コメントはメンション。Teams は個人へのメンション。メールは To と CC）
- **リスト宛て**: データソースの窓口のアドレス（`selfAddresses`）と、グループのチャネルで宛先のない投稿（今の fold の `except`）。リスト宛ての名指しは、**見るときに**そのときのリストの読者（ListMember）に展開する（送り主本人は除く）。イベントには窓口のアドレスのまま残す（マスタから引いた値をイベントに焼き込まない。0030）。一覧では、名指しとリスト宛てを分けて見せる
- 名指しは上書きしない。スレッドの最後の 1 通で決めると、3 人以上の会話で、ほかの人の発言で自分への名指しが消える（代案）

### 3. 名指しを外すのは、明示的な操作だけ

- 新しいイベント（名前は未決 1。仮に `AttentionAcknowledged`）: スレッド・外すアドレス・どのシグナルまでか・外した User
- 外すのは「そのシグナルまで」の名指し。それより後に名指しされれば、また残る
- 発言しただけでは外れない（「後で見ます」もある。発言から応えたかを推測するのは意味の判断）
- 外していいかは、スレッドを読んでスタンドが判断する。量はスタンドが操作するので問題にしない。スタンドから返事を送るとき（`record_sent`）に、自分への名指しを一緒に外せばよい
- イベントにはアドレスを書く。外す User を、そのリストでの本人のアドレスに直すのは操作の判断（コア）で行う。fold はマスタを読まずに、アドレスとシグナルの順番だけで「残っている名指し」を畳む（0014・0030）

### 4. 外せるのは、自分への名指しと、このリストの読者でないアドレスへの名指し

- 読者（そのリストの ListMember）への名指しは、本人だけが外せる
- 読者でないアドレス（お客さん、まだ参加していないチームのメンバー、Murmur の User だがこのリストの読者でない人）への名指しは、そのリストの読者なら誰でも外せる。お客さんが返事をくれたときは、それを読んだ担当のスタンドが、自分への名指しと一緒に外す
- 読者でないアドレスかどうかは、そのリストの読者が名乗ったアドレス（0030 の決定 7 のアイデンティティ）と比べて決める。リストに閉じたアドレスの比較で、相手の Contact があるかどうかは使わない
- 外した人と時刻はイベントに残るので、誰が代わりに判断したかも追える

### 5. 後から読者になった人

- イベントにはアドレスしか残らず、読者かどうかは見るときに決まる。後から ListMember になった人には、過去の自分のアドレスへの名指しが、自分の名指しとして見える
- 参加する前に、ほかの読者が代わりに外したものは外れたまま
- 参加した時点で、そのアドレスを外せるのは本人だけになる
- 結び付くのは、イベントのアドレスと本人が名乗ったアドレスの値が一致するときだけ（Jira の accountId、Teams の Entra の ID は一致する。メールの別名などは名寄せするまで結び付かない）
- 溜まった名指しは、閉じたスレッドを数えないことと、参加のときにスタンドがまとめて外すこと（スレッドごとのイベントを 1 回の承認で書く）で片付ける。リスト単位の 1 つのイベントにはしない（スレッドの fold がほかのスレッドのイベントを読むことになり、0014 の「fold は 1 段」が崩れる）

### 6. 見え方は 2 つの軸から導く

| 見え方 | 条件 |
| --- | --- |
| 自分の番 | 開いている ∧（自分が担当 ∨ 自分への名指しが残っている ∨ リスト宛ての名指しを自分が外していない）。理由（担当・名指し・リスト宛て）を添える |
| 仕分け待ち | 共有リスト ∧ 開いている ∧ 担当がいない |
| 相手待ち | 開いている ∧ 読者でないアドレスへの名指しが残っている |
| 期限超過 | 返事の期限（`record_sent` の返事期待）付きの名指しが、期限を過ぎても残っている |

- 閉じたスレッド（片付け・ソースで完了）は、どの見え方にも数えない
- 個人リストでは、自分への名指し ≒ これまでの「こちらの番」、読者でないアドレスへの名指し ≒ 「相手の番」。両方が同時に立つこともある（CC など。実態のとおり）
- 「待ち」はモデルの概念にしない。誰を待たせているか（人）は名指しで、相手待ちはその見え方

### 7. やめるもの

- ボール（`us / user / contact / none`）と、誰の番（`Turn`）の 2 段。`us` は要らない（共有リストでは仕分け待ちかリスト宛ての名指し、個人リストでは本人）
- 「どちら側か」の判定（`sides.ts` の送り主で側を決める解決）。「こちら」は、名指しを外す権利（決定 4）と見え方の「相手待ち」で、読者のアドレス ∪ リスト宛てのアドレスとして使うだけ
- シグナルのボール（`Request`）。名指しに置き換わる
- 「読者が 1 人ならその人の番」。個人リストは本人が暗黙の担当、共有リストは仕分け待ち
- ボールのための needsResponse。誰の番にも使わない
- 写しの holders が Contact に解決できないとき効かない、という規則（0030 の追記、0035 の決定 4）。番の種類は Contact があるかどうかで変わらない。Contact は名前を出すためだけに使う

## 代案

- **今のモデルに対処療法を足す**（解決できない holders をアドレスのまま相手の番にする、共有リストで「読者が 1 人」を使わない、送り主ではなく宛先で側を決める）: 今回の件は直るが、2 者の会話の前提とボールの出所が 2 つあることは残る。Teams・Slack を足すたびに同じ形の穴が出る
- **スレッドの最後の 1 通で名指しを決める**（上書き）: 単純だが、3 人以上の会話で、ほかの人の発言で自分への名指しが消える。今のモデルは needsResponse で補っていたが、本体から意味の判断を外すと補えない
- **人ごとに、最後に名指しされた時刻とその人の最後の発言を比べる**（発言で外れる）: ルールは 1 つで fold で決まるが、発言は応えた証拠にならない
- **リスト宛てを取り込むときに読者へ展開する**: fold はアドレスだけで済むが、マスタから引いた値をイベントに焼き込むことになり（0030 が `direction` を外したのと逆）、名指しとリスト宛ての区別も消える
- **読者でないアドレスへの名指しは外せないまま残す**: お客さんやまだ参加していない人の分が溜まり続ける。代わりに外す権利を読者に与えるほうが、外れ方の原則（明示的な操作だけ）を崩さない

## 帰結

- 今回の件: 担当も名指しも、読者でない担当者。読者はどの見え方にも出ない（相手待ちには出る）
- 誰の番が AI の判断に依らなくなる。Ingest に残る AI の判断は区切りだけになる（needsResponse を残すかは未決 2）
- ADR: 0030（クエリ層の誰の番、こちら、読者が 1 人、分かっている代償）、0031 の決定 6（誰の番の優先順位）、0035 の決定 4（解決できない holders）、0036 の決定 4（メンションなし → 仕分け待ち。名指しはリスト宛て）、0037（読者が名乗ったアドレスで、外す権利が決まる）を、この ADR で改める。採用したら各 ADR の状態にその旨を書く
- イベント: 名指しを外すイベントを足す。CLAUDE.md の約束どおり、zod スキーマ・fold の純関数テスト・リプレイテスト（H1）と fixtures の expected を同じ PR で直す
- fold（`comm.ts`）: ボールの代わりに、名指し（アドレスごとに、最後に名指しされたシグナルと、外した位置）を畳む。担当は写しの holders と `ThreadClaimed` をそのまま持つ
- クエリ層: `turn.ts`・`sides.ts` の判定を、2 つの軸からの導出（決定 6）に置き換える。`derivedBall`（メモのスレッドの導出したボール）も、結んだ先の見え方から導き直す
- コマンド: 状態を持つソースのスレッドへの claim を断る（`commands.ts`）。名指しを外す操作と、参加のときのまとめての外しを足す
- HTTP API: スレッドの `ball`・`turn`・`unansweredSince` を、担当・名指し（残っているものと外した記録）・見え方に置き換える。`filter=my_turn`・`triage` の意味が変わる。スキル（`plugins/heddleway/skills/murmur/SKILL.md`）の手順と API の表を同じ時期に直し、プラグインの版を上げる
- テスト: `test/domain/turn-shared-jira.test.ts`（今回の再現。今は赤）の期待値を、新しい形に書き直す。H8 のテスト（`turn.test.ts`・`mirror.test.ts`）とシナリオの expected も直す
- 仮説 H8 の言い方を「構造（宛先・担当）と明示的な操作（持つ・外す）だけで、自分の番が決まる」に改める

## 実装の記録（2026-11-06）

決定のとおりに実装した。決定に書いていなかったことと、実装で決めたこと:

- イベント `AttentionAcknowledged`（`threadId`・`untilSignalId`・`addresses`・`list`・`actorUserId`・`reason`）。`addresses` は外すアドレス、`list` はリスト宛ての名指しを外した User について外す。fold（`comm.ts`）はアドレスごとに最後に名指ししたシグナルと外した位置（いちばん後ろ）を持ち、宛先のないシグナル（`broadcasts`）とリスト宛ての外し（User ごと）を持つ。外す操作はシグナルの位置で効く（ログの中の順番には依らない）。移し替えでなくなったシグナルまでの外しは効かない
- 状態を持つソースは、チャネルが `jira`・`bitbucket` のデータソース。個人リストは、個人のメモと、共有でない個人の資格情報の箱（Outlook）。個人リストの暗黙の担当は API に出さない（`assignee: null`。自分の番は名指しで決まる。担当を出すと開いているスレッドが全部自分の番になる）。個人リストでは `claim` を断る
- 自分の番（`myTurn`）の理由は `assignee`・`named`・`list`。`filter=my_turn` はそのどれか。`filter=awaiting`（相手待ち）を足した
- 返事期待は、その送信の宛先の名指しが全部外れれば消える（それまでは、その送り主以外のシグナルで消えていた）。返事が来ても、読んで相手の名指しを外すまで期限超過は残る
- 取り込みの区切りの「返事を待っているスレッド」（`awaitingThread`）は、読者でない相手への名指しが残っていて、その相手が名指しのあとにそのスレッドで発言していないもの。発言したかは区切りの判断にだけ使う（名指しは発言では外れない）。名指しだけで見ると、返事をくれた相手の別件が古いスレッドに入ってしまう（シナリオ absence の s06・repair-estimate の s05 で見つけた）
- `record_sent` に `acknowledge`（任意）。`true` なら、送ったスレッドの、送る前までの自分への名指しを一緒に外す（明示の指定。既定は外さない）
- まとめて外す `POST /acknowledge`（`thread_ids`）。スレッドごとのイベントになる（決定 5）
- Ingest: アンカーでスレッドが決まる受信（`fixed`）は AI を呼ばない。`SignalThreaded.needsResponse` は `null` を書き、fold は読まない（古いイベントの値も読まない）。プロンプトと構造化出力の `needs_response` は記録を取り直すまで残す（未決 9）
- Jira のコメントの宛先は、メンションした人だけ（未決 3）
- 保存された投影の形が古ければ（スレッドに `attention` がなければ）、読むときにイベントから作り直す（`isStaleProjections`）。動いているデプロイも、デプロイしたあとの最初の読みで作り直される
