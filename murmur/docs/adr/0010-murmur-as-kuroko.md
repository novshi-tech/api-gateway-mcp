# 0010 Murmur は黒子になる（用件ごとに正を 1 つ。受け皿のない用件だけ Murmur が正）

- 状態: 採用（2026-10-17、直樹と合意。正本はリポジトリ（0011））
- 関連: 0009（2 層のリスト。未決 5「元のサービスの側が用件を持つもの」をここで決めた）、0007（読み取り専用の試用）、0005、H5、H7

## 背景

0009 で Jira の課題の扱いを詰めたところ、development シナリオで加藤さんが Jira の状態をタスクの属性に手で写していた（a06〜a09）。
Jira の課題はそれ自体が用件で、Murmur がそれを写すと二重の入力とずれが生まれる。

一方で、用件のリストから Jira へ起票したい場面は多い（LINE 公式アカウントで来た用件を用件のリストに入れ、Jira に起票する。今は手でやっている）。

究極の形として 2 つの方向がある。

- A. Jira のようなタスク管理ツールを完全に置き換え、用件の単位の同期を不要にする
- B. 既存のサービスが主な UI になり、Murmur は黒子になる

どちらに進むにしても、当面は Jira との同期が要る。

## 決定

### 方向: B 寄り

- Murmur にしかない価値は、タスク管理の手前と周りにある。構造のない連絡（LINE・メール・Slack）を拾って用件に振り分けること、
  チャネルをまたいで誰が誰に返事を待っているか（ボール）を追うこと、境界と承認で外への出入りを守ること。課題の管理そのものは Jira や Backlog が成熟している
- 業務に特化したシステム（UBS の bm-next・board）は置き換えられない。A でも同期は要り続けるので、連携を得意にするほうが筋がよい
- Murmur の人向けの UI はもともとスタンド（Cowork / Claude Code）。A はボードやスプリントの画面を作ることになり、AI ネイティブの前提から外れる
- B は A への道を閉じない。スタンドが主な UI になって人が Jira を開かなくなれば、Jira はただの保存先になり、そこから置き換えるのは簡単

### 用件ごとに正を 1 つ

- 元のサービスの側に用件があるもの（Jira の課題、bm-next の業務・不在・割当など）は、そのサービスが正。
  Jira のプロジェクトは、会話の層を経ずに用件の層のリスト（正は Jira）として直接つなぐ。課題が用件になる
- 受け皿のない用件（LINE の勤怠連絡、メールの問い合わせなど）は Murmur が正
- 起票で、用件の正が Murmur から元のサービスに移る。起票したあとの用件は「元のサービスの課題（正）+ Murmur が持つ会話（LINE のスレッドなど）」の組になる。
  元のサービスが知らない会話とボールを Murmur が持つのが、黒子としての価値
  （例: 開発者が Jira に「修正しました、確認をお願いします」と書いたが、報告者は LINE で連絡してきたお客さんで Jira を見ない。
  スタンドが「この回答を LINE で送りますか？」と提案できる）

### 同期: 状態は片方向、会話は両方向

上書きされるものは正を 1 つにし、追記されるものは両方向に流す。

| 種類 | 例 | 流し方 |
| --- | --- | --- |
| 状態（上書き） | ステータス、担当者、優先度、期日 | 正から Murmur への片方向の写し。Murmur の側では書き換えない。変えるときは元のサービスの画面か、スタンドがゲートウェイ経由で直接操作し、結果は写しとして戻る |
| 会話（追記） | コメント | 両方向 |

Murmur から元のサービスに書くのは、起票とコメントの 2 つだけで、どちらも送信（承認のゲート）として扱う。

コメントの 3 つのケース:

| 誰がどこで書いたか | Murmur での扱い | ボール |
| --- | --- | --- |
| Murmur を使わない人（社外の報告者、Murmur を使っていない同僚）が元のサービスに書いた | 受信のシグナルとして用件のスレッドに付く | こちらに返事や対応を求めているならこちら（@メンションがあればその人） |
| Murmur のユーザーが Murmur を通さず元のサービスに直接書いた | 観測された送信（`SignalObservedSent`。メールや Slack と同じ仕組み） | 宛先へ移る。返事期待は推定器で推定する |
| Murmur のユーザーがスタンド経由で書いた | 送信。コメントの ID を `sentRef` に持つ | 宛先へ移る。元のサービスから戻る通知は `sentRef` で重複排除する（H5） |

コメントの編集・削除（上書き）の扱いは未決。元の版を残して新しい版をシグナルとして足すか、無視するか。実データの試用（0007）で頻度を見てから決める。

### 起票ルール

- 購読（0009）の逆向き。「備品リストの用件のうち、設備の不具合は Jira の XX プロジェクトに起票する」のように、業務の知識をデータとして登録し、Murmur が実行する
- 承認: 最初はミニマムに作る意味で、ルールの登録を事前の承認と見なし、当たったら 1 件ずつの承認なしで起票する
- ユーザーサポート用のプロダクト（お客さんに課題が見えるもの）とつなぐ場合は、用件がそのままゴースト（外部の相手）にも見えるので、
  ルールごとに「1 件ずつ承認」を選べるようにする必要が出る可能性がある。ステップ 7 の「AI のリスク判断による自動承認」の線引きの最初の具体例
- 起票には書き込みの資格情報が要る。0007 の試用は読み取り専用なので、起票を実データで試すのはその先の段階。プロトタイプではダミーのコネクタで流れを確かめる

### UI

- 人が日々触るのは、既存のサービスの画面とスタンド。Murmur は業務用の画面を持たない
- 管理用に、内部の状態を確かめる参照専用の UI を作る。リストの一覧、タスク（用件・スレッド）の一覧、タスクの詳細くらいのシンプルなもの。
  今の `timeline.html`（`TIMELINE_TOKEN` を知っている人に全リストが見える確認用ページ）を育てる形を想定する。認証と可視性の扱いは作るときに決める

## 代案

- A. タスク管理ツールを置き換える: 差のつかない部分（課題の管理と画面）で戦うことになり、業務に特化したシステムは置き換えられないので同期も残る
- 完全な黒子（Murmur は正を一切持たない）: 受け皿のない用件（LINE の勤怠連絡など）を置く場所がない
- 状態も両方向に同期する: どちらが新しいかの判定、ワークフローの対応、衝突の解決を抱える。状態の変更は元のサービスの画面かスタンドで足りる
