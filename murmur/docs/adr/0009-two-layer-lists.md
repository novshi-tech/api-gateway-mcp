# 0009 リストを 2 層に分ける（会話の層 = データソース、用件の層 = 人とチーム）

- 状態: 採用（2026-10-17、直樹と合意。計画 v2（`docs/PLAN.md`）に反映した。正本はリポジトリ（0011））。
  **2026-10-20: 用件の層（チームリスト・購読・派生・外部のリスト）は 0013 で作り直した。会話の層と直す操作はそのまま**
- 関連: 0008（有力案「1 データソース = 1 リスト」の具体化）、0005（ボールの所在、派生を起こすのはスタンド）、H2、H3、H4、H6、H7

## 背景

H7 で absence を実環境で回したところ、s02（伊藤さんの「大丈夫です、入れます！」）を AI が打診のタスクではなく元の欠勤タスクに付けた（confidence 0.6）。
原因は 3 つ重なっていた。

- 外部派生は派生先リスト（`l_dispatch`）にタスクを作るが、返事は LINE 公式アカウント（`@ubs-clean`）に届く。返事の届く受信箱と、打診のタスクのリストがずれている
- AI に渡す候補の履歴はシグナルだけで、送った派生の本文が入らない。打診のタスクは空に見えた
- LINE には返信先のアンカーがない

根にあるのは、今のモデルのタスクが事実上「1 人の相手との会話」になっていること。ボールの所在は 1 か所しか持てないので、相手が増えるたびに派生でタスクが分かれ、
用件（「山本さんの欠勤対応」）は TaskLink の束としてしか存在しない。派生は「リストをまたぐ受け渡し（見える人が変わる）」と「外への送信（組織の外に出る）」の 2 つを兼ねている。

0008 の有力案（リスト = データソース）なら Ingest は業務の知識を要らないが、「私が関心のあるタスク」を一覧する方法がなかった。

## 決定（案）

リストを 2 層に分ける。

| | 会話の層 | 用件の層 |
| --- | --- | --- |
| リストの単位 | データソース（機械的に作る） | 個人（ユーザーごとに 1 つ、自動で作る）とチーム（人が作る。例: 採用、勤怠）。元のサービスのプロジェクト（Jira など。正はそのサービス、0010） |
| メンバー | データソースを読める人（元のサービスの権限を写す） | 個人なら本人、チームなら人が決める |
| タスク | スレッド（シグナルの束） | 用件（人が追うもの。複数のスレッドを束ねる） |
| 持つもの | ボール（こちら / 相手）と、つながった用件 | 状態・カスタム属性・クローズ・導出したボール |
| 決めるもの | Ingest（業務の知識なし） | 昇格のルール、スタンド、人 |

### 会話の層

- データソースの単位: メールはメールボックス（個人で 1 つ、グループごとに 1 つ。だいたい宛先アドレスごと）、Slack・Teams はチャネル、LINE は公式アカウント。
  Jira のように元のサービスの側に用件があるものは、会話の層を経ずに用件の層のリストとして直接つなぐ（0010）
- 外部の相手（ゴースト Party）はリストのメンバーにせず、スレッドの相手として持つ
- Ingest が判断するのは「同じ会話の続きか、新しい会話か」と「受け手に返事や対応を求めているか」の 2 つだけ。どちらも業務の知識に依らないので、プロンプトを固定できる
- スレッドの区切り（2026-10-17）。区切りのないチャネル（LINE の 1:1、Slack の DM やチャネル直下、返信でない新しいメール）でもスレッドを作る。
  スレッドになっていると、用件からの対応が明確になり、ユーザーが必要に応じて生の会話を確かめやすい。
  つながった用件の判断もスレッドの最初の 1 回で済み、続きは自動で同じ用件に入る
  1. アンカー（メールの In-Reply-To、Slack の thread_ts、Jira キー、PR 番号、LINE の引用返信の `quotedMessageId`）で決まれば、そのスレッド
  2. 同じ相手（グループのチャネルならそのチャネル）で、こちらが返事を待っているスレッドが 1 本だけなら、そのスレッド（構造で決まる。H7 の s02 はこれ）
  3. 発信者の直近のスレッド（グループのチャネルならチャネルの直近のスレッド）の中から、話題の続きかを AI が判断する。候補は数本で、業務の知識は要らない
  4. どれにも当たらなければ、新しいスレッドを作る
  - 区切りの基準は時間ではなく話題。同じ相手から勤怠と補充依頼が来れば、スレッドは 2 本に分かれ、並行して開いていてよい
  - 「直近」の範囲（最後のシグナルから何日か）は設定値。つながった用件が閉じていても、範囲内ならスレッドは候補に入る
- 閉じた用件につながったスレッドに続きが来たとき（2026-10-17）: シグナルはスレッドに付き、用件にも記録として見える。用件を開き直すのは、ボールがこちらに来たとき
  （返事や対応を求めている）だけ。「熱が下がりました」やお礼・スタンプでは開き直さない
- スレッドは open / closed とカスタム属性を持たない。ふだん人が見るのは用件の層なので、状態で絞り込めなくても困らない見込み。
  会話の層で要る一覧は「昇格していなくて、ボールがこちらにあるスレッド」（仕分け待ち）で、ボールと昇格の有無から導出できる
- ignore はなくす。すべてスレッドに記録し、昇格しないものが今の ignore にあたる。CI の成功通知・スタンプ・お礼はボールが動かないので昇格しない。
  H6 で ignore を選ばない問題（業務の知識が要る判断）は、「返事や対応を求めているか」（発話の種類の判断）に言い換わる

### 用件の層と購読（2026-10-17）

用件のリストは、データソースを「購読」して流入を定義する。購読は（データソース、条件）の組で、用件のリストの側に持つ。
リストはもともと仮想メールボックスのようなもので、用件のリストは購読で中身が決まる仮想メールボックスになる。

- 例: 勤怠リストが LINE 公式アカウントを「勤怠の連絡（欠勤・遅刻・早退）」の条件で購読する。備品リストは同じアカウントを「消耗品の補充依頼」で購読する。
  採用リストは recruit@ を条件なしで、info@ を「求人サイトからの応募通知」で購読する
- 購読を登録できるのは、用件のリストのメンバーで、かつデータソースを読める人（会話の層のリストのメンバー）。両側を見る
- 購読はテナントが DB に登録し、Murmur が実行する。スタンドはパターンに気づいたら購読や条件の手直しを提案し、人が承認して登録する。
  知識の出どころはスタンドと人のままで、日々の振り分けはスタンドが動いていなくても回る

条件は 2 種類。

- 構造の条件: データソース、宛先アドレス、送り主の Party・属性・ドメイン、件名のパターン、チャネル固有のフィールド（Jira の課題の種類、Bitbucket の通知の種類など）。
  コアの純関数で評価する。Party の属性（例: bm-next から同期した所属の現場）を使えば、業務の知識をデータで持ち込める
- 自然文の条件: 固定のプロンプトの分類器が、データソースを購読しているリストの条件の中から「どれに当たるか、どれにも当たらないか」を選ぶ。
  LINE 公式アカウントのように、同じ相手から勤怠と補充依頼が同じ会話で来るものは、キーワードでは分けられないので要る（メールだけなら構造の条件でほぼ足りる見込み）。
  プロンプトは固定で、業務の知識は購読の条件の文（データ）にある。0008 の選択肢 B（リストの説明を Claude が読む）に近いが、
  対象が会話の層ではなく昇格で、候補がそのデータソースを購読しているリストに限られる。Claude の呼び出しなので `RecordReplayLlm` を通す

スレッドを用件につなぐ（昇格する）順序。

1. スレッドがすでに用件につながっている → 用件に反映する（新しい昇格はしない）。用件から送ってできたスレッドは最初からつながっている
2. 購読に当たる（構造の条件 → 自然文の条件の順） → そのリストに用件を作る。ボールの宛先が特定のユーザーなら担当にする。
   購読は「返事や対応を求めていない」連絡にも当てられる（CI の失敗通知など。この通知は対応が要る、という業務の知識をここで表す）
3. ボールが特定のユーザーに来た（個人のメールボックス・DM なら本人、Slack の @メンションなら言及された人、Jira なら担当者、メンバーが 1 人のリストならその人）
   → その人の個人リストに用件を作る
4. アンカーの相互参照（Slack の本文の Jira キー、PR の本文の Jira キー、メールの件名のチケット番号）で既存の用件が見つかった
   → その用件のリストがそのデータソースを購読しているか、個人リストなら、つなぐ。そうでなければスタンドか人に任せる（購読を迂回して見える人を増やさない）
5. どれでもない → データソースの仕分け待ち（会話の層のリストのメンバーに見える）。スタンドか人がつなぐ。間違ったら直せるように、用件の統合・分割の操作が要る

昇格の判断はイベント（どの購読・どの経路で、誰が）として残す。購読はあとで変わるので、リプレイでは購読を評価し直さず、記録した判断を使う（IngestDecided と同じ扱い。H1）。

用件のボールは、つながったスレッドのボールから導出する（どれかがこちら → 用件の担当、全部が相手待ち → 返事待ち、期限は最も早いもの）。
相手が複数いる用件も 1 つのタスクで表せる。

### スレッドと用件は 1 対 1 以下（2026-10-17）

- 1 本のスレッドがつながる用件は多くても 1 つ。複数の用件につなぐと、スレッドのボールが 1 つなので、片方から返事をするともう片方のボールも動いてしまう
- 複数の購読に当たるときは、構造の条件を先に、構造の条件の中では登録順で採る。自然文の条件は分類器が 1 つだけ選ぶ
- 1 通に 2 つの話が入っている連絡（「明日休みます。あと洗剤がなくなりそうです」）は、つながった用件から、もう一方のリストへ派生で渡す（スタンドが本文を書く）
- 個人リストに来た用件をチームリストに渡すのも同じ。渡し方は 2 通りある
  - 派生: 自分の用件は残り、チームには派生の本文（要約）が届く。生のスレッドはチームに見えない
  - 移す: チームのリストに用件を作り、自分の用件をそこへ統合する（下の操作）。スレッドごと移るので、チームに生の会話が見える

### 直す操作（2026-10-17）

誤りが起きた層ごとに、基本の操作を持つ。どれも追記で、元の判断は消さない。

| 誤り | 操作 | 例 |
| --- | --- | --- |
| シグナルを違うスレッドに入れた（区切りの誤り） | シグナルを別のスレッドへ移す（新しいスレッドも可）。新しいスレッドは昇格の流れに乗る。今の `correct_ingest` の後継 | 欠勤のスレッドに「洗剤がなくなりそう」が続きとして入った → 新しいスレッドに出すと備品の購読に当たる |
| スレッドを違う用件につないだ（昇格の誤り） | スレッドを別の用件へ付け替える（新しい用件、つながない = 仕分け待ちに戻す、も可） | 補充依頼が勤怠に入った → 備品の用件へ |
| 同じ件で用件が 2 つできた | 用件の統合: B のスレッドを全部 A に付け替え、B は「A に統合」として閉じる。属性は A を優先し、B の値は履歴に残す。B の派生（返事待ちなど）は A に移す | 山本さんの家族からの電話連絡が別の用件になった |
| 対応の要らないものが仕分け待ちに残る | 片付け: スレッドのボールを「なし」にして理由を残す。今の IgnoreLog・`explain_ignore` を引き継ぐ | 迷惑メール、宛先違い |

- 用件の分割は、新しい用件を作ってスレッドを付け替えればできるので、専用の操作は持たない
- スレッドを用件につなぐイベントは、自動の昇格（購読・ボールの宛先・アンカー・送信の出どころ）と手の操作で同じ形にし、経路と操作した人を持たせる
- 操作できるのは、スレッドが見えていて、かつ移し先のリストのメンバーである人。付け替えると、元の用件のリストのメンバーにはそのスレッドが見えなくなる（元のデータソースのメンバーでない限り）
- スタンドがユーザーの指示で明示的に呼んだ操作に、Murmur 側で承認を求めない（`set_attribute` と同じ扱い）。外に何も出ず、追記で戻せる

### 送信と派生

- 送信: 用件から外へ出す。データソースのアドレスから送り、会話の層にスレッドができる（用件につながった状態で）。承認のゲートを通る
- 派生: 用件の層のリストの間の受け渡しだけ。見える人が変わるので要約を渡し、承認を通す
- 0008 の「外部派生の送信元は、派生先リストのデータソースのアドレスにする」は、送信が会話の層で起きることで自然に満たされる。返事は送ったスレッドに戻る

### 可視性（2026-10-17）

- リストのメンバーには、そのリストにあるものが見える。用件のリストに昇格したスレッドは、そのリストのメンバーに中身ごと見える
- メンバーは、リストを作る人の責任で決める。昇格で見える人が増えることを、別の承認の仕組みでは止めない。歯止めは、購読の登録に両側のメンバーであることを求める点（上）
- 昇格で見せるのは生のスレッドなので、Murmur が要約を作る必要はない（0008 で `AiSummarizer` を外す方針と合う）。要約が要るのは派生だけで、本文はスタンドが書く
- 用件のリストにあとから入った人には、過去に昇格したスレッドも見える（Slack のチャネルに入ると履歴が見えるのと同じ）

## 振り分けのモデル（チューニングの段階で検討する）

自然文の条件の分類（と、できればスレッドの続き / 新規の判断）は、型の決まった判断を返すだけで、文章を生成しない。
件数は受信の数だけあり、速さと費用が効く。判断専用のモデル（TypeSafe AI の Jev。2026-09 公開、分類・振り分け向け、
入力 100 万トークンあたり $0.042、70〜500ms。精度はベンダーの比較で Claude Opus 5 より下）がよく合いそう。

- まず Claude で回し、記録した判断を基準にする。チューニングの段階で、同じ入力を Jev で取り直して一致率と費用を比べる
- そのために、分類器の入出力を型（zod）で決め、モデルによらない形にしておく。記録・再生の層は Claude 以外のモデルも通せるようにする
- 別のベンダーに本文（スタッフの連絡、応募者の個人情報）を送ることになるので、0007「量の見通し」の 6（本文の置き場所）と一緒に判断する

## 代案

- 1 層のまま、リスト = データソースにし、「私のタスク」はボールを持つ人でリストを横断して検索する（思考実験）。
  用件をまとめられず（Jira の課題と Slack のスレッドが別々に出る）、カスタム属性の置き場もない
- 1 層のまま今の形（リストを業務で設計し、Ingest の Claude がリストの説明を読んで置く）。0008 の問題（業務の知識が Ingest に入る、置き間違いが境界を破る）が残る
- 同じタスクから外へ送る操作だけを足す（今日の議論の案 C）。absence は 1 タスクで済むが、Ingest の置き先の問題（0008）と「私のタスク」の問題は残る
