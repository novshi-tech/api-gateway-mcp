# 0037 共有リストはスペース単位で作り、読者はソースから写す

- 状態: 採用（2026-11-05、直樹とのディスカッション）。実装は各サービスの S0 のあと（Teams は 0036、Jira は 0034 の改め）。2026-11-05 に土台・Jira・Teams を実装
- 関連: 0013（チームリストは持たない）、0014（スレッド 1 種類）、0023（ゲートウェイの機能。口と読める口）、0024（個人の資格情報は読者 1 人。この ADR で改める）、0030（Contact とアドレス）、0033（リストの性格。この ADR で改める）、0034（Jira のコネクタ。この ADR で改める）、0035（アクションの範囲）、0036（Teams）、H3・H8

## 背景

Teams のチャネルを共有リストにする案（0036）を議論するうちに、「共有リストを誰が作ってよいか」が問いになった（2026-11-05、直樹）。

- ソースの役割（Teams のチームの所有者）で決める案は、所有者が UI で見つけにくく、サービスごとに役割の形が違う（Slack のチャネルマネージャー、Jira のプロジェクト管理者）。Slack を足したときに説明がばらばらになる
- Slack も 1 チャネル 1 共有リストにしたい。Teams と同じ規則で作りたい
- Jira は個人リストを既定にした（0033・0034）が、プロジェクトを共有リストにしたほうが、統一感の点でも、取りこぼしのなさ（個人の JQL の範囲の外を拾えない。0035 の割り切り）の点でもよい
- 個人リストが増えると、同じ課題が人の数だけ別のスレッドになり、リンクも持ち主にしか見えない（0033 の割り切り）。共有リストならリンクは読者全員に見える

## 決定

### 1. 共有リストの単位はスペース。1 スペースに 1 つ

- **スペース**: Teams のチャネル、Slack のチャネル、Jira のプロジェクト。サービスの上で「読める人の集まり」がはっきり決まっている単位
- 1 つのスペースに共有リストは 1 つ。誰がつないでも同じデータソースとリストになる（2 人目のつなぎは同じものを返す）

### 2. 読者はソースから写す。対応は本人が名乗ったものだけ

- 読者は「そのスペースを読める人」のうち、Murmur の User に対応が付く人。見回りでソースの一覧を読み、リストの `ListMember` に写す（足す・外す。マスタの書き換えとして変更の記録に残る。0030）
  - Teams・Slack: チャネルのメンバーの一覧
  - Jira: プロジェクトの閲覧の権限を持つ人の一覧（`/user/permission/search?permissions=BROWSE_PROJECTS`。アプリのアカウントは外す。S0 で読めることを確かめた）
- ソースのアカウントと Murmur の User の対応は、**本人が名乗ったものだけ**を使う。推測（メールアドレスの一致など）では付けない
  - サインインと同じ IdP のサービス: IdP の ID でそのまま付く（Entra でサインインするゲートウェイと Teams なら、ゲートウェイの User ID に入っている Entra のオブジェクト ID）
  - それ以外（Jira・Slack）: 本人がゲートウェイでそのサービスをつなぎ、Murmur を有効にしているとき、本人の接続で自分のアカウント ID を読んで付ける（Jira の `myself`）。つないでいない人は、つなぐまで読者にならない
- 読者がソースの読める人より広がらないので、共有リストを作ること自体では情報は漏れない

### 3. 経路は作った人の委任の権限

- 共有リストは、つないだ人のゲートウェイの接続（委任）で読む。アプリの権限は使わない（Teams は保護された API。どのサービスでも管理者の作業が重い）
- その人がスペースを読めなくなる・Murmur を無効にすると broken になる。ほかの読者がつなぎ直すと、資格情報だけが入れ替わる
- **0024 の約束を改める**: 「個人の資格情報は読者 1 人のデータソースにだけ使う」→「委任の資格情報は、読者 1 人のデータソースか、読者をソースから写し続ける共有リストにだけ使う」。`seedProblems` もこの形に直す
- 作った人には見えて、ほかの読者には見えないものがあるサービスでは、それを取り込まない。Jira の課題のセキュリティレベルが付いた課題は、共有リストに入れない（プロジェクトの閲覧権限があっても見えない人がいる）

### 4. 作れるのは、そのスペースを読める人なら誰でも。サービスは管理者が許す

- 共有リストを作れるのは、そのスペースを読める人（つなぐ人の委任で読めること）。ソースの役割（所有者・管理者）は見ない
- 管理者は、デプロイの設定で共有リストを許すサービスを決める（既定は許さない）。チャネルの投稿が AI の判断にかかり Murmur に写ること、読者の画面が増えること、費用は、チームの方針として管理者が決める。スペースごとの許可・除外は要るときに足す
- 作ったら、スタンドがそのスペースに知らせる（「このチャネルを Murmur で追い始めました」。スキルで案内する。Murmur 自身はソースに書かない。0012）
- 外せる（つなぐのをやめる）のは、作った人とゲートウェイの管理者
- 読者が自分の画面から外す（ミュート）のは、最初は入れない。困ったら足す

### 5. Jira は共有リストに置き換える

- Jira はプロジェクト単位の共有リストにする（0034 の個人リスト・本人の JQL の範囲をやめる）。誰の番は今までどおり担当者の写し（0031・0035）
- 0033 の「データソースが共有の状態を持てば個人リストを既定にする」を改める。共有の状態をソースが持つかどうかは、誰の番の決め方の違い（Jira は担当者の写し、チャットは `ThreadClaimed`）で、リストの性格を分ける理由にはしない
- 個人リストのまま残すのは、本人だけが読むもの（Outlook の本人の箱、個人のメモ）
- 今ある直樹の Jira の個人リストは、プロジェクトの共有リストができたら消す（直樹）

## 代案

- **ソースの役割（所有者・管理者）だけが作れる**: 所有者が見つけにくく、サービスごとに役割の形が違う
- **ゲートウェイの管理者だけが作れる**: 管理者がボトルネックになり、スペースの事情を知らない人が決める。チームリストを配る形に近づく（0013）
- **読者を宣言で持つ**: 人の出入りのたびに手が要り、ソースの見え方とずれる
- **アカウントの対応をメールアドレスで推測する**: 取り違えると、読めない人に見える

## 帰結

- 0024・0033・0034 の状態に「0037 で改めた」を書く。0036（Teams）は、この ADR の Teams の形として書き直す
- ドメイン: 共有リストの読者を実行時に入れ替える操作（マスタの書き換え）、User ごとのサービスのアカウントの対応（Contact のアドレスとして持てるか、実装のときに決める）、`seedProblems` の改め
- ゲートウェイの口: 管理者かどうか（外す操作のため）、どのサービスで共有リストを許すか（デプロイの設定）
- コネクタ: 読者の同期（メンバー・権限の一覧）を見回りに足す。Jira は範囲を本人の JQL からプロジェクトに変え、セキュリティレベル付きの課題を除く
- スキル: スペースをつなぐ手順、つないだらスペースに知らせる、持つ・手放す（`ThreadClaimed`）
- 試用（0016 の段階 5）は、この形の Teams と Jira で回す

## 実装の記録

### 土台（2026-11-05）

- マスタ: サービスのデータソースに `shared`（`spaceKey`・`createdBy`）。あれば共有リスト。`seedProblems` は、共有リストを「個人の資格情報は読者 1 人」から外し、「スペースに 1 つ」を足した
- `src/domain/shared.ts`（純関数）: `connectSharedSpace`（スペースに 1 つ。作った人が最初の読者、名乗りのアドレスを本人の Contact に付ける）、`syncSharedReaders`（ソースの読める人を読者に写す。本人が名乗ったアドレスか、IdP の ID で User が分かる人だけ。つないだ人が外れたら `ownerLost`）、`replaceSharedCredential`（読者の 1 人の委任に入れ替える）、`canDisconnect`（共有は作った人と管理者、個人は本人）
- ゲートウェイの口に `isAdmin`（ゲートウェイの `ADMINS`）。外す操作（`Connections.disconnect`）は `canDisconnect` で決める
- 設定: 共有リストを許すサービスを `MURMUR_SHARED_SERVICES`（例 `jira,teams`）で渡す（`MurmurConfig.sharedServices`。既定は空）。使うのは次の Jira から
- まだ: 読者の同期を見回りに入れること、つなぐ API（Jira・Teams のコネクタと一緒に）

### Jira（2026-11-05）

- 接続先に `projectKey`。範囲は `project = KEY AND level IS EMPTY`（セキュリティレベル付きを除く）。Webhook の絞りは `project = KEY`（JQL の `level` が Webhook の絞りで使えるか分からないので広めにし、差分の JQL で除く）。共有リストの差分は `key in (...)` で広げない（あとからセキュリティレベルが付いた課題を取らないため）
- つなぐ: `POST /connections/jira` に `project`。省けばつなぐ人が見えるプロジェクトの一覧（`choose_project`）。デプロイの設定で許していなければ `forbidden`。既にあれば、つなぐ人の権限でその場で読者を写し、止まっていればその人の委任でつなぎ直す。個人リストを作る経路（本人の JQL、`PATCH /connections/{id}`）はやめた。今ある個人リストは、消すまで今のまま動く
- 読者の同期: 見回りで 60 分ごと（と setup で）、`/user/permission/search?permissions=BROWSE_PROJECTS` の人（`atlassian`・有効）を `syncSharedReaders` に渡す。つないだ人が閲覧できなくなったら broken
- 一覧（`GET /connections`）に、読者になっている共有リストも出す（`shared`・`created_by`）
- スキル: `api-gateway-murmur` 0.1.8

### Teams（2026-11-05）

- 0036 の実装の記録のとおり。読者は名乗りなしで Entra の ID から付く（決定 2 の「サインインと同じ IdP」）。設定は `MURMUR_SHARED_SERVICES` に `teams`
