# 0008 Murmur は業務の知識を持たない（派生と要約はスタンド。新規シグナルの置き先は未決）

- 状態: 採用（2026-10-17。原則と「派生と要約」は採用。未決だった新規シグナルの置き先は 0009 で決めた。正本はリポジトリ（0011））
- 関連: H3、H6、0009（有力案を 2 層のリストに具体化した案）、0005「派生を起こすのはスタンド」、計画「Claude API: Ingest 判断と、境界越えの要約・翻訳」「提案: Ingest（またはスタンド）が DerivationProposed を出す。境界越えの要約は Claude が生成する」

## 背景

実装では、派生を起こすのはスタンドだけになった（0005）。一方で、境界越えの要約（`AiSummarizer`）は Murmur の中にある。
計画では Ingest も派生を提案する前提だったので、本文を書くスタンドがいない場合に備えて Murmur に要約を置いていた。
その前提がなくなり、「派生はスタンドが起こすが、その本文は Murmur が書く」という非対称が残っている。

派生先のリストを選べるのは、リストの役割を知っている側だけ。Murmur はそれぞれのリストの役割を知らないはずである。

## 決定（案）

### 原則

Murmur はどの業務でも同じ仕組みだけを持ち、業務の意味（リストの役割、何が対応の要る連絡か、誰に何を渡すか）は持たない。

| Murmur | スタンド |
| --- | --- |
| 事実の記録（イベント）、アンカーによる紐づけ、可視性、ボールの所在、期限の見回り | 意図と判断（何をどこへ渡すか）、文章（派生の本文・要約・翻訳） |
| 承認のゲート、境界を越える本文の検査 | 業務の知識（スキル、ユーザーとのやりとり） |

### 派生と要約

- 派生の提案も、その本文もスタンドが持つ。`propose_derivation` の `body` は必須にし、`AiSummarizer`（`boundary_summary`）は外す
- Murmur は、誰が書いた本文でも、境界を越える前に同じ検査を通す（生ペイロードの引用、渡し先が知らなくてよい情報が入っていないか）。
  結果は `list_proposals` の確認項目に指摘として出し、決めるのは人の承認。検査に Claude を使うなら `RecordReplayLlm` に乗せる
- 今は「内部事情・個人情報・引用を含めない」がスタンドの書いた本文には効かない（要約のプロンプトにしかない）。検査を Murmur に置くと、書き手によらず境界の守り方がそろう

## 未決: 新規シグナルの置き先（リスト）を誰が決めるか

原則に照らすと、今の Ingest は業務の知識に寄りかかっている。

- **new の置き先**: Ingest の Claude は seed のリストの名前と説明を読んで置き先を選ぶ。業務の知識をデータとして持ち込んでいる
- **ignore**: 「誰も動かなくてよい連絡か」も業務の知識。同じ CI の成功通知でも、チームによって雑音にも要件にもなる。
  H6 で AI が ignore を選ばなかった（`docs/HANDOFF.md`）のも、根はここにあるかもしれない
- attach（同じ用件の続きか）は会話のつながりの判断なので、業務の知識がなくても比較的決められる

置き先の判断が難しい理由:

- 1 つの受信箱（取得主体のアドレス）に、複数のリストの用件が混ざって届く。同じ送り主でも用件で置き先が変わる
- 置き先を決める知識（契約、担当、物件など）は業務側にあり、よく変わる
- 置き間違いは境界の問題になる。違うリストに置かれると、そのリストのメンバーに生ペイロードが見える（H3 の境界を振り分けの誤りが破る）
- 置いた後にタスクをリスト間で動かすイベントがない。直す手段は `correct_ingest` での振り分けのやり直しだけ

選択肢（未判断）:

- A. ルールだけで決める: 取得主体とチャネルで受信箱のリストに機械的に置き、仕分けはスタンドが後で行う。Murmur は知識を持たないが、仕分けの操作（リスト間の移動）が要る
- B. 今のまま: テナントが書いたリストの説明を Murmur の Claude が読む。知識はコードではなくデータにある、という線引き。精度は説明の書き方しだい
- C. スタンドが決めるまで保留する: 置き先の決まらないシグナルは保留にし、スタンドが仕分ける。スタンドが動いていないと止まる
- D. 組み合わせ: ルールで決まればそれで決め、決まらなければ AI が候補を出し、スタンドか人が確定する

### 有力案: 1 つのデータソースは必ず 1 つのリストに属する（2026-10-16、A の具体化）

リストはもともと仮想メールボックスのようなものなので、データソースとリストを 1 対 1 にしてもおかしくない。
後から直すと大きいので、プロトタイプの段階で入れることも考える。

- Murmur はリストの役割を知らなくてよい。Ingest が決めるのは attach / new / ignore だけで、置き先はデータソースから機械的に決まる
- 境界がそのまま守られる。メールボックスを見られる人 = リストのメンバーなので、置き間違いで生ペイロードが漏れない
- 別のリストで扱うべきものは、スタンドが内部派生で渡す。仕分け用の新しい仕組み（リスト間の移動）は要らない
- 外部派生の送信元は、派生先リストのデータソースのアドレスにする。返事は送信元のメールボックスに届き、
  アンカーは置けるリストのタスクにしか付かない（`resolveAnchors` の `placeable`）ので、こうしないと返事が派生に紐づかない

今の実装との差と、詰めること:

1. 「データソース」の単位がない。今は（取得主体 × チャネル）で置けるリストを複数持ち、User 主体ならその User が所属する全リストに置ける
   （`Directory.allowedListIds`）。「資格情報 + 絞り込み（ラベル・フォルダ・Slack のチャンネル）→ リスト 1 つ」のエンティティに替える。
   1 つの資格情報で多数のチャンネルが見えるもの（Slack など）は、チャンネル単位でデータソースを分ける
2. 個人の受信箱は「その人の受信箱リスト」になり、業務が混ざる人ほど仕分けの内部派生が増える。内部派生は 1 件ずつ承認が要るので、
   承認が多すぎる問題（計画「派生・境界・承認・送信・観測」）とぶつかる。量は 0007 の試用で測る
3. 重複排除のキー（`sourceRefs`）はテナント単位。同じメールが CC で 2 つのメールボックスに届いたら、それぞれのリストに 1 件ずつ置くのが正しい。
   `sourceRef` はデータソースごとに別の値にする、をコネクタの約束にする
4. ignore の判断は残るが、単位がリスト（データソース）ごとになるので、「このリストでは CI の通知は ignore」のような設定として外に出しやすい

決めるための材料は、実データでの試用（0007）で取る。受信箱ごとに、置き先のリストが何通りに分かれるか、
`correct_ingest` で置き先を直した件数、ignore を直した件数を見る。
