# 0026 自分専用の Murmur は作らない。横断は巡回で、個人のメモは各 Murmur の中に持つ

- 状態: 案（2026-10-29、直樹とのディスカッション）。採用したら 0020 の 4 と 0022 の「個人の Murmur」の節を直す
- 関連: 0020（チーム単位でセルフホストする。4: 個人の Murmur）、0022（Murmur 間連携の構想。個人の Murmur の節）、0014（個人のメモは読者が本人だけのデータソース）、0018（1 人のユーザが複数の組織にまたがる対応はしない）、H3
- 発端: novshi-tech/boid の `docs/plans/split-and-shrink.md`（boid の分割と縮退）§2.2

## 背景

0020 の 4 と 0022 で、自分専用の Murmur を「1 人のチーム」として立て、チームの Murmur と同じ約束でつなぐオプションを書いた。1 人が複数のチームに属する問題を、個人の側から解く案だった。

boid（直樹が個人で使ってきたパーソナル AI オーケストレータ）にはプロジェクトを横断する triage があり、Murmur はその card と signal inbox を引き継いだもの（0012「boid からの系譜」）。boid を縮退させる議論（2026-10-29）で、横断の置き場をどうするかが問いになった。

boid を使って分かったこと: **結局 workspace でフィルタして、それぞれのタスクを見ていた**。大事なのは複数のデータソースからの Ingest と判断で、人はそれぞれの workspace の「モード」でリストを眺めたい。横断の俯瞰は、思っていたほど要らなかった。

## 決定（案）

### 1. 自分専用の Murmur は作らない

- 0022 の Murmur 間連携の延長で、自分専用の Murmur に各チームの要約を集める形は、セキュリティの境界が微妙すぎる。0022 自身が論点に挙げていたこと（要約を入れるのは誰か、接続先がユーザーごとに違う、組織の管理者の制御、読む側の境界）は、どれも「チームの境界の外に本人だけの集約点を作る」ことから来ている
- チームの Murmur どうしの連携（0022 の本題）は、構想のまま残す

### 2. 個人のメモは、各チームの Murmur の中に持つ（0014 のまま）

- 個人のメモのデータソース（読者が本人だけ）は、今のとおり各 Murmur の中にある。1 つの Murmur の個人のメモは、そのチームの件だけを持つ
- 言葉を分ける。「個人のメモ」は各 Murmur の中のデータソース、「自分専用の Murmur」は別のデプロイ。「個人の Murmur」という言い方は、どちらとも取れるので使わない

### 3. チームをまたぐ俯瞰は、巡回で行う

- 0020 の 4 の「当面は、チームごとのスタンドでそれぞれの Murmur を巡回する」を、当面ではなく形として採る
- チームの数だけ Murmur とゲートウェイのペアを並べる（0020 の 1 対 1）。チームの境界は、受託先ごとの環境のような小さい単位でもよい。並べたペアを、スタンドが 1 つずつ見る

## 代案

- **自分専用の Murmur（0020 の 4・0022）**: 上の決定 1 の理由で採らない
- **1 つの Murmur の中で、本人だけがチームをまたいで見える**: 0018 で入れないとした仕組み（発行者ごとにチームを決める）が共有の Murmur に入る。採らない

## 帰結

- 採用したら、0020 の 4 を「自分専用の Murmur は作らない（0026）。チームをまたぐ俯瞰は巡回」に、0022 の「個人の Murmur」の節を「やらない（0026）」に直す
