# Murmur プロトタイプ計画 v2 — 外部リストとマイリスト

2026-10-17 · @Naoki NOSE · 設計の正本（`docs/adr/0011`）。立ち位置は `docs/adr/0012`、リストの構成は `docs/adr/0013`（2026-10-20 に反映）。v1 の計画はタグ `proto-v1` の `docs/PLAN.md`

## 目的と前提

このプロトタイプは、Murmur のデータモデルとアーキテクチャが成立するかを、外部接続なしで確かめるためのもの。製品の MVP ではない。

v1（`proto-v1`）で、イベントソーシングの土台（決定的な畳み込み、FC-IS、記録・再生、ゲートウェイ経由の認証、実環境へのデプロイ）は確かめた。
H7 を実環境で回したところで、リストの構成に根本の問題が見つかった（`docs/adr/0009` の背景）。v2 は 0008〜0010・0012・0013 の形にデータモデルを組み替え、もう一度確かめる。

- 検証対象: 外部リストとマイリスト（0013）、業務の知識を持たない Ingest、持ち主の操作と構造だけで決まる振り分け、
  送信の記録、正が外にある用件（黒子）、スタンドへのハンドオフ、Murmur の有無でスタンドの一手が変わるか
- 外部接続は全部ダミー。Claude API と、ゲートウェイ経由のスタンド接続は本物。実データでの試用（0007）は並行トラック
- UI は作らない。人が触るのはスタンド（Cowork / Claude Code）。管理用に参照専用の画面だけ作る（0010）
- 技術要素は v1 と同じ: Cloudflare Workers + Neon（Postgres）+ 既存の API ゲートウェイ

## 方向（0010・0012・0013）

Murmur は、連絡から対応の要る用件を抽出し、その経過を追跡する（0012）。**外部リスト**（データソースの写し。テナントで 1 つの共有の実体で、見えるのはそのデータソースを読める人）と、
**マイリスト**（各自の用件・メモ・属性。本人だけのもの）から成る（0013）。
綴じるのは、連絡（観測）、人とエージェントの行動（送った・持った・決めた・付け替えた）、用件に宛てたメモの 3 種類。
Murmur が判断するのは「どこに綴じるか」と「ボールが動いたか」だけで、何をするかは判断しないし、何も実行しない。**外には何も書かない**。
外への送信（メッセージ・起票・コメント）はスタンドがゲートウェイ経由で行い、本体にはその事実を記録する。前例は boid の card と signal inbox と identity 索引（0012「boid からの系譜」）。

Murmur は黒子（0010）。用件ごとに正を 1 つにし、受け皿のある用件（Jira の課題、bm-next の業務など）はそのサービスが正、受け皿のない用件（LINE の勤怠連絡、メールの問い合わせなど）だけ Murmur が正。
**チームの共有は既存のツール（Jira・グループメール・Slack）に任せ、Murmur はチームリストを持たない**（0013）。受け皿のない用件をチームで共有したければ、スタンド経由で外の受け皿に起票して記録する。
Murmur の価値は、構造のない連絡を拾って用件にすること（抽出）、チャネルをまたいで誰が誰に返事を待っているか（ボール）を追うこと（追跡）、
要約レベルの違い（LINE の生の会話と Jira の課題）とツールの垣根を越えて同じ用件を結び、どちらからも辿れるようにすること（索引）。

業務の知識（何をどこへ渡すか、どの連絡を誰が扱うか）は Murmur のコードにもプロンプトにもデータにも持たない（0008）。
誰が持つかは人とスタンドの操作（持ち主）と構造（宛先・メンション・担当者・読者が 1 人のソース）で決まり、何をするか・外へ何を書くかはスタンドが判断して実行する（0012・0013）。

## 検証仮説と合否基準

それぞれを自動テストにする。全部緑なら v2 のデータモデルは「成立」。

| # | 仮説 | 合否基準（テストの形） |
| --- | --- | --- |
| H1 | 畳み込みは決定的 | 投影を全削除してイベントからリプレイし、投影のハッシュが元と一致する（全シナリオ、メモリと Postgres）。外部リストを先に畳み、その投影を渡してマイリストを畳む 2 段で、逆の依存がない |
| H2 | 状態は二層で足りる | スレッドのボールは事前定義属性と持ち主から、用件のボールは参照するスレッドから導出できる。用件の状態は自前の open / closed とカスタム属性だけで表せる |
| H3 | 境界が守られる | 外部リストのメンバーには、そのデータソースのスレッドだけが見える。マイリストは本人だけ。持ち主と外の受け皿へのリンクはスレッドにあるので外部リストの読者に見える。テナント外は 0 件、ゴースト Party は何も取れない |
| H4 | 送信の記録と持ち主の操作が回る | スタンドが記録した送信（記録 → 送ったスレッドができてボールが相手へ → 返事は送ったスレッドに戻る → 期限超過）と、持ち主の操作（持つとボールがその人へ移って用件ができる、手放すと仕分け待ちに戻る、引き継ぐと移る）が、各遷移で期待どおりにボールを動かす |
| H5 | 観測と送信の記録を重複排除できる | スタンドが記録した送信と、同じメッセージの observed-sent が、どちらの順で届いても sent_ref で 1 本に統合され、状態が二重に変わらない（Jira のコメントでも） |
| H6 | Ingest が運用に耐える | 固定のプロンプトで、スレッドの区切りと「返事や対応を求めているか」の正解ラベルとの一致率が、アンカー込みで 90%、AI 判断のみで 80% を超える |
| H7 | スタンドに必要十分な情報が渡る | 実環境で、欠勤連絡とクレームのシナリオをスタンド主導で完走できる。人の操作はユーザーが Claude に出す指示と承認だけ |
| H8 | 構造と持ち主だけで振り分けが回る | 自然文の条件なしに、構造（宛先・メンション・担当者・読者が 1 人のソース・アンカー）と持ち主の操作だけで、4 シナリオのマイリストが期待どおりに組み上がる |
| H9 | 正が外にある用件を黒子として扱える | ダミーの Jira で、プロジェクトを外部リスト（1 課題 1 スレッド）としてつなぎ、状態は片方向の写し（スレッドの属性）で足り、コメントは両方向に重複なく流れ、スタンドが起票して記録すると LINE のスレッドと課題のスレッドが同じ用件に結ばれる |
| H10 | Murmur があるほうがスタンドは良い一手を出せる | 同じ absence を、Murmur なし（LINE・Gmail の MCP だけ渡したスタンド）とありで回し、完走できたか・ユーザーへの確認の回数・ツール呼び出しの回数・取り違えの件数・セッションが切れた後に続きから入れるかを比べ、ありが上回る。モデルを変えたら回し直す |

## アーキテクチャ

v1 と同じ（`docs/adr/0001`・`0003`）。本体 Worker 1 本、Neon、既存の API ゲートウェイの 3 つ。本体は上流サービスのトークンを持たず、外からの取り込みはゲートウェイ経由。外へは何も書かない（0012）。

- 本体 Worker: fetch（HTTP API・Webhook・管理用の画面）と scheduled（Cron: 取り込みのポーリングと期限の見回り）
- 判断はすべて純関数のコア（`src/domain/`）に置き、副作用はシェルに集める（FC-IS）
- スタンドはゲートウェイの MCP から本体の HTTP API を呼ぶ（認可の接続の形 (B)）。本体はゲートウェイが署名した sub を検証する
- Claude API（claude-sonnet-5-5、構造化出力）を使うのは **Ingest の 1 か所だけ**（スレッドの区切りと「返事や対応を求めているか」）。「綴じるために要る判断」（0012）で、プロンプトは固定、記録・再生の層を通す
- 境界越えの要約（v1 の `AiSummarizer`）、観測された送信の返事期待の推定（v1 の `ReplyEstimator`）、購読の自然文の条件の分類（0009）は外す。本文はスタンドが書き（0008）、返事期待はスタンドが送信の記録で明示し（0012）、振り分けは構造と持ち主で決まる（0013）

## データモデル

正は append-only のイベント列。スレッドと用件は投影で、いつでもイベントから作り直せる。

### 外部リストとマイリスト（0013）

| | 外部リスト | マイリスト |
| --- | --- | --- |
| 単位 | データソースごとに 1 つ（機械的に作る）。テナントで 1 つの共有の実体。人ごとのコピーは作らない | ユーザーごとに 1 つ（自動で作る） |
| メンバー | そのデータソースを読める人（取り込みの設定で決まる） | 本人 |
| 中身 | スレッド（シグナルの束）。ソース固有の粒度（メールのスレッド、Slack のスレッド、Jira の課題、LINE は Ingest の区切り） | 用件（人が追うもの。複数のスレッドを参照して 1 つにまとめる） |
| 持つもの | ボール（こちら / 特定のユーザー / 相手 / なし）、持ち主、アンカー（外の受け皿へのリンクを含む）、ソースの属性の写し、片付け | 状態（open / closed）、カスタム属性、メモ、導出したボール、参照するスレッド |

0009 の「外部リスト」（元のサービスのプロジェクトを用件の層のリストとしてつなぐ）とは別物。0013 以降は、データソースの写し全部を外部リストと呼ぶ。Jira のプロジェクトも粒度を元から持つデータソースとして外部リストになる。

### マスタ（イベントではない）

| エンティティ | 所有 | 要点 |
| --- | --- | --- |
| Tenant | — | 秘匿境界の単位 |
| User | グローバル | ゲートウェイの User と 1:1。各テナントに自分の Party を 1 つ持つ |
| Party | Tenant | 人物／組織。ゴースト = User を持たない Party。外部マスタ（bm-next など）へのポインタと属性 |
| Address | Tenant | チャネル種別 + 値。Party に紐づく |
| CredentialRef | Tenant | ゲートウェイ側の資格情報への参照 + 主体（User か Organization） |
| DataSource | Tenant | 資格情報 + 絞り込み（メールボックス、Slack のチャネル、LINE 公式アカウント、Jira のプロジェクト）。外部リスト 1 つに対応する。送信元のアドレスを持つ |
| List | Tenant | 種類（external / personal）。可視性の単位 |
| ListMember | List | Party の所属。外部リストは読者、マイリストは本人 |
| AttributeDef | List | マイリストのカスタム属性の定義。名前・型・AI が読める意味の記述 |

v1 の ChannelPolicy と 0009 の Subscription はなくなる。置き先はデータソースから機械的に決まり、誰のマイリストに入るかは構造と持ち主で決まる。
約束: 共有のデータソースは組織の資格情報で取り込む。個人の資格情報は読者 1 人のデータソースにしか使わない（0013）。

### イベント

外部リスト:

| 種別 | 誰が出す | 要点 |
| --- | --- | --- |
| SignalReceived | コネクタ | 外部からの受信。データソース、from / to、anchors（In-Reply-To・thread_ts・Jira キー・PR 番号・LINE の quotedMessageId）、body、attachments（参照のみ）、source_ref（データソースごとの重複排除キー） |
| SignalObservedSent | コネクタ | ツール外で行われた送信の観測 |
| SignalThreaded | Ingest・人 | シグナルをスレッドに入れる（既存 / 新規）。by（anchor / awaiting / ai / human）、confidence、reason、返事や対応を求めているか。人の訂正（シグナルの移し替え）も同じイベントで追記する |
| ThreadClaimed | 人・スタンド | 持ち主。ボールを特定のユーザーへ明示の操作で動かす。userId が null なら手放す（ボールは「こちら」= 組織に戻る）、別の人なら引き継ぐ。理由を残す |
| ThreadMirrored | コネクタ | 正が外にあるスレッド（Jira の課題など）の状態の写し（ステータス・担当者・優先度・期日・完了）。0010 の MatterMirrored の後継 |
| ThreadDismissed | 人・スタンド | 片付け。スレッドのボールを「なし」にし、理由を残す（v1 の IgnoreLog の後継） |

マイリスト:

| 種別 | 誰が出す | 要点 |
| --- | --- | --- |
| MatterCreated | つなぎ・人・スタンド | 用件を作る。マイリスト、件名、出どころ（ball / anchor / sent / manual） |
| ThreadLinked | つなぎ・人・スタンド | スレッドを用件につなぐ（null なら外す）。経路（sent / ball / anchor / manual）、操作した人 |
| MatterAttributeSet | 人・スタンド | カスタム属性の値の変更 |
| MatterClosed / MatterReopened | 人・スタンド・見回り | 閉じた用件は、参照するスレッドのボールが本人に来たときだけ自動で開き直す |
| MatterMerged | 人・スタンド | B を A に統合する（B のスレッドの参照を全部 A に付け替え、B は閉じる。属性は A を優先） |
| MatterNoted | 人・スタンド | 用件に宛てたメモ（自由記述）。電話や対面などデータソースのないチャネルの記録、判断の記録、スタンドとのやりとりの控え。Murmur は中身を解釈せず、タイムラインに並べるだけ（0012） |

送信の記録:

| 種別 | 誰が出す | 要点 |
| --- | --- | --- |
| OutboundRecorded | スタンド | スタンドがゲートウェイ経由で送った直後に記録する。用件、データソース、宛先 Party（か Address）、本文（必須）、sent_ref（メールの Message-ID・Slack の ts・LINE の `sentMessages[].id`・Jira の課題キーやコメント ID）、返事期待（省略可）。送ったシグナルが入るスレッドを作り（新規なら。用件につながった状態で、経路 sent）、ボールを相手へ移す。sent_ref はスレッドのアンカーになる |
| ReplyOverdue | Cron の見回り | 返事期待の期限超過。冪等 |

### 投影

- スレッド（外部リスト）: データソース、相手の Party、anchors（外の受け皿のキーを含む）、シグナルの列、ボール（こちら / 特定のユーザー / 相手の Party / なし）、持ち主、属性の写し、
  last_inbound_at、last_outbound_at、reply_expected_by、overdue、片付け済みか。**どのマイリストに参照されているかは持たない**（逆の依存を作らない）
- 用件（マイリスト）: マイリスト、件名、open / closed、カスタム属性、参照するスレッド、導出したボール（参照するスレッドのどれかが本人 → 自分の番 / 全部が相手待ち → 返事待ち、期限は最も早いもの / なし）、統合先、メモ
- 仕分け待ち: ボールが「こちら」（組織）で持ち主がなく、片付けていないスレッド（データソースごと。外部リストの読者に見える）。
  用件に結びつかなかった観測された送信のスレッドも、送った本人の仕分け待ちに出る
- 「自分に関連する」ビュー: 外部リストの投影に対するクエリ層の純関数。宛先・CC・@メンション・Jira の担当者と報告者・スレッドの参加者・読者が 1 人のソース・持ち主
- 記録した送信、タイムライン（用件ごとに、参照するスレッドのシグナルと用件のイベント・メモを並べる。`since` で前回見てからの差分に絞れる）。タイムラインは投影として持たず、クエリ層で 2 つの投影を合わせて作る

### ルール

- 可視性はクエリ層が Viewer（User → そのテナントの Party → リスト所属）から強制する。外部リストのメンバーには、そのデータソースのスレッドの生の中身が見える。マイリストは本人だけ。
  持ち主と外の受け皿へのリンクはスレッドの側にあるので、外部リストの読者に見える。テナント外は 0 件、ゴーストは何も取れない
- 1 本のスレッドを参照する用件は、1 人のマイリストの中では多くても 1 つ。別の人の用件が同じスレッドを参照するのはよい（同じ連絡を別の仕事として追う）。
  1 通に 2 つの話がある連絡は、シグナルの移し替えでスレッドを分ける
- 通信状態は事前定義属性と持ち主だけから機械的に導出する。作業状態は全部用件のカスタム属性。正が外にあるスレッドの状態は写しで、Murmur の側では書き換えない
- 本体は外に何も書かない。送信・起票・コメントはスタンドが行い、事実だけが記録として入る（0012）
- **fold の依存は一方向**。外部リストの fold は外部リストのイベントだけ読む。マイリストの fold は、自分のイベントと外部リストの投影（ボール・reply_expected_by・overdue・last_*_at・anchors）を読む。逆はない（0013）
- 畳み込み（fold）は IO を持たない純関数

## Ingest（外部リスト）

判断はスレッドの区切りと「返事や対応を求めているか」だけ。業務の知識を使わないので、プロンプトは固定。

1. 受信: コネクタが SignalReceived か SignalObservedSent を append する。source_ref が既出なら弾く。observed-sent が記録した送信の sent_ref と一致すれば統合する。
   観測が記録より先に届いたときは受信と同じくスレッドに入れ（ボールは相手、返事期待なし）、後から記録が来たら統合する（H5）
2. スレッドの区切り（上から順に）
   1. アンカーで決まれば、そのスレッド
   2. 同じ相手（グループのチャネルならそのチャネル）で、こちらが返事を待っているスレッドが 1 本だけなら、そのスレッド
   3. 発信者の直近のスレッド（グループのチャネルならチャネルの直近のスレッド）から、話題の続きかを AI が判断する。「直近」の範囲は設定値
   4. どれにも当たらなければ新しいスレッド
3. 返事や対応を求めているか: アンカーで決まったシグナルも含めて AI が判断する（発話の種類の判断。スタンプ・お礼・成功通知は求めていない）。
   観測された送信にはこの判断をしない。ボールは相手へ移り、返事期待は記録がなければなし
4. 記録: SignalThreaded を append する
5. 新しいスレッド（区切りの訂正で出たものも含む）はマイリストへのつなぎに回す

区切りの基準は時間ではなく話題。同じ相手のスレッドが並行して開いていてよい。v1 の ignore はなくなり、誰のマイリストにも入らないものがそれにあたる。

**記録・再生**: AI の入出力を `fixtures/<scenario>/recordings/` に保存し、テストでは再生する。モデルを変えたら取り直して差分を見る。
入出力は型（zod）で決め、Claude 以外の判断専用のモデル（Jev など）も同じ層で比べられるようにする（チューニングの段階）。

## マイリストへのつなぎ（0013。0009 の昇格の後継）

スレッドを用件につなぐ。上から順に当てる。購読はない。

1. 用件から送ってできたスレッドは、最初からその用件につながっている（経路 sent）
2. ボールが特定のユーザーに来た（個人のメールボックス・DM なら本人、@メンションなら言及された人、Jira なら担当者、読者が 1 人のデータソースならその人、ThreadClaimed で持った人）
   → その人のマイリストに用件を作る（経路 ball）。誰も見ていない夜中に届いたメールも、朝には用件になっている（0012）
3. アンカーの相互参照（Jira キー・PR 番号・チケット番号・sent_ref）で、その人の既存の用件が見つかった → つなぐ（経路 anchor）
4. どれでもない → データソースの仕分け待ち（ボールは「こちら」= 組織、持ち主なし）。外部リストの読者かスタンドが持つか、片付ける

**持ち主の操作**（ThreadClaimed）: 持つ・手放す・引き継ぐ。LINE 公式アカウントのように「誰宛」のないソースで、誰のボールかを決める唯一の操作。
「これを自分で持つ」というスタンドの操作は、シェルが ThreadClaimed の追記と用件の作成を並べて呼ぶ。コアの中では別の層の操作で、持つだけ・用件にするだけ、もできる。
起票の前にスタンドが共有のスレッドを見れば、もう誰かが持っていて外の受け皿へのリンクも付いていると分かるので、同じチケットは増えにくい。

**直す操作**（どれも追記で、元の判断は消さない。スタンドがユーザーの指示で明示的に呼ぶものに、Murmur 側で承認は求めない）

| 誤り | 操作 |
| --- | --- |
| シグナルを違うスレッドに入れた | シグナルを別のスレッドへ移す（新しいスレッドも可） |
| スレッドを違う用件につないだ | スレッドを別の用件へ付け替える（新しい用件、外す、も可） |
| 同じ件で用件が 2 つできた | 用件の統合 |
| 対応の要らないものが仕分け待ちに残る | 片付け |

操作できるのは、スレッドが見えている人。用件の分割は、新しい用件を作ってスレッドの参照を付け替える。

## 送信の記録と観測

外への送信（メッセージ・起票・コメント）は、スタンドがユーザーの確認を取り、ゲートウェイ経由で実行する。本体は外に何も書かない（0012）。
外へのゲートは本体ではなく、スタンドとの会話とゲートウェイの資格情報の権限。本体に承認を要するものは残らない（0013）。

- **送信の記録**: スタンドは送った直後に `record_sent` で記録する（用件、データソース、宛先、本文、sent_ref、返事期待）。本体は OutboundRecorded を綴じ、
  送ったシグナルの入るスレッドを用件につながった状態で作り、ボールを相手へ移す。送信元はデータソースのアドレスなので、返事は同じデータソースに戻り、送ったスレッドに入る。
  返事期待の期限を過ぎたら Cron の見回りが ReplyOverdue を出す。遅れて返事が来れば解消する
- **同僚への受け渡し**: 0009 の派生はない。同僚に渡すのも外のチャネル（メール・Slack・Jira）で送って記録する。相手のメールボックスや担当にボールが来て、相手のマイリストに用件ができる。
  2 人の用件は sent_ref のアンカーで同じスレッドを参照する
- **起票**: 外の受け皿への起票も送信。sent_ref（課題キー）がスレッドのアンカーになり、LINE のスレッドと課題のスレッドが同じ用件に結ばれる。リンクを作るのは起票した人で、起票の副作用として付く
- **ボール**: 送信の記録でスレッドのボールは相手へ、返事でこちらへ戻る。持ち主の操作で特定のユーザーへ
- **観測された送信**: ツール外の送信は SignalObservedSent として入る。記録した送信の sent_ref と一致すれば、どちらが先に届いても 1 本に統合する。
  一致しなければ受信と同じくスレッドに入れ、ボールは相手へ、返事期待はなし。用件に結びつかなければ送った本人の仕分け待ちに出る。管理したい用件はスタンド経由で送るのが運用の約束
- **前提の指標**: 「外には書かない」と「チームの共有は外の受け皿で」が成り立っているかを、用件に結びつかなかった観測された送信の件数、外の受け皿へのリンクのない課題の件数、
  誰も持たないまま古くなったスレッドの件数で見る（0007 の試用でも）。多すぎれば、まずスキルで「送ったら記録する」「共有するなら起票する」を徹底し、
  それでも足りなければゲートウェイが送信を本体に通知する形（0006 の延長）に寄せる

## 正が外にある用件（0010・0013）

- Jira のプロジェクトは、データソース 1 つ（外部リスト）としてつなぐ。1 課題 = 1 スレッドで、コメントがシグナル、課題の状態は ThreadMirrored でスレッドの属性に写す
- 状態は Jira から Murmur への片方向。変えるときは Jira の画面か、スタンドがゲートウェイ経由で直接操作する
- 会話（コメント）は両方向。Murmur を使わない人のコメントは受信、Murmur のユーザーが直接書いたものは観測された送信、スタンド経由は記録した送信（H5 で重複排除）
- 担当者が Murmur のユーザーなら、その人のマイリストに用件ができる（つなぎの 2）。Slack のスレッドや PR は Jira キーのアンカーで同じ用件に結ばれる（つなぎの 3）
- 起票: スタンドが Jira に起票し、OutboundRecorded で記録する。課題キーが元のスレッド（LINE など）のアンカーになり、課題のスレッドと同じ用件に結ばれる。起票ルール（0010）は本体に持たない（0012）
- コメントの編集・削除は扱わない（0007 の試用で頻度を見てから決める）

## スタンド接続（本体の API）

スタンドはゲートウェイの MCP から呼ぶ。使い方はゲートウェイのスキル（nvt-api-gateway-skills の `murmur`）で渡す。HTTP API を変えたらスキルの表も直す。

| ツール | 返すもの・起こすこと |
| --- | --- |
| me | User と各テナントの Party |
| list_lists / get_list | 見えるリストの一覧。外部リストのメンバー・データソース、マイリストの属性定義 |
| list_my_matters | 自分の用件。filter（open / ball_at_me / overdue / all）、tenant |
| get_matter | 用件、参照するスレッド、タイムライン（メモを含む）、属性定義と意味記述。`since` で前回見てからの差分に絞れる |
| list_related | 自分に関連するスレッド（宛先・メンション・担当・読者が 1 人のソース・持ち主）。用件になっていないものを含む |
| list_triage / get_thread | 仕分け待ちのスレッド（データソースごと）、スレッドの生のシグナルと持ち主・リンク |
| claim_thread | ThreadClaimed。持つ・手放す（null）・引き継ぐ。用件を作るかは別の引数 |

## コネクタ

コネクタは取り込みだけを持つ。「どのデータソースとして取得したか」を必ず持つ。送信はスタンドがゲートウェイ経由で行い、コネクタを通らない（0012）。

```typescript
interface Connector {
  channel: 'email' | 'slack' | 'line' | 'jira' | 'bitbucket';
  // Cron から呼ばれる。データソースの資格情報で cursor 以降を取る
  pull(source: DataSource, cursor: Cursor | null): Promise<{ signals: InboundSignal[]; mirrors: ThreadMirror[]; cursor: Cursor }>;
}
// Webhook（LINE / Slack Events）は Worker の fetch で受け、同じ InboundSignal に正規化する
```

- ダミー実装: pull はフィクスチャのキューから返す。シナリオの action 行で `record_sent` を呼ぶと、ダミーはその sent_ref の observed-sent を次の pull で返す（H5）。
  観測を記録より先に返す順もシナリオで作れるようにする
- ダミーの Jira: 課題の状態の写し（ThreadMirror）とコメントを返す。スタンドの起票・コメントは `record_sent` で入り、ダミーは対応する通知を観測として返す
- 本番の実装はゲートウェイ経由。インタフェースを変えずに差し替える。実データでの試用（0007）も読み取りだけで、本体に書き込みの資格情報は要らない
