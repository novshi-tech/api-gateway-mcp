# Murmur プロトタイプ計画 v2 — スレッドとリンク

2026-10-20 · @Naoki NOSE · 設計の正本（`docs/adr/0011`）。立ち位置は `docs/adr/0012`、データモデルは `docs/adr/0013` を `docs/adr/0014` で 1 種類のスレッドに統合した形（2026-10-20）。v1 の計画はタグ `proto-v1` の `docs/PLAN.md`

## 目的と前提

このプロトタイプは、Murmur のデータモデルとアーキテクチャが成立するかを、外部接続なしで確かめるためのもの。製品の MVP ではない。

v1（`proto-v1`）で、イベントソーシングの土台（決定的な畳み込み、FC-IS、記録・再生、ゲートウェイ経由の認証、実環境へのデプロイ）は確かめた。H7 を実環境で回したところで、リストの構成に根本の問題が見つかった（`docs/adr/0009` の背景）。v2 は 0008〜0010・0012〜0014 の形にデータモデルを組み替え、もう一度確かめる。

- 検証対象: スレッド 1 種類のデータモデル（データソースの写しと個人のメモを同じ形で扱う。0013 を 0014 で統合した形）、業務の知識を持たない Ingest、持ち主の操作と構造だけで決まる結び候補、本人とスタンドが張るリンク、送信の記録、状態の写しを持つデータソース（Jira）、スタンドへのハンドオフ、Murmur の有無でスタンドの一手が変わるか
- 外部接続は全部ダミー。Claude API と、ゲートウェイ経由のスタンド接続は本物。実データでの試用（0007）は並行トラック
- UI は作らない。人が触るのはスタンド（Cowork / Claude Code）。管理用に参照専用の画面だけ作る（0010）
- 技術要素は v1 と同じ: Cloudflare Workers + Neon（Postgres）+ 既存の API ゲートウェイ

## 方向（0010・0012・0013・0014）

Murmur は、連絡から対応の要る件を拾い、その経過を追跡する（0012）。エンティティは**スレッド**の 1 種類だけ。スレッドはデータソースの写しで、データソースごとに 1 つの**リスト**（テナントで 1 つの共有の実体。人ごとのコピーは作らず、見えるのはそのデータソースを読める人）に入る。データソースには外のサービス（メールボックス、Slack のチャネルや DM、LINE 公式アカウント、Jira のプロジェクト）のほかに、**個人のメモ**（読者が本人 1 人のデータソース。シグナルは本人が書く）がある。0013 の「マイリスト」「用件」は、個人のメモのデータソースのスレッドにすぎないので、別のエンティティとしては持たない（2026-10-20 のレビューで統合。`docs/adr/0014`）。綴じるのは、連絡（観測）、人とエージェントの行動（送った・持った・片付けた・結んだ）、本人のメモの 3 種類。Murmur が判断するのは「どのスレッドに綴じるか」と「ボールが動いたか」だけで、何をするかは判断しないし、何も実行しない。**外には何も書かない**。外への送信（メッセージ・起票・コメント）はスタンドがゲートウェイ経由で行い、本体にはその事実を記録する。前例は boid の card と signal inbox と identity 索引（0012「boid からの系譜」）。

Murmur は黒子（0010）。スレッドはどれもデータソースの写しで、正は常にデータソースの側にある。データソースが状態を持つ（Jira の課題のステータス・担当・期日）ならその写しをスレッドの属性に持ち、持たない（LINE の会話、メール）なら写しがないだけで、違いは変換の程度にすぎない。個人のメモのスレッドも同じで、正は本人のメモ。Murmur はどの側の状態も自分では書き換えない。**チームの共有は既存のツール（Jira・グループメール・Slack）に任せ、Murmur はチームリストを持たない**（0013）。LINE の件をチームで追いたければ、スタンド経由で Jira などに起票して記録し、スレッド同士をリンクで結ぶ。軽く運用したければ、持ち主だけ追ってリンクは張らなくてよい。Murmur の価値は、構造のない連絡を拾ってスレッドにすること（抽出）、チャネルをまたいで誰が誰に返事を待っているか（ボール）を追うこと（追跡）、要約レベルの違い（LINE の生の会話と Jira の課題と本人のメモ）とツールの垣根を越えて同じ件のスレッドを結び、どこからも辿れるようにすること（索引）。

業務の知識（何をどこへ渡すか、どの連絡を誰が扱うか）は Murmur のコードにもプロンプトにもデータにも持たない（0008）。誰が持つかは人とスタンドの操作（持ち主）と構造（宛先・メンション・担当者・読者が 1 人のソース）で決まり、どのスレッドを 1 つの件として結ぶかは本人とスタンドが決め（Murmur はアンカーの一致を候補として見せるだけ）、何をするか・外へ何を書くかはスタンドが判断して実行する（0012・0013）。個人のメモの側（開く・閉じる・属性・メモ）を Murmur は自動で変えない。結んだ先のスレッドが動いたという事実を返すだけで、閉じた件を開き直すかはスタンドが判断する。

| H3 | 境界が守られる | リストの読者には、そのデータソースのスレッドだけが見える。個人のメモのスレッドは本人だけ。持ち主は、そのスレッドが見える人に見える。他のスレッドへのリンクは、両端のスレッドを読める人にだけ見える（`docs/adr/0033`）。テナント外は 0 件、ゴースト Party は何も取れない |

| H5 | 観測と送信の記録を重複排除できる | スタンドが記録した送信と、同じメッセージの observed-sent が、どちらの順で届いても sent\_ref で 1 本に統合され、状態が二重に変わらない（Jira のコメントでも） |
| H6 | Ingest が運用に耐える | 固定のプロンプトで、スレッドの区切りと「返事や対応を求めているか」の正解ラベルとの一致率が、アンカー込みで 90%、AI 判断のみで 80% を超える |
| H7 | スタンドに必要十分な情報が渡る | 実環境で、欠勤連絡とクレームのシナリオをスタンド主導で完走できる。人の操作はユーザーが Claude に出す指示と承認だけ |
| H8 | 構造と持ち主だけで「自分の番」が決まる | 自然文の条件なしに、構造（宛先・メンション・担当者・読者が 1 人のソース）と持ち主の操作だけで、4 シナリオの各人の「自分の番」のスレッド一覧が期待どおりになり、アンカーの一致が結び候補として正しく出る |
| H9 | 状態の写しを持つデータソースを黒子として扱える | ダミーの Jira で、プロジェクトをデータソース（1 課題 1 スレッド）としてつなぎ、状態は片方向の写し（スレッドの属性）で足り、コメントは両方向に重複なく流れ、スタンドが起票して記録すると LINE のスレッドと課題のスレッドがリンクで結ばれる |
| H10 | Murmur があるほうがスタンドは良い一手を出せる | 同じ absence を、Murmur なし（LINE・Gmail の MCP だけ渡したスタンド）とありで回し、完走できたか・ユーザーへの確認の回数・ツール呼び出しの回数・取り違えの件数・セッションが切れた後に続きから入れるかを比べ、ありが上回る。モデルを変えたら回し直す |

## アーキテクチャ

v1 と同じ（`docs/adr/0001`・`0003`）。本体 Worker 1 本、Neon、既存の API ゲートウェイの 3 つ。本体は上流サービスのトークンを持たず、外からの取り込みはゲートウェイ経由。外へは何も書かない（0012）。

- 本体 Worker: fetch（HTTP API・Webhook・管理用の画面）と scheduled（Cron: 取り込みのポーリングと期限の見回り）
- 判断はすべて純関数のコア（`src/domain/`）に置き、副作用はシェルに集める（FC-IS）
- スタンドはゲートウェイの MCP から本体の HTTP API を呼ぶ（認可の接続の形 (B)）。本体はゲートウェイが署名した sub を検証する
- Claude API（claude-sonnet-5-5、構造化出力）を使うのは **Ingest の 1 か所だけ**（スレッドの区切りと「返事や対応を求めているか」）。「綴じるために要る判断」（0012）で、プロンプトは固定、記録・再生の層を通す
- 境界越えの要約（v1 の `AiSummarizer`）、観測された送信の返事期待の推定（v1 の `ReplyEstimator`）、購読の自然文の条件の分類（0009）は外す。本文はスタンドが書き（0008）、返事期待はスタンドが送信の記録で明示し（0012）、どのスレッドを結ぶかは本人とスタンドが決め、Murmur は構造と持ち主で「自分の番」と結び候補を出すだけ（0013）

## データモデル

正は append-only のイベント列。スレッドは投影で、いつでもイベントから作り直せる。エンティティはスレッドの 1 種類。

### スレッドとデータソース（0014）

|  | 外のサービスのデータソース | 個人のメモのデータソース |
| --- | --- | --- |
| 例 | メールボックス（組織・個人）、Slack のチャネル・DM、LINE 公式アカウント、Jira のプロジェクト | ユーザーごとに 1 つ（自動で作る） |
| 読者 | そのデータソースを読める人（取り込みの設定で決まる）。1 人のこともある | 本人 |
| シグナル | 受信・観測された送信・記録した送信（コネクタとスタンドが入れる） | メモ（本人・スタンドが書く。電話・対面・判断の記録） |
| スレッドの区切り | ソース固有の粒度（メールのスレッド、Slack のスレッド、Jira の課題、LINE は Ingest の区切り） | 本人が「この件」として作る |
| 属性 | ソースの写し（Jira のステータス・担当・期日など。Murmur は書き換えない） | 本人が付ける（定義はデータソースに付く） |
| open / closed | ソースが持てばその写し、持たなければ片付けの有無 | 本人・スタンドが付ける。自動では変えない |
| ボール | シグナルの向きと持ち主から導出 | リンク先のスレッドのボールから導出（クエリ層） |

リストはデータソースごとに 1 つ（機械的に作る）。テナントで 1 つの共有の実体で、人ごとのコピーは作らない。可視性の単位。0013 の「外部リスト」「マイリスト」の区別はなくなり、どちらもデータソースのリスト。「用件」は個人のメモのスレッドで、他のスレッドへのリンクで 1 つの件を束ねる。0009 の「外部リスト」（元のサービスのプロジェクトを用件の層のリストとしてつなぐ）とも別物。

| Party | Tenant | 人物／組織。ゴースト = User を持たない Party。外部マスタ（bm-next など）へのポインタと属性 |
| Address | Tenant | チャネル種別 + 値。Party に紐づく |
| CredentialRef | Tenant | ゲートウェイ側の資格情報への参照 + 主体（User か Organization） |
| DataSource | Tenant | 資格情報 + 絞り込み（組織や個人のメールボックス、Slack のチャネルや DM、LINE 公式アカウント、Jira のプロジェクト）、または個人のメモ（ユーザーごとに 1 つ）。リスト 1 つに対応する。外のサービスのものは送信元のアドレスを持つ |

### イベント

スレッド（どのデータソースでも同じ 1 組）:

| 種別 | 誰が出す | 要点 |
| --- | --- | --- |
| SignalObserved | コネクタ・人・スタンド | データソースで観測されたシグナル。受信も、ツール外で行われた送信（相手への返信をメーラーから直接送ったなど）も同じ種別で、direction（inbound / outbound）で区別する。direction は from がデータソースの送信元（こちら）かどうかでコネクタが機械的に決める。データソース、from / to、anchors（In-Reply-To・thread\_ts・Jira キー・PR 番号・LINE の quotedMessageId）、body、attachments（参照のみ）、source\_ref（データソースごとの重複排除キー）。個人のメモのシグナル（電話や対面の記録、判断の記録、スタンドとのやりとりの控え）も同じ種別で、データソースが個人のメモ、from が本人。Murmur は中身を解釈せず、タイムラインに並べるだけ（0012。v2 当初の SignalReceived・SignalObservedSent・MatterNoted を 1 つにしたもの） |
| SignalThreaded | Ingest・人 | シグナルをスレッドに入れる（既存 / 新規）。by（anchor / awaiting / no\_match（どの規則にも当たらず候補もない） / ai / human / self）、confidence、reason、返事や対応を求めているか。人の訂正（シグナルの移し替え）も同じイベントで追記する。個人のメモは本人が置き先を指定する（by: self。新規なら「この件」のスレッドができる） |
| ThreadClaimed | 人・スタンド | 持ち主。ボールを特定のユーザーへ明示の操作で動かす。userId が null なら手放す（ボールは「こちら」= 組織に戻る）、別の人なら引き継ぐ。理由を残す |
| ThreadMirrored | コネクタ | 状態を持つデータソース（Jira の課題・PR）の状態の写し。Murmur が決めた形（`closed / holders / title / statusLabel / due`）で、件名のある写しはスレッドも作る。0010 の MatterMirrored の後継（0031） |
| ThreadAttributeSet | 人・スタンド | 本人が付ける属性の値の変更（個人のメモのスレッドだけ。定義は AttributeDef）。写しは ThreadMirrored で、こちらでは触らない |
| ThreadLinked | 人・スタンド | スレッド A と B を結ぶ（unlink で外す）。リンクは無向で、1 つのイベントが両方のスレッドの投影に載る（A から見ても B から見ても同じ辺）。経路の sent には「元 → 送った」の由来があるが、それは経路の属性で、辺の向きではない。追記で、元の判断は消さない。経路（sent / anchor / manual）、操作した人、理由。起票や送信の副作用として付くものも同じ種別。v2 当初の ThreadLinked（スレッドを用件につなぐ）の後継で、両端ともスレッド |
| ThreadDismissed / ThreadReopened | 人・スタンド | 片付けと開き直し。スレッドのボールを「なし」にし、理由を残す（v1 の IgnoreLog の後継）。状態を持たないデータソースの open / closed はこれで表す。個人のメモのスレッドも同じで、閉じた件に結ばれた先が動いても Murmur は自動で開き直さない（スタンドが判断する） |

送信の記録:

| 種別 | 誰が出す | 要点 |
| --- | --- | --- |
| OutboundRecorded | スタンド | スタンドがゲートウェイ経由で送った直後に記録する。送る元になったスレッド（省略可。個人のメモのスレッドか、返事をしている相手のスレッド）、データソース、宛先 Party（か Address）、本文（必須）、sent\_ref（メールの Message-ID・Slack の ts・LINE の `sentMessages[].id`・Jira の課題キーやコメント ID）、返事期待（省略可）。送ったシグナルが入るスレッドを作り（新規なら）、元のスレッドがあれば ThreadLinked（経路 sent）で結び、ボールを相手へ移す。sent\_ref はスレッドのアンカーになる |
| ReplyOverdue | Cron の見回り | 返事期待の期限超過。冪等 |

### 投影

- スレッド（1 種類）: データソース、相手の Party、anchors（外のサービスのキーを含む）、シグナルの列、ボール（こちら / 特定のユーザー / 相手の Party / なし）、持ち主、属性（写し + 本人が付けたもの）、リンク（結んだスレッドの id と経路）、last\_inbound\_at、last\_outbound\_at、reply\_expected\_by、overdue、片付け済みか。個人のメモのスレッドも同じ形で、シグナルがメモ、相手がなし
- 導出したボール（クエリ層）: リンク先のどれかが本人の番 → 自分の番 / 全部が相手待ち → 返事待ち、期限は最も早いもの / なし。主に個人のメモのスレッドから見るが、どのスレッドからでも同じ計算
- 仕分け待ち: ボールが「こちら」（組織）で持ち主がなく、片付けていないスレッド（データソースごと。そのリストの読者に見える）。どこにも結ばれなかった観測された送信のスレッドも、送った本人の仕分け待ちに出る
- 「自分の番」ビュー: スレッドの投影に対するクエリ層の純関数。宛先・CC・@メンション・Jira の担当者と報告者・スレッドの参加者・読者が 1 人のソース・持ち主。ボールが自分にあるスレッドと、結び候補（アンカーが自分の見えるスレッドと一致するが、まだ結ばれていないもの）を返す
- 記録した送信、タイムライン（スレッドごとに、そのシグナルと、リンク先のスレッドのシグナルと、両者のイベントを並べる。`since` で前回見てからの差分に絞れる）。タイムラインは投影として持たず、クエリ層で合わせて作る

### ルール

- 可視性はクエリ層が Viewer（User → そのテナントの Party → リスト所属）から強制する。リストの読者には、そのデータソースのスレッドの生の中身が見える。個人のメモのスレッドは本人だけ。持ち主とリンク（結び先の id）はスレッドの側にあるので、そのスレッドが見える人に見えるが、結び先の中身はその先の可視性に従う。テナント外は 0 件、ゴーストは何も取れない
- 個人のメールボックスや DM も読者が本人だけのデータソース。同じ DM や社内メール（A → B）を 2 人がそれぞれつなぐと、読者ごとに別のデータソース・別のスレッドになる。両者の結びは sent\_ref などのアンカーの候補をスタンドが見て張る。データソースをまたぐ重複排除はしない
- 1 通に 2 つの話がある連絡は、シグナルの移し替えでスレッドを分ける。同じスレッドを 2 人がそれぞれ自分のメモのスレッドに結ぶのはよい（同じ連絡を別の仕事として追う）
- 通信状態（ボール・期限）は事前定義属性と持ち主だけから機械的に導出する。作業状態は、ソースの写し（Murmur は書き換えない）か、本人が付ける属性と片付け。本人の側の状態を Murmur が自動で変えることはない
- 本体は外に何も書かない。送信・起票・コメントはスタンドが行い、事実だけが記録として入る（0012）
- **結ぶのは人とスタンド**。Murmur はアンカーの一致を結び候補として見せるだけで、自分ではリンクを張らない（送信・起票の副作用として付く sent 経路だけが例外で、これはスタンドの操作の一部）。アンカーをついでに書いただけの連絡で別の件が溶けないようにするため
- **fold は 1 段**。スレッドの fold は、そのスレッドのイベントとリンクのイベントだけ読む。リンク先の状態は fold に持ち込まず、クエリ層で合わせる
- 畳み込み（fold）は IO を持たない純関数

## Ingest（外部リスト）

判断はスレッドの区切りと「返事や対応を求めているか」だけ。業務の知識を使わないので、プロンプトは固定。

1. 受信: コネクタが SignalObserved を append する（direction は inbound / outbound）。source\_ref が既出なら弾く。outbound のシグナルが記録した送信の sent\_ref と一致すれば統合する。観測が記録より先に届いたときは受信と同じくスレッドに入れ（ボールは相手、返事期待なし）、後から記録が来たら統合する（H5）
2. スレッドの区切り（上から順に）
   1. アンカーで決まれば、そのスレッド（同じデータソースの中だけ。ソースが元から持つ区切り（Jira の課題キー・PR）は、一致しなければ新しいスレッドに決まる）
   2. 同じ相手（グループのチャネルならそのチャネル）で、こちらが返事を待っているスレッドが 1 本だけなら、そのスレッド
   3. 発信者の直近のスレッド（グループのチャネルならチャネルの直近のスレッド）から、話題の続きかを AI が判断する。「直近」の範囲は設定値
   4. どれにも当たらなければ新しいスレッド
3. 返事や対応を求めているか: アンカーで決まったシグナルも含めて AI が判断する（発話の種類の判断。スタンプ・お礼・成功通知・知らせだけの連絡（遅刻の連絡など）は求めていない）。AI の答えをそのまま使い、confidence の閾値で倒さない（シンプルで予測しやすい挙動を優先。2026-10-21）。勤怠を要対応とするような業務の知識による上書きは、将来の振り分けルールのカスタマイズの話で、デフォルトには入れない（0008）。観測された送信にはこの判断をしない。ボールは相手へ移り、返事期待は記録がなければなし
4. 記録: SignalThreaded を append する
5. 新しいスレッド（区切りの訂正で出たものも含む）は、構造から「誰の番か」を決め、アンカーから結び候補を計算する（次節）

区切りの基準は時間ではなく話題。同じ相手のスレッドが並行して開いていてよい。v1 の ignore は片付け（ThreadDismissed）になる。

**記録・再生**: AI の入出力を `fixtures/<scenario>/recordings/` に保存し、テストでは再生する。モデルを変えたら取り直して差分を見る。入出力は型（zod）で決め、Claude 以外の判断専用のモデル（Jev など）も同じ層で比べられるようにする（チューニングの段階）。

## 誰の番かと、結び（0014。0013 のつなぎの後継）

Murmur が決めるのは「誰の番か」（ボール）まで。スレッド同士を 1 つの件として結ぶのは本人とスタンド。購読はなく、用件の自動作成もない。

1. **誰の番か（Murmur）**: 構造で決まる。個人のメールボックス・DM なら本人、@メンションなら言及された人、Jira なら担当者、読者が 1 人のデータソースならその人、ThreadClaimed で持った人。どれでもなければ「こちら」= 組織で、データソースの仕分け待ちに出る（持ち主なし）。誰も見ていない夜中に届いたメールも、朝には本人の「自分の番」に出ている（0012）
2. **結び候補（Murmur）**: アンカーの相互参照（Jira キー・PR 番号・チケット番号・sent\_ref）で、本人の見えるスレッドと一致するものを候補として出す。張らない
3. **結ぶ（本人・スタンド）**: スタンドが候補と文脈を見て ThreadLinked を張る。件として追いたければ、個人のメモのデータソースに「この件」のスレッドを作り（最初のメモが SignalObserved）、関係するスレッドを結ぶ。LINE の 1 本だけで済むなら、メモのスレッドを作らず持ち主だけ追ってもよい
4. **送信・起票の副作用（スタンド）**: メモのスレッドなどから送った・起票したスレッドは、record\_sent の中で元のスレッドと結ばれる（経路 sent）

**持ち主の操作**（ThreadClaimed）: 持つ・手放す・引き継ぐ。LINE 公式アカウントのように「誰宛」のないソースで、誰のボールかを決める唯一の操作。「これを自分で持つ」はボールを動かすだけで、メモのスレッドを作るかは別の操作（スタンドが続けて呼ぶ）。起票の前にスタンドが共有のスレッドを見れば、もう誰かが持っていて Jira へのリンクも付いていると分かるので、同じチケットは増えにくい。

**直す操作**（どれも追記で、元の判断は消さない。スタンドがユーザーの指示で明示的に呼ぶものに、Murmur 側で承認は求めない）

| 誤り | 操作 |
| --- | --- |
| シグナルを違うスレッドに入れた | シグナルを別のスレッドへ移す（新しいスレッドも可） |
| 違うスレッドと結んだ | リンクを外す（ThreadLinked の unlink）。結び直すのは外して張る |
| 同じ件でメモのスレッドが 2 つできた | 一方のメモのシグナルとリンクをもう一方へ移し、空いたほうを片付ける（統合の専用イベントはない） |
| 対応の要らないものが仕分け待ちに残る | 片付け |

操作できるのは、スレッドが見えている人。件の分割は、新しいメモのスレッドを作ってリンクを張り直す。

## 送信の記録と観測

外への送信（メッセージ・起票・コメント）は、スタンドがユーザーの確認を取り、ゲートウェイ経由で実行する。本体は外に何も書かない（0012）。外へのゲートは本体ではなく、スタンドとの会話とゲートウェイの資格情報の権限。本体に承認を要するものは残らない（0013）。

- **送信の記録**: スタンドは送った直後に `record_sent` で記録する（元のスレッド、データソース、宛先、本文、sent\_ref、返事期待）。本体は OutboundRecorded を綴じ、送ったシグナルの入るスレッドを作って元のスレッドと結び、ボールを相手へ移す。送信元はデータソースのアドレスなので、返事は同じデータソースに戻り、送ったスレッドに入る。返事期待の期限を過ぎたら Cron の見回りが ReplyOverdue を出す。遅れて返事が来れば解消する
- **同僚への受け渡し**: 0009 の派生はない。同僚に渡すのも外のチャネル（メール・Slack・Jira）で送って記録する。相手のメールボックスや担当にボールが来て、相手の「自分の番」に出る。相手が自分のメモのスレッドを作って結ぶかは相手の判断。送ったスレッドは 1 本なので、2 人は同じスレッドを別々に結んでいることになる
- **起票**: 外の受け皿への起票も送信。sent\_ref（課題キー）がスレッドのアンカーになり、LINE のスレッドと課題のスレッドが ThreadLinked で結ばれる。リンクを作るのは起票した人で、起票の副作用として付く
- **ボール**: 送信の記録でスレッドのボールは相手へ、返事でこちらへ戻る。持ち主の操作で特定のユーザーへ
- **観測された送信**: ツール外の送信は direction が outbound の SignalObserved として入る。記録した送信の sent\_ref と一致すれば、どちらが先に届いても 1 本に統合する。一致しなければ受信と同じくスレッドに入れ、ボールは相手へ、返事期待はなし。どのスレッドにも結ばれなければ送った本人の仕分け待ちに出る。追いたい件はスタンド経由で送るのが運用の約束
- **前提の指標**: 「外には書かない」と「チームの共有は外のツールで」が成り立っているかを、どこにも結ばれなかった観測された送信の件数、元のスレッドへのリンクのない Jira 課題の件数、誰も持たないまま古くなったスレッドの件数で見る（0007 の試用でも）。多すぎれば、まずスキルで「送ったら記録する」「共有するなら起票する」を徹底し、それでも足りなければゲートウェイが送信を本体に通知する形（0006 の延長）に寄せる

## 状態の写しを持つデータソース（Jira。0010・0013）

- Jira のプロジェクトは、データソース 1 つとしてつなぐ。1 課題 = 1 スレッドで、コメントがシグナル、課題の状態は ThreadMirrored でスレッドに写す（0031）。LINE やメールとの違いは、区切りと状態を元から持っていることだけ
- 状態は Jira から Murmur への片方向。変えるときは Jira の画面か、スタンドがゲートウェイ経由で直接操作する
- 会話（コメント）は両方向。Murmur を使わない人のコメントは受信、Murmur のユーザーが直接書いたものは観測された送信、スタンド経由は記録した送信（H5 で重複排除）
- 担当者が Murmur のユーザーなら、その人の「自分の番」に出る。Slack のスレッドや PR は Jira キーのアンカーで結び候補になり、スタンドが結ぶ
- 起票: スタンドが Jira に起票し、OutboundRecorded で記録する。課題キーが元のスレッド（LINE など）のアンカーになり、課題のスレッドと元のスレッドが結ばれる。起票ルール（0010）は本体に持たない（0012）
- コメントの編集・削除は扱わない（0007 の試用で頻度を見てから決める）

## スタンド接続（本体の API）

スタンドはゲートウェイの MCP から呼ぶ。使い方はゲートウェイのスキル（api-gateway-mcp のプラグイン `api-gateway-murmur` の `murmur`）で渡す。HTTP API を変えたらスキルの表も直す。

| ツール | 返すもの・起こすこと |
| --- | --- |
| me | User と各テナントの Party |
| list\_lists / get\_list | 見えるリストの一覧。データソース・メンバー・属性定義 |
| list\_threads | 見えるスレッド。filter（my\_turn / mine（自分のメモのソース） / open / overdue / triage / all）、data\_source、tenant。`since` で前回見てからの差分に絞れる |
| get\_thread | スレッドの生のシグナル・持ち主・属性・リンク（結び先の id と経路）、導出したボール、タイムライン（リンク先のシグナルも時系列に並べる）、結び候補（アンカーの一致）。`since` で差分に絞れる |
| add\_note | 個人のメモのデータソースへの SignalObserved。thread\_id を渡せば既存のメモのスレッドに足し、渡さなければ新しいスレッド（「この件」）を作る |
| claim\_thread | ThreadClaimed。持つ・手放す（null）・引き継ぐ |
| link\_threads / unlink\_threads | ThreadLinked。経路 manual |
| set\_attribute | ThreadAttributeSet（本人が付ける属性） |
| dismiss\_thread / reopen\_thread | ThreadDismissed / ThreadReopened |
| move\_signal | 直す操作（シグナルの移し替え） |
| record\_sent | OutboundRecorded。スタンドがゲートウェイ経由で送った直後に呼ぶ。元のスレッドを渡せば経路 sent で結ぶ。スキルは「送る → 記録する」を 1 つの手順にする。起票も同じ |

0009 の `propose_derivation` / `list_proposals` / `approve` / `reject` / `reply_derivation` / `register_subscription` / `list_subscriptions` はなくなる。v2 当初の list\_my\_matters / get\_matter / link\_thread / merge\_matters / close\_matter / reopen\_matter も、スレッド系のツールに統合してなくなる。

## コネクタ

コネクタは取り込みだけを持つ。「どのデータソースとして取得したか」を必ず持つ。送信はスタンドがゲートウェイ経由で行い、コネクタを通らない（0012）。

```typescript
interface Connector {
  channel: 'email' | 'slack' | 'line' | 'jira' | 'bitbucket';
  // Cron から呼ばれる。データソースの資格情報で cursor 以降を取る
  pull(source: DataSource, cursor: Cursor | null): Promise<{ signals: InboundSignal[]; mirrors: ThreadMirror[]; cursor: Cursor }>;
}
// Webhook（LINE / Slack Events）は Worker の fetch で受け、同じ InboundSignal に正規化する
```

- ダミー実装: pull はフィクスチャのキューから返す。シナリオの action 行で `record_sent` を呼ぶと、ダミーはその sent\_ref の observed-sent を次の pull で返す（H5）。観測を記録より先に返す順もシナリオで作れるようにする
- ダミーの Jira: 課題の状態の写し（ThreadMirror）とコメントを返す。スタンドの起票・コメントは `record_sent` で入り、ダミーは対応する通知を観測として返す
- 本番の実装はゲートウェイ経由。インタフェースを変えずに差し替える。実データでの試用（0007）も読み取りだけで、本体に書き込みの資格情報は要らない

**計画 v2 のあと**: ステップ 1〜8 は 2026-10-21 に完了した（`docs/retrospective-v2.md`）。次の段階（自社の実データで Ingest が使えるかを確かめる）のゴールと段取りは `docs/adr/0016`。

**並行トラック（0007 の実データでの試用）**: ステップ 2 が終われば、読み取り専用の実コネクタ（Gmail のメールボックス 1 つ。読者 1 人のデータソース）を回し、区切りの判断と訂正を貯める。前提は 0007「量の見通し」の 6（実メールの本文が残る記録をどこに置くか）を決めること。ステップ 4 のあとは、前提の指標（どこにも結ばれなかった観測された送信、リンクのない課題、誰も持たないスレッドの件数）も数える。

各ステップのテスト名とコミットメッセージに、対応する仮説番号（H1〜H10）を付ける。

## 開発環境・テスト・デプロイ

v1 と同じ。

- ローカル: `pnpm test`（Node の vitest。Postgres は pglite）。`wrangler dev` は Neon の dev ブランチにつなぐ
- 環境: wrangler の env で `dev` と `prod`。main への push で CI が dev にデプロイする。`v*` のタグで prod（prod の設定が空なので当面打たない）
- 実環境: murmur-dev（Neon の `dev` ブランチ、ゲートウェイの Service Binding）。手順は `docs/stand/connect.md`
- Secrets: ANTHROPIC\_API\_KEY、DATABASE\_URL、WEBHOOK\_SECRET、TIMELINE\_TOKEN、GATEWAY\_JWKS / IDENTITY\_ISSUER（vars）
- 監視は Workers Logs のみ

## スコープ外

- チームリスト、購読（構造・自然文の条件）、派生と本体の承認、用件の自動作成とアンカーによる自動リンク（0013・0014。チームの共有は既存のツール、結ぶのは人とスタンド）
- 本物のコネクタ（実データでの試用の読み取りを除く）。本体は外に書かないので、実際の送信・起票はスタンドのスキル（Gmail・LINE などのスキルは既にある）の話で、本体の実装には入らない
- bm-next をデータソースにする（absence の不在の登録・代務の割当）。型は Jira と同じなので H9 で代表させる
- 判断専用のモデル（Jev など）との比較。チューニングの段階で行う
- Jira の人ごとの課題の権限差（0013 の未決）
- コメントの編集・削除
- 起票ルール、承認の件数の計測、観測された送信の返事期待の推定（0012 で外した）
- 後回しと再浮上（boid の決定 9。boid でも効果的に機能していないので入れない）
- 性能（0007「量の見通し」）、通知、モバイル、UI のデザイン
- ゲートウェイの拡張の実装（アカウントリンク、ServiceClient、act-as。`docs/adr/0006`）
