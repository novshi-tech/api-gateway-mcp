# AIネイティブ タスク管理ツール プロトタイプ計画 v2

2026-10-17 · @Naoki NOSE · 設計の正本（`docs/adr/0011`）。v1 の計画はタグ `proto-v1` の `docs/PLAN.md`

## 目的と前提

このプロトタイプは、AI ネイティブ タスク管理ツールのデータモデルとアーキテクチャが成立するかを、外部接続なしで確かめるためのもの。製品の MVP ではない。

v1（`proto-v1`）で、イベントソーシングの土台（決定的な畳み込み、FC-IS、記録・再生、ゲートウェイ経由の認証、実環境へのデプロイ）は確かめた。
H7 を実環境で回したところで、リストの構成に根本の問題が見つかった（`docs/adr/0009` の背景）。v2 は 0008・0009・0010 の形にデータモデルを組み替え、もう一度確かめる。

- 検証対象: 2 層のリスト（会話の層 = データソース、用件の層 = 人とチーム）、業務の知識を持たない Ingest、購読による振り分け、
  送信と派生、正が外にある用件（黒子）、スタンドへのハンドオフ
- 外部接続は全部ダミー。Claude API と、ゲートウェイ経由のスタンド接続は本物。実データでの試用（0007）は並行トラック
- UI は作らない。人が触るのはスタンド（Cowork / Claude Code）。管理用に参照専用の画面だけ作る（0010）
- 技術要素は v1 と同じ: Cloudflare Workers + Neon（Postgres）+ 既存の API ゲートウェイ

## 方向（0010）

Murmur は黒子になる。用件ごとに正を 1 つにし、受け皿のある用件（Jira の課題、bm-next の業務など）はそのサービスが正、受け皿のない用件（LINE の勤怠連絡、メールの問い合わせなど）だけ Murmur が正。
Murmur の価値は、構造のない連絡を拾って用件に振り分けること、チャネルをまたいで誰が誰に返事を待っているか（ボール）を追うこと、境界と承認で外への出入りを守ること。

業務の知識（リストの役割、何をどこへ渡すか、どの連絡を誰が扱うか）は Murmur のコードとプロンプトに持たない（0008）。
テナントが登録したデータ（購読・起票ルール）として持ち、Murmur は機械的に実行する。知識の出どころはスタンドと人。

## 検証仮説と合否基準

それぞれを自動テストにする。全部緑なら v2 のデータモデルは「成立」。

| # | 仮説 | 合否基準（テストの形） |
| --- | --- | --- |
| H1 | 畳み込みは決定的 | 投影を全削除してイベントからリプレイし、投影のハッシュが元と一致する（全シナリオ、メモリと Postgres）。購読を変えてもリプレイの結果は変わらない（昇格の判断はイベントに残っている） |
| H2 | 状態は二層で足りる | スレッドのボールは事前定義属性から、用件のボールはつながったスレッドから導出できる。作業状態は用件のカスタム属性だけで表せる |
| H3 | 境界が守られる | リストのメンバーには、そのリストにあるものだけが見える（会話の層はデータソースの読者、用件の層は昇格したスレッドと派生の本文）。テナント外は 0 件、ゴースト Party は何も取れない |
| H4 | 送信と派生が回る | 用件からの送信（承認 → 送信 → 返事は送ったスレッドに戻る → 期限超過）と、用件のリスト間の派生（承認 → 適用 → 返事）が、各遷移で期待どおりにボールを動かす |
| H5 | 観測と送信を重複排除できる | ツール経由で送った後、同じメッセージが observed-sent として戻っても 1 本に統合され、状態が二重に変わらない（Jira のコメントでも） |
| H6 | Ingest が運用に耐える | 固定のプロンプトで、スレッドの区切りと「返事や対応を求めているか」の正解ラベルとの一致率が、アンカー込みで 90%、AI 判断のみで 80% を超える |
| H7 | スタンドに必要十分な情報が渡る | 実環境で、欠勤連絡とクレームのシナリオをスタンド主導で完走できる。人の操作はユーザーが Claude に出す指示と承認だけ |
| H8 | 購読だけで業務の振り分けが回る | Ingest のプロンプトを変えずに、テナントの購読（構造の条件と自然文の条件）だけで、4 シナリオの用件の層が期待どおりに組み上がる。自然文の条件の分類の一致率が 80% を超える |
| H9 | 正が外にある用件を黒子として扱える | ダミーの Jira で、状態は片方向の写しで足り、コメントは両方向に重複なく流れ、起票ルールで用件から起票できる |

## アーキテクチャ

v1 と同じ（`docs/adr/0001`・`0003`）。本体 Worker 1 本、Neon、既存の API ゲートウェイの 3 つ。本体は上流サービスのトークンを持たず、外との出入りはゲートウェイ経由。

- 本体 Worker: fetch（HTTP API・Webhook・管理用の画面）と scheduled（Cron: 取り込みのポーリングと期限の見回り）
- 判断はすべて純関数のコア（`src/domain/`）に置き、副作用はシェルに集める（FC-IS）
- スタンドはゲートウェイの MCP から本体の HTTP API を呼ぶ（認可の接続の形 (B)）。本体はゲートウェイが署名した sub を検証する
- Claude API（claude-sonnet-5-5、構造化出力）を使うのは 3 か所だけ。どれもプロンプトは固定で、記録・再生の層を通す
  1. Ingest: スレッドの区切りと「返事や対応を求めているか」
  2. 昇格: 購読の自然文の条件の分類
  3. 観測された送信の返事期待の推定
- 境界越えの要約（v1 の `AiSummarizer`）は外す。派生の本文はスタンドが書く（0008）

## データモデル

正は append-only のイベント列。スレッドと用件は投影で、いつでもイベントから作り直せる。

### 2 層のリスト（0009）

| | 会話の層 | 用件の層 |
| --- | --- | --- |
| リスト | データソースごとに 1 つ（機械的に作る） | 個人（ユーザーごとに 1 つ、自動で作る）、チーム（人が作る）、外部（元のサービスのプロジェクト。正はそのサービス） |
| メンバー | データソースを読める人 | 個人は本人、チームと外部は人が決める（リストを作る人の責任） |
| タスク | スレッド（シグナルの束） | 用件（人が追うもの。複数のスレッドを束ねる） |
| 持つもの | ボール、つながった用件 | 状態（open / closed）、カスタム属性、導出したボール、外部の写し |

### マスタ（イベントではない）

| エンティティ | 所有 | 要点 |
| --- | --- | --- |
| Tenant | — | 秘匿境界の単位 |
| User | グローバル | ゲートウェイの User と 1:1。各テナントに自分の Party を 1 つ持つ |
| Party | Tenant | 人物／組織。ゴースト = User を持たない Party。外部マスタ（bm-next など）へのポインタと、購読の条件に使える属性（例: 所属の現場） |
| Address | Tenant | チャネル種別 + 値。Party に紐づく |
| CredentialRef | Tenant | ゲートウェイ側の資格情報への参照 + 主体（User か Organization） |
| DataSource | Tenant | 資格情報 + 絞り込み（メールボックス、Slack のチャネル、LINE 公式アカウント、Jira のプロジェクト）。会話の層のリスト 1 つに対応する。送信元のアドレスを持つ |
| List | Tenant | 種類（source / personal / team / external）。可視性の単位 |
| ListMember | List | Party の所属 |
| AttributeDef | List | 用件の層のリストのカスタム属性の定義。名前・型・AI が読める意味の記述 |
| Subscription | List | 用件のリストがデータソースを購読する。条件（構造 / 自然文）、順序、登録した人。登録できるのは用件のリストのメンバーで、かつデータソースを読める人 |
| FilingRule | List | 起票ルール。用件のリストの用件のうち条件に当たるものを、外部のリストのデータソースに起票する（0010） |

v1 の ChannelPolicy（取得主体 × チャネル → 置けるリスト）はなくなる。置き先はデータソースから機械的に決まる。

### イベント

会話の層:

| 種別 | 誰が出す | 要点 |
| --- | --- | --- |
| SignalReceived | コネクタ | 外部からの受信。データソース、from / to、anchors（In-Reply-To・thread_ts・Jira キー・PR 番号・LINE の quotedMessageId）、body、attachments（参照のみ）、source_ref（データソースごとの重複排除キー） |
| SignalObservedSent | コネクタ | ツール外で行われた送信の観測。返事期待は推定値を持つ |
| SignalThreaded | Ingest・人 | シグナルをスレッドに入れる（既存 / 新規）。by（anchor / awaiting / ai / human）、confidence、reason、返事や対応を求めているか。人の訂正（シグナルの移し替え）も同じイベントで追記する |
| ThreadDismissed | 人・スタンド | 片付け。スレッドのボールを「なし」にし、理由を残す（v1 の IgnoreLog の後継） |

用件の層:

| 種別 | 誰が出す | 要点 |
| --- | --- | --- |
| MatterCreated | 昇格・派生・人・外部 | 用件を作る。リスト、件名、出どころ（promotion / derivation / manual / external） |
| ThreadLinked | 昇格・人・スタンド | スレッドを用件につなぐ（null なら外して仕分け待ちに戻す）。経路（subscription / ball / anchor / sent / external / manual）、購読の ID、操作した人 |
| MatterAttributeSet | 人・スタンド | カスタム属性の値の変更 |
| MatterClosed / MatterReopened | 人・スタンド・見回り | 閉じた用件は、つながったスレッドのボールがこちらに来たときだけ自動で開き直す |
| MatterMerged | 人・スタンド | B を A に統合する（B のスレッドを全部 A に付け替え、B は閉じる。属性は A を優先） |
| MatterMirrored | コネクタ | 正が外にある用件の状態の写し（ステータス・担当者・優先度・期日・完了） |

送信と派生:

| 種別 | 誰が出す | 要点 |
| --- | --- | --- |
| OutboundProposed | スタンド・起票ルール | 用件から外への送信（メッセージ・起票・コメント）の提案。データソース、宛先 Party、本文、返事期待、返信先のスレッド（省略可） |
| OutboundApproved | 人・起票ルール | 承認。宛先の Address を解決して凍結する。起票ルールなら登録が事前の承認（0010） |
| OutboundRejected | 人 | 却下 |
| OutboundSent | コネクタ | 送信の完了。sent_ref。送ったシグナルが入るスレッド（新規なら作る。用件につながった状態で） |
| DerivationProposed | スタンド | 用件のリストから別の用件のリストへの受け渡し。本文（スタンドが書く、必須）、返事期待（省略可） |
| DerivationApproved | 人 | 承認。派生先に用件を作って適用する |
| DerivationRejected | 人 | 却下 |
| DerivationReplied | スタンド・人 | 派生先から元への返事 |
| ReplyOverdue | Cron の見回り | 返事期待の期限超過（送信・派生）。冪等 |

### 投影

- スレッド: データソース、相手の Party、anchors、シグナルの列、ボール（こちら / 特定のユーザー / 相手の Party / なし）、last_inbound_at、last_outbound_at、
  reply_expected_by、overdue、つながった用件、片付け済みか
- 用件: リスト、件名、open / closed、カスタム属性、担当（ボールの宛先のユーザー）、導出したボール（つながったスレッドのどれかがこちら → 担当 / 全部が相手待ち → 返事待ち、期限は最も早いもの / なし）、
  外部の写し、つながったスレッド、統合先
- 仕分け待ち: どの用件にもつながっていなくて、ボールがこちらにあり、片付けていないスレッド（データソースごと）
- 送信、派生、タイムライン（用件ごとに、つながったスレッドのシグナルと用件のイベントを並べる）

### ルール

- 可視性はクエリ層が Viewer（User → そのテナントの Party → リスト所属）から強制する。リストのメンバーには、そのリストにあるものだけが見える。
  会話の層のリスト: スレッドの生の中身。用件のリスト: 用件と、つながったスレッドの生の中身と、派生の本文。テナント外は 0 件、ゴーストは何も取れない
- スレッドと用件は 1 対 1 以下。1 通に 2 つの話がある連絡は、つながった用件から派生で渡す
- 通信状態は事前定義属性だけから機械的に導出する。作業状態は全部用件のカスタム属性。正が外にある用件の状態は写しで、Murmur の側では書き換えない
- 畳み込み（fold）は IO を持たない純関数

## Ingest（会話の層）

判断はスレッドの区切りだけ。業務の知識を使わないので、プロンプトは固定。

1. 受信: コネクタが SignalReceived か SignalObservedSent を append する。source_ref が既出なら弾く。observed-sent が送信の sent_ref と一致すれば統合する（H5）
2. スレッドの区切り（上から順に）
   1. アンカーで決まれば、そのスレッド
   2. 同じ相手（グループのチャネルならそのチャネル）で、こちらが返事を待っているスレッドが 1 本だけなら、そのスレッド
   3. 発信者の直近のスレッド（グループのチャネルならチャネルの直近のスレッド）から、話題の続きかを AI が判断する。「直近」の範囲は設定値
   4. どれにも当たらなければ新しいスレッド
3. 返事や対応を求めているか: アンカーで決まったシグナルも含めて AI が判断する（発話の種類の判断。スタンプ・お礼・成功通知は求めていない）。
   送信なら返事期待を推定する
4. 記録: SignalThreaded を append する
5. 新しいスレッド（区切りの訂正で出たものも含む）は昇格に回す

区切りの基準は時間ではなく話題。同じ相手のスレッドが並行して開いていてよい。v1 の ignore はなくなり、昇格しないものがそれにあたる。

**記録・再生**: AI の入出力を `fixtures/<scenario>/recordings/` に保存し、テストでは再生する。モデルを変えたら取り直して差分を見る。
入出力は型（zod）で決め、Claude 以外の判断専用のモデル（Jev など）も同じ層で比べられるようにする（チューニングの段階）。

## 昇格（用件の層）

新しいスレッドを用件につなぐ。上から順に当てる。

1. 用件から送ってできたスレッドは、最初からその用件につながっている（経路 sent）
2. 購読に当たる（構造の条件 → 自然文の条件の順。構造の条件の中は登録順。自然文の条件は分類器が 1 つだけ選ぶ） → そのリストに用件を作る。
   ボールの宛先が特定のユーザーなら担当にする。購読は「返事や対応を求めていない」連絡にも当てられる（CI の失敗通知など）
3. ボールが特定のユーザーに来た（個人のメールボックス・DM なら本人、@メンションなら言及された人、メンバーが 1 人のリストならその人） → その人の個人リストに用件を作る
4. アンカーの相互参照（Jira キー・PR 番号・チケット番号）で既存の用件が見つかり、その用件のリストがそのデータソースを購読しているか個人リストなら → つなぐ
5. どれでもない → 仕分け待ち。スタンドか人がつなぐ

構造の条件: データソース、宛先アドレス、送り主の Party・属性・ドメイン、件名のパターン、チャネル固有のフィールド。コアの純関数で評価する。
自然文の条件: 固定のプロンプトの分類器が、そのデータソースを購読しているリストの条件から 1 つ選ぶか、どれにも当たらないと答える。confidence が閾値に届かなければ当たらない扱い。

**直す操作**（どれも追記で、元の判断は消さない。スタンドがユーザーの指示で明示的に呼ぶものに、Murmur 側で承認は求めない）

| 誤り | 操作 |
| --- | --- |
| シグナルを違うスレッドに入れた | シグナルを別のスレッドへ移す（新しいスレッドも可） |
| スレッドを違う用件につないだ | スレッドを別の用件へ付け替える（新しい用件、外して仕分け待ちに戻す、も可） |
| 同じ件で用件が 2 つできた | 用件の統合 |
| 対応の要らないものが仕分け待ちに残る | 片付け |

操作できるのは、スレッドが見えていて、かつ移し先のリストのメンバーである人。用件の分割は、新しい用件を作ってスレッドを付け替える。

## 送信・派生・承認・観測

人の承認が外への唯一のゲート（起票ルールは登録が事前の承認）。

- **送信**: 用件から外へ出す。送信元はデータソースのアドレス（返事が同じデータソースに戻り、送ったスレッドに入る）。提案 → 承認（宛先の Address を凍結） → 送信。
  返事期待の期限を過ぎたら Cron の見回りが ReplyOverdue を出す。遅れて返事が来れば解消する。本文はスタンドが書く
- **派生**: 用件のリストの間の受け渡し（見える人が変わる）。提案 → 承認（派生先に用件を作る） → 返事。返事期待は省略可（v1 の 2026-10-16 決定を引き継ぐ）。本文はスタンドが書き、必須
- **ボール**: 送信でスレッドのボールは相手へ、返事でこちらへ戻る。派生でボールは派生先のリストへ移り、返事で戻る
- **観測された送信**: ツール外の送信は SignalObservedSent として入り、送信の sent_ref と一致すれば統合する。一致しなければ、受信と同じくスレッドに入れ、返事期待を推定する
- 承認の件数と種類をシナリオごとに計測し、振り返りで「AI のリスク判断による自動承認」の線引きの材料にする

## 正が外にある用件（0010）

- Jira のプロジェクトは、データソース（コメントのスレッド。課題のキーで 1 課題 1 スレッド）と、外部のリスト（課題 = 用件、正は Jira）の組でつなぐ。
  スレッドと用件は課題のキーで自動でつながる（経路 external）
- 状態は Jira から Murmur への片方向（MatterMirrored）。変えるときは Jira の画面か、スタンドがゲートウェイ経由で直接操作する
- 会話（コメント）は両方向。Murmur を使わない人のコメントは受信、Murmur のユーザーが直接書いたものは観測された送信、スタンド経由は送信（H5 で重複排除）
- 起票ルール: 用件のリストの用件のうち条件に当たるものを、起票の送信として提案し、登録を事前の承認として送る。起票が済むと、用件は課題のキー（外部の参照）を持ち、状態は写しになる
- コメントの編集・削除は扱わない（0007 の試用で頻度を見てから決める）

## スタンド接続（本体の API）

スタンドはゲートウェイの MCP から呼ぶ。使い方はゲートウェイのスキル（nvt-api-gateway-skills の `murmur`）で渡す。HTTP API を変えたらスキルの表も直す。

| ツール | 返すもの・起こすこと |
| --- | --- |
| me | User と各テナントの Party |
| list_lists / get_list | 見えるリストの一覧。リストのメンバー・属性定義・購読・データソース |
| list_my_matters | 自分の用件（担当か、ボールが自分にある）。filter（open / ball_at_me / overdue / all）、tenant |
| get_matter | 用件、つながったスレッド、タイムライン、リストの属性定義と意味記述 |
| list_triage / get_thread | 仕分け待ちのスレッド、スレッドの生のシグナル |
| set_attribute / close_matter / reopen_matter | MatterAttributeSet / MatterClosed / MatterReopened |

## コネクタ

コネクタは「どのデータソースとして取得・送信したか」を必ず持つ。

```typescript
interface Connector {
  channel: 'email' | 'slack' | 'line' | 'jira' | 'bitbucket';
  // Cron から呼ばれる。データソースの資格情報で cursor 以降を取る
  pull(source: DataSource, cursor: Cursor | null): Promise<{ signals: InboundSignal[]; mirrors: MatterMirror[]; cursor: Cursor }>;
  // 承認済みの送信（メッセージ・起票・コメント）。sent_ref は重複排除キー
  send(source: DataSource, msg: OutboundMessage): Promise<{ sentRef: string }>;
}
// Webhook（LINE / Slack Events）は Worker の fetch で受け、同じ InboundSignal に正規化する
```

- ダミー実装: pull はフィクスチャのキューから返す。send は送信ログに書くだけ。`echoObserved: true` なら、送ったものを次の pull で observed-sent として返す（H5）
- ダミーの Jira: 課題の状態の写しとコメントを返し、起票とコメントを受ける
- 本番の実装はゲートウェイ経由。インタフェースを変えずに差し替える。実データでの試用（0007）は読み取り専用で、send はエラーにする

## 実装ステップ

1 ステップ = Claude Code の 1〜2 セッションを目安にし、完了条件のテストが緑になったら次へ進む。

| # | ステップ | 成果物 | 完了条件 | 主に使うシナリオ |
| --- | --- | --- | --- | --- |
| 1 | 計画の書き直し | この PLAN.md v2、`CLAUDE.md`、ADR 0008〜0011 | 直樹のレビュー | — |
| 2 | 会話の層 | DataSource、スレッド、Ingest v2（区切り + 返事や対応を求めているか）、片付け、シグナルの移し替え、記録の取り直し | H1・H3（会話の層）・H6 が緑 | 4 本とも（受信の流れ） |
| 3 | 用件の層と昇格 | 個人・チームのリスト、購読（構造 + 自然文）、昇格の流れ、用件のボールの導出、開き直し、付け替え・統合 | H2・H8 が緑 | absence・complaint |
| 4 | 送信と派生 | 用件からの送信、用件のリスト間の派生（`AiSummarizer` を外す）、期限の見回り、観測された送信 | H4・H5 が緑 | absence・complaint・repair-estimate |

## スコープ外

- 本物のコネクタ（実データでの試用の読み取りを除く）。書き込み（実際の起票・送信）は試用の先の段階
- bm-next を正とする用件（absence の不在の登録・代務の割当）。型は Jira と同じなので H9 で代表させる
- 判断専用のモデル（Jev など）との比較。チューニングの段階で行う
- 派生の本文の境界の検査（0008）。v2 では本文はスタンドが書き、人が承認する
- コメントの編集・削除、起票ルールの「1 件ずつ承認」（ユーザーサポート用のプロダクトとつなぐとき）
- 性能（0007「量の見通し」）、通知、モバイル、UI のデザイン
- ゲートウェイの拡張の実装（アカウントリンク、ServiceClient、act-as。`docs/adr/0006`）
