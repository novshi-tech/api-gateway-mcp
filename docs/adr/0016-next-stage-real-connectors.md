# 0016 次の段階: 自社の実データで Ingest が使えるかを確かめる

- 状態: 採用（方向と順番。2026-10-21、直樹）。ゴールの数字と最初のデータソースは案で、段階 5 に入る前に直樹と決める
- 関連: `docs/retrospective-v2.md`（4 章の持ち越し 1〜6。7 はやらない）、0007（読み取り専用の実コネクタで Ingest から始める）、0015（手元の pull スクリプトの案）、0006（act-as）、0012（本体は外に書かない）、0014、H6

## 背景

計画 v2 で、スレッドとリンクのデータモデルとアーキテクチャは外部接続なしで成立した（`docs/retrospective-v2.md`）。
ただし Ingest の数字（H6 の 34/34）は Claude が書いたシナリオの数字で、設計メモの未決のうち「無視の閾値と監査」（判定 7）と「観測者としての Ingest だけで価値が出るか」（判定 10）は、実データでしか答えが出ない。

直樹の方針（2026-10-21）: 次は自社向けに実コネクタを作り、そこで Ingest がうまく動くかを確かめる。そのために必要なことを、振り返りの持ち越しの順番でやっていく。

## ゴール

**自社（UBS・ノブシテック）の実際の連絡を読み取り専用で Murmur に取り込み続け、区切りと「返事や対応を求めているか」が業務で使える精度かを、人の訂正を正解の代わりにして測る。**

この段階が終わったときに答えが出ているもの:

1. 実データでの Ingest の精度。訂正（シグナルの移し替え、「求めているか」の直し）の件数を、取り込んだ件数で割ったもの（判定 7）
2. 観測者としての Ingest だけで価値が出るか（判定 10）。実際に使った人（直樹・木村さん）の判断で、続けて使いたいか
3. 運用の約束（追いたい件はスタンド経由で送って記録する）が守られているか。計画 v2 の前提の指標（どこにも結ばれなかった観測された送信、元のスレッドへのリンクのない Jira の課題、誰も持たないまま古くなったスレッド）の件数（判定 6）
4. プロンプトかモデルを変えたとき、貯めた実データを手元で再生して比べられること

完了条件（案。段階 5 に入る前に直樹と決める）:

- 自社のデータソース 1 つ以上を、2 週間続けて取り込めた（本体は外に書かず、資格情報は読み取りの権限だけ）
- その期間の取り込み件数・AI を呼んだ件数・区切りの根拠の内訳・訂正の件数・前提の指標を集計した
- 1〜3 の答えを `docs/` に書き、直樹のレビューを通った

やらないこと: 性能の作り込み（0007「量の見通し」は詰まり具合を見て考える）、本物のデータソースへの書き込み、他社への提供。

## 段取り

振り返りの持ち越しの順番どおりに進める。1〜4 は実データを入れる前に整えること、5 が本題、6 は LINE をつなぐときに要ること。
それぞれ、着手するときに ADR に案を書いてから実装する（CLAUDE.md の約束）。

| # | やること | ゴールにどう効くか | 終わりの目安 |
| --- | --- | --- | --- |
| 1 | **相手を引く API**: 自分のテナントの Party と Address を名前で引く（例: `GET /parties?q=伊藤`） | 実データには、やりとりのない相手への送信が普通にある。スタンドが宛先を推測せずに `record_sent` できないと、運用の約束（判定 6）が守れず、前提の指標も測れない（H7 で唯一スタンドだけで完走できなかった箇所） | スタンドがやりとりのない相手の宛先を引いて記録できる。スキルの表に載る |
| 2 | **件名を属性として畳む**: Ingest の件名を初期値にし、本人やスタンドが直せる。ソースの写し（Jira の要約）もここに入れる | 実データでは AI の件名が外れることがあり、一覧の読みやすさがそのまま使い心地になる。直した件数も精度の材料になる | 件名を直す操作と、Jira の要約の写しがある。イベント型を足すなら zod・fold のテスト・リプレイテストを同時に直す |

| 4 | **写しが課題のスレッドより先に届いたとき**: 作成の通知を先に流すか、写しからスレッドを作る | 実物の Jira の webhook は順番を保証しない。自社の Jira をデータソースにするなら要る | Jira の写しがどの順で届いてもスレッドに入る |

## 段階 5 に入る前に決めること

- **最初のデータソース**: 候補は Gmail（ノブシテック、読者は直樹 1 人。ラベル 1 つに絞れる）、UBS の LINE 公式アカウント（読者は木村さん）、UBS の Outlook。0007 は「メールボックス 1 つ、ラベルかフォルダ 1 つから」
- **取り込みの経路**: 手元の pull スクリプト（0015 の案。本体もゲートウェイもほぼ変えない）か、ゲートウェイに act-as を足して Worker の Cron で取る（0006。本番に近いが重い）。LINE は webhook なので、ゲートウェイか本体に受け口が要る
- **取り込みに使う資格情報をテナントごとにどう置くか**: ゲートウェイの資格情報はサインインしたユーザーごとに登録され（ラベルで urban-b・nvt などを区別しているだけ）、ゲートウェイにテナントという概念はない。
  Murmur の側は `CredentialRef`（principal が user か organization。`gatewayCredentialId` は未使用）で「このデータソースはどの資格情報で取るか」を持つが、本体からゲートウェイを呼ぶ経路（0006 の ServiceClient・act-as）がない。
  共有のデータソース（UBS の LINE 公式アカウントなど）は組織の資格情報で取る約束（0013）なので、組織の資格情報をゲートウェイのどこに置くかを決める
- **ログインのアカウント**: Murmur の User はゲートウェイのサインインの ID と 1 対 1。ゲートウェイ（api-gateway-mcp）は 1 つのデプロイに IdP が 1 つ（`IDP_TYPE` が entra か google、Entra はシングルテナントのアプリ）で、
  今のデプロイは UBS の Entra。サインインできるのは UBS の Entra のアカウントを持つ人だけになる。
  この段階はそれで足りる: 直樹は UBS の Entra でサインインし、その User に UBS とノブシテックの両方の Party を持たせる（ノブシテックのサービスの資格情報も、同じゲートウェイの User に登録済み）。木村さんも UBS の Entra
- **複数の組織のメンバーが同じ Murmur を使う形はこの段階の外**（2026-10-21、直樹の指摘）: データモデルはマルチテナント（Party・イベントはテナントごと、User は複数テナントに入れる）だが、
  ゲートウェイの IdP が 1 つなので、別の組織の人（ノブシテックの Google のアカウントだけを持つ人）はサインインできない。実質、使えるのは 1 つの組織の人と、その人が持つ複数のテナント。
  直樹は 2 社を経営し顧客の環境でも作業するので、早めに要る（直樹）。論点は `docs/adr/0017` に書き残した。設計は次のステップで行う
- **実データの本文を Claude に送る範囲と、記録（`recordings`）の置き場所**（0007「量の見通し」の 6。0015 の案は手元だけ、git にも Neon にも入れない）
- **完了条件の数字**（期間・件数）

## 代案

- いきなり 5 から始める: 1〜3 がないと、宛先を推測した記録や、件名の読みにくさ、スタンドの説明の誤りが訂正の件数に混ざり、Ingest の精度と切り分けられない
- 実データの代わりにシナリオを増やす: Claude が書くシナリオでは、判定 7・10 に答えが出ない（v2 の振り返りの結論）
