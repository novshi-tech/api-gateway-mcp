# 0035 Jira で「アクションが要る」のは担当している課題だけ。ほかは文脈として取り込み、範囲の外のメンションは取り込まない

- 状態: 採用（2026-11-04、直樹とのディスカッション）
- 関連: 0012（抽出と追跡。成功の定義の「網羅性・文脈同梱・Go 一発」）、0030（名寄せは人とスタンド）、0031（写しは決まった形。Jira の状態が正）、0033（状態を持つデータソースは個人リスト）、0034（Jira のコネクタ）、H8・H9

## 背景

0034 を実装して UBS で通したあと、Jira の担当者を変えたらどうなるかを考えるうちに、次の問いになった。

1. Murmur のマスタにいない担当者（accountId）は Contact に解決できないので、担当者の写しが効かず、誰の番が「なし」になる
2. 他の人が起票した課題で自分が担当から外れたら、追跡はどうなるか
3. 他の人の課題で担当を自分に変えられたら、取り込まれるか
4. メンションとウォッチをどう扱うか。特に、担当が別の人の課題で自分にメンションされた（質問された）とき、JQL で「自分がメンションされた」を書けない範囲の外のメンション

まとめると「Jira で自分が関わる課題は、すべて Murmur に移さなければならないのか」。答えは No。

## Murmur の責務の確認

直樹の言い方では、Murmur の責務は 2 つ。

- **アクションが必要なタスクを識別する**
- **タスクの実行に必要なコンテキストを構造化して収集する**

0012 の定義（連絡から対応の要る用件を抽出し、その経過を追跡する）と、成功の定義（提示された用件に応えていくだけで仕事が進む。キューへの信頼 = 網羅性・文脈同梱・Go 一発）と突き合わせた。

| この ADR の言い方 | 0012 | 判定 |
| --- | --- | --- |
| アクションが必要なタスクを識別する | 抽出 | 同じ |
| 実行に必要なコンテキストを構造化して収集する | 文脈同梱、綴じる 3 種類（0012）、リンクとタイムライン（0014・0031） | 同じ |
| （上の 2 つに含める） | 追跡（ボールと期限をチャネルをまたいで追う） | ボールの在りかと期限は、次に動くための文脈として読める。矛盾しない |

0012 の定義文は変えない。この ADR の線引きで削れるのは「網羅性」の一部で、それを下の決定 3 の経路で補う。

## 決定

### 1. Jira で「アクションが要る」とみなすのは、担当している課題だけ

- 誰の番は、これまでどおり担当者の写しで決まる（0031。Jira の状態が正）。自分が担当なら自分の番、別の人なら相手の番
- 起票した課題・ウォッチしている課題は、範囲（0034 の決定 2 の既定の JQL）に入れて**文脈として**取り込む。自分の番にはならない
- 担当から外れても、Murmur で開いているスレッドの課題は取り続ける（0034 の決定 2 の `key in (...)`）。写しが追いかけて相手の番になり、片付けるか Jira で完了するまで続く。Webhook の条件からは外れるので、更新は見回りの差分（最大 10 分）で届く
- 他の人の課題で担当を自分に変えられたら、Webhook の条件（担当か起票が自分）と範囲に入るので、写しでスレッドができて自分の番になる。それ以前の起票やコメントは取らない（つなぐ前の過去は取らない。0034）。実物ではまだ確かめていない

### 2. 範囲の中のメンションは、担当者の番のまま

- 担当が別の人の課題で自分にメンションされても、誰の番は担当者のまま。コメントのシグナルの宛先（ボールの保持者）は自分になるが、誰の番は担当者の写しが先に決める
- Jira は担当者を 1 人しか持てないので、メンションで生じる部分的なタスクを担当者の仕組みで表せない。これは Jira の弱点で、Murmur がメンションを解釈して埋めることはしない（Jira の状態が正。0031）
- ボールを渡したいときは担当を変える。自分宛てのメンションに気づく経路は、次の 3

### 3. 範囲の外のメンションは取り込まない。気づくのは Jira の通知、経緯を残すのはウォッチか担当

- JQL には「自分がメンションされた」の条件がなく、Webhook の jqlFilter でも書けない。範囲の外の課題でのメンションは、Jira のコネクタでは取り込まない
- 気づく経路は Jira 自身の通知。Jira のメール通知が Outlook に届いていれば、Outlook のリスト（0024）に入り、「返事や対応を求めているか」が判定され、本文の課題キーで Jira のスレッドの結び候補にもなる。網羅性はこの経路で保つ
- 経緯（課題のコメントの流れ）を Murmur に残したいときは、ウォッチするか担当にする。スタンドはユーザーに頼まれたら Jira のスキルでウォッチを足す。次の差分から範囲に入る

### 4. 解決されていない登場人物は、スタンドが Contact を作る

- Murmur 本体は、Contact に解決できない担当者の写しを誰の番に使わない（今のまま）。埋めるのはスタンド（0030 の決定 8 の名寄せの流れ）
- スタンドは `GET /addresses/unresolved` で Jira の accountId を見つけたら、ゲートウェイの Jira で表示名を引き、**新しい Contact を作る**（`POST /contacts`。名前は表示名、アドレスは `jira` の accountId）。新しく作るだけなら取り違えがないので、ユーザーに確かめなくてよい
- **既にある Contact にアドレスを付ける・まとめる**のは、取り違えると過去のスレッドの相手と誰の番が変わるので、今までどおりユーザーに確かめてから
- Contact ができれば、担当者の写しがその人の番として効く（過去のスレッドにも効く。0030）

## 代案

- **Murmur が範囲の外のメンションも取り込む**（Jira の通知メールや、課題のコメントの全文検索から自分のメンションを探す）: Jira の弱点を Murmur の側で埋めることになり、Jira のコネクタが Jira の通知の仕組みを作り直すことになる。メールの経路で足りる
- **範囲の中のメンションで自分の番にする**（担当者の写しより、自分宛ての新しいメンションを先にする）: Jira の状態（担当者）と Murmur の誰の番が食い違い、0031 の「Jira の状態が正」を崩す。部分的なタスクを表したければ、メモのスレッド（0031）で自分のタスクとして追える
- **解決できない担当者をアドレスのまま相手の番にする**（本体で）: ボールの `addresses` と同じ扱いで一貫するが、担当者が実はチームのメンバー（まだ名寄せしていない人）のとき、相手の番と出てしまう。スタンドが Contact を作るほうが、名前でも見えて分かりやすい

## 帰結

- スキル（novshi-tech/api-gateway-mcp の `api-gateway-murmur`）: 名寄せの節に、Jira の accountId は表示名を引いて新しい Contact を作る（確かめなくてよい）こと、既存の Contact に付ける・まとめるのは確かめること、を足す。「Jira をつなぐ」の節に、アクションが要るのは担当の課題だけで、メンションでボールを渡されても担当者の番のままであること、経緯を残したい課題はウォッチすること、を足す
- 本体のコードは変えない
- 確かめること: 他の人の課題で担当を自分に変えられたときに Webhook が届き、自分の番のスレッドができること（決定 1 の最後）

## 未決

1. 起票・ウォッチの課題を範囲の既定に入れておくか。文脈としては役に立つが、自分の番にならないスレッドが一覧に増える。試用（0016 の段階 5）で件数を見て決める
2. 新しい Contact を作るのを、スタンドが見回りのたびにやるか、ユーザーが一覧を見たときにやるか
