# 0025 Microsoft 365 グループのメールボックスは、アプリの権限 `Group.Read.All` で読む

- 状態: 案（2026-10-29、直樹の判断「まずは `Group.Read.All` を与える」）。実物で確かめるまで実装しない
- 関連: 0024（決定 4: 共有の箱はアプリの権限で読み、RBAC for Applications で絞る。この案はその例外）、0012（外には何も書かない）、0013（共有のデータソースは組織の資格情報）、0020（1 デプロイ = 1 チーム）

## 背景

0024 は、チームの共有の連絡先を「共有メールボックス」と見て、アプリの権限（Exchange の役割 `Application Mail.Read`）を RBAC for Applications の管理スコープで読ませる箱だけに絞ることにした。

実際には、チームの共有のアドレスが共有メールボックスではなく、Microsoft 365 グループ（グループのメールボックス。`RecipientTypeDetails` が `GroupMailbox`）のことがある。この場合:

- `Set-Mailbox` では見つからず、0024 の手順はそのまま使えない
- Graph でグループのメールを読むのは `/groups/{id}/conversations`（スレッドと投稿）で、要るのは Entra のアプリの権限 `Group.Read.All`。Exchange の RBAC for Applications のスコープでは絞れない（と見ている。確かめること）
- `Group.Read.All` はテナントのすべてのグループ（会話・メンバー・プロパティ）に届く

## 決定（案）

1. グループのメールボックスは、アプリの権限 `Group.Read.All` で読む。テナントのすべてのグループに届くことは、まずは割り切る
2. Entra の側では `Group.Read.All`（アプリ）に管理者の同意をする。`Mail.Read` などのメールのアプリ権限は付けない（付けると全員の箱に届く）。共有メールボックスを読むときは 0024 のとおり RBAC for Applications で渡す
3. ゲートウェイは変えない。`client_credentials` の接続先（スコープ `https://graph.microsoft.com/.default`）で、同意した権限のトークンが出る
4. 読むグループは管理者が seed で宣言する（データソースにグループの ID を明示する）。本体はそれ以外のグループを読まない。読み取りしかしないことは、0024 と同じく本体のコードで保証する
5. 読者: グループのメンバーは `Group.Read.All` で読めるので、宣言した読者がメンバーと食い違えば `seedProblems` で知らせられる（0024 の共有メールボックスでは確かめられなかった点）

## 割り切り

- 0024 の「アプリの権限は読ませる箱だけに絞る」より弱い。本体（とゲートウェイを置く Cloudflare のアカウントに Worker をデプロイできる人）は、理屈の上でテナントのすべてのグループの会話を読める
- 絞る方法が見つかったら（下の「確かめること」）、そちらに移る

## 代案

- 共有メールボックスを 1 つ作り、グループのメンバーかつ購読者にして、届いたメールのコピーを受けさせる。0024 の設計のまま RBAC for Applications で絞れる。グループごとに管理者の作業が 1 回要り、コピーが別の箱にできる
- 本人の権限（委任）でグループを読む: 本人がメンバーなら読めるが、グループの会話の変更通知を委任で受けられるかが怪しい

## 実物で確かめること

- グループの会話（`/groups/{id}/conversations` か `threads`）に変更通知のサブスクリプションを作れるか。どの権限か
- delta があるか。なければ Cron の見回りで `lastDeliveredDateTime` を手がかりに取る
- RBAC for Applications のスコープがグループのメールボックスに効かないこと（効くなら絞る）
- 投稿から In-Reply-To・Message-ID に当たるもの（アンカー）が取れるか
- `Group.Read.All` に同意したあと、client credentials のトークンの `roles` に入ること
