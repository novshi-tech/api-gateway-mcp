# 0023 ゲートウェイと Murmur を 1 つのリポジトリにまとめる（構想）

- 状態: 構想（2026-10-28、直樹）。今はまとめない。まとめるときに、この ADR を案に書き直す
- 関連: 0020（チーム単位でセルフホストする。ゲートウェイとは 1 対 1）、0021（決定の 4: ゲートウェイの `deploy` スキルで一緒にデプロイする）、0003（identity）、0012

## 背景

外部コネクタ（Outlook の Webhook）の設計で、Webhook の管理をゲートウェイと Murmur のどちらに置くかを議論した（2026-10-28）。
ゲートウェイに置くと、ゲートウェイの性格（HTTP と OAuth2 だけを知り、サービスを足してもコードを変えない）が崩れ、ゲートウェイから Murmur へ処理を投げ返すことになって、両者が密に結合する。
以前にも、両者の結合が強まると見て 1 つのリポジトリにまとめる案が出たが、「リポジトリだけをまとめるなら、今のままでよい」として見送った。

Webhook の管理を Murmur に置くなら（コネクタの ADR で決める）、実行時の結合は増えない。それでも、開発とデプロイの結合はもう密になっている。

- 認証方式 `identity` と Service Binding を使うのは Murmur だけ。この取り決めを変えるたびに、2 つのリポジトリで足並みをそろえる
- 0021 の決定 4（ゲートウェイの `deploy` スキルで Murmur も一緒にデプロイする）は、リポジトリが別だとやりにくい。ゲートウェイの「1 つのクローンから複数のデプロイを管理する」形（`deployments/<名前>.jsonc`）にそのまま乗る
- 0020 で、セルフホストの手間を下げることを製品の課題にした。チームが取ってくるリポジトリは 1 つのほうがよい

## 構想

- まとめるのはリポジトリだけ。Worker（デプロイの単位）は分けたままにする
- ゲートウェイは単独でもデプロイでき、Murmur なしでも使える（業務の自動化に使っている）。依存の向きは Murmur から共通の部品へだけで、ゲートウェイは Murmur の何も import しない。ゲートウェイのテストとデプロイは Murmur がなくても通る
- 1 つの `deploy` スキルで、ゲートウェイだけ、またはゲートウェイと Murmur を一緒にデプロイする。配線（Service Binding・JWKS・シークレット）を自動にする

## まとめるときに決めること

1. 運用の違い: ゲートウェイは本番で使っていて PR で回している。Murmur はプロトタイプで main に直接 push している。どちらに寄せるか
2. パッケージ管理: ゲートウェイは npm、Murmur は pnpm。ワークスペースの形
3. プラグインのマーケットプレイス: ゲートウェイのリポジトリのルートが、プラグインのマーケットプレイスを兼ねている。構成を変えても配布が壊れないようにする
4. 移し方: 履歴を残すか（unrelated histories のマージか subtree）、CI、murmur-dev へのデプロイ
5. スタンド用のスキル（nvt-api-gateway-skills の `murmur`）をどこに置くか

## いつ考えるか

急がない。きっかけになりそうなのは、0021 の決定 4（一緒にデプロイ）に手を付けるときか、2 つのリポジトリにまたがる変更が続いて足並みをそろえるのがつらくなったとき。
