# 0024 外部コネクタ: Webhook は本体が持ち、個人の箱は本人の OAuth、共有の箱はアプリの権限で読む

- 状態: 採用（2026-10-29、直樹）。共有のアドレスが Microsoft 365 グループのときは 0025（購読者にした共有メールボックスで読む）。0012 の状態に注記を足し、CLAUDE.md の約束事と注意を直した。ゲートウェイの側は api-gateway-mcp の `docs/background-access.md`（#15）で決める。**本体がゲートウェイの OAuth クライアントになる形（CIMD）は 0023（採用、2026-11-04）で改める**（Murmur をゲートウェイの機能にして 1 つの Worker にする。実装までは今の書き方が実装の正）
- 関連: 0012（外には何も書かない。この ADR で緩める）、0016（次の段階。段取り 5 の準備）、0007（読み取り専用・量の見通し 7）、0015（手元の pull スクリプトの案。この ADR で置き換える）、0003（identity）、0006（ServiceClient・act-as。この ADR で置き換える）、0013（共有のデータソースは組織の資格情報）、0020・0021（1 デプロイ = 1 チーム、同じ Cloudflare アカウント）、0023（リポジトリをまとめる構想）
- 設計の詳細: Artifact「Murmur 外部コネクタ設計」（v3）。ゲートウェイの側の提案は api-gateway-mcp の `docs/background-access.md`（#15）

## 背景

0016 の段取り 5（実データの試用）に入るため、最初の実コネクタを Outlook（Microsoft Graph）で作る。
外部コネクタの難所は Webhook の管理で、Graph ではサブスクリプションに寿命（message は最長 10,080 分）があり、更新・再認可・作り直し・取りこぼしの回復が要る。
また、誰の権限で動かすかで見えるメールボックスが変わる。Graph の委任の権限で通知を受けられるのは本人の箱だけで、共有メールボックスの通知にはアプリの権限が要る（`Mail.Read.Shared` は通知に使えない）。

議論の経過（2026-10-28）:

1. 手元のランナー（0015 の読み替え）: Webhook の管理を避けているだけで、先送りになる
2. Webhook の管理をゲートウェイに置く: ゲートウェイは HTTP と OAuth2 だけを知り、サービスを足してもコードを変えない製品で、Webhook はサービスごとの知識とサブスクリプションの状態を持ち込む。さらにゲートウェイから Murmur へ処理を投げ返すことになり、両者が密に結合する。採らない
3. Murmur は正規化・delta・アンカーでもうサービスの仕様を知っているので、Webhook も Murmur が持つ。そのために 0012 を緩める（この ADR）
4. 権限は全部アプリに寄せる案も出たが、人が増えるたびに管理者の作業（Exchange の RBAC のスコープの変更）が要り、本人がつないだ記録も残らない。個人の箱は本人の権限、共有の箱はアプリの権限に分ける
5. Murmur がゲートウェイの資格情報を使う許可のために新しい機構（grant）を考えたが、ゲートウェイはもともとエージェント向けに OAuth で許可を出している。Murmur も Claude と同じ OAuth クライアントになればよい。新しい機構は要らない
6. 共有の箱のアプリの資格情報には同意する人がいない。テナントの管理者がゲートウェイの管理画面で登録し、Murmur は Service Binding の専用入口から使う

## 決定（案）

### 1. Webhook の管理は本体が持つ。0012 を緩める

- 変えない: データソースの中身を書き換えない。送信・起票・コメント・状態の変更はスタンドがゲートウェイ経由で行い、本体は `record_sent` で事実だけを記録する
- 新しく許す: 取り込みのための購読の管理（Graph のサブスクリプションの作成・更新・再認可・削除、Jira の動的 Webhook の登録と延長など）。データソースの中身に触れない操作に限る
- 読み取りしかしないことは、本体のコードで保証する。取り込みで AI が判断するのは区切りと「返事や対応を求めているか」だけで、書き込むかどうかを判断する箇所はないので、決定論的に保証できる。本体のためだけに読み取りだけの接続は用意しない（2026-10-28、api-gateway-mcp#15 のレビュー）
- 本体は上流のトークンを持たない（CLAUDE.md のまま）。持つのは、個人の箱についてのゲートウェイのリフレッシュトークンだけ
- 本体の公開ルートに `/webhooks/graph`（通知とライフサイクル）と OAuth のコールバック・クライアントのメタデータを足す

### 2. 通知はヒントで、正は delta

- 通知の中身（メールの id）は使わず、必ず delta クエリで取る。受け口は clientState を照合してキューに積み、3 秒以内に 202 を返す
- 取りこぼしの保険を 3 つにする: 通知、ライフサイクルの `missed`、Cron の定期の delta（30 分ごと）。どれも同じ「delta で差分を取る」になる
- 同期は直列にする（Cloudflare Queues、同時実行 1。0007「量の見通し」の 7 の構成をここで入れる）。cursor は取り込みが終わってから進め、`sourceRef` の重複排除で二重を防ぐ
- サブスクリプションの台帳・delta の cursor・トークン・同期の健康状態は、台帳（スレッドの事実）ではないのでイベントにせず、D1 のテーブルに置く。リプレイ（H1）の対象外
- サブスクリプションの一生（作成・延長・再認可・作り直し・`broken`・試し直し・削除）は、計画を純関数にしてテストする

### 3. 個人の箱は本人の OAuth

- 本体はゲートウェイの OAuth クライアントになる（Claude と同じ。CIMD で、client_id は本体が公開するメタデータの URL）
- 本人がゲートウェイで Graph の接続をつなぎ（スタンドが使うものと同じ）、スタンドから本体に「Outlook をつなぐ」を頼み、ゲートウェイの同意の画面で本体を許可する
- 取り込みのたびに `issue_token` で 15 分のトークンをもらい、ゲートウェイの REST で Graph を呼ぶ。リフレッシュトークンは入れ替わるので、リフレッシュは 1 か所で直列にする
- データソースは本人の同意のあとに本体が実行時に作る。読者は本人 1 人（`seedProblems` の「個人の資格情報は読者 1 人のデータソースだけ」が構造で守られる）。マスタを seed だけで持つのをやめ、この経路だけ実行時の作成を許す
- 割り切り: 今のゲートウェイの同意は全体の単位で、接続ごとには絞れない。本体は理屈の上で本人のほかの接続にも届く（Claude と同じ信頼の置き方）

### 4. 共有の箱はアプリの権限

- テナントの管理者が Entra に本体専用のアプリを登録し、Exchange の RBAC for Applications で役割 `Application Mail.Read` を読ませる箱だけの管理スコープに付ける。Entra の側では API のアクセス許可を何も付けない（`Mail.Read` のアプリ権限に同意すると全員の箱に届き、Exchange のスコープより優先される。2026-10-29 に書き方を直した）
- ゲートウェイには、管理者が管理画面で client credentials の接続先を登録する（client id と secret はゲートウェイの `Registry` に暗号化して置く）
- 本体はゲートウェイの名前付きエントリポイント（インターネットに出ず、Service Binding からしか呼べない）から使う。本体とゲートウェイの間のシークレットは要らない。信頼の境界は Cloudflare のアカウントになる（0020 でチームのもの）
- その入口で使えるのは、デプロイが持つ client credentials の接続だけ。個人の接続には届かない
- データソースと読者は管理者が seed で宣言する。Graph からは箱の権限を読めないので、本体は読者を自動では確かめられない。`seedProblems` に「アプリの資格情報のデータソースは箱の OID を明示する」を足し、データソースの説明に読者の根拠を書く

### 5. ゲートウェイに頼むこと（api-gateway-mcp の側で決める）

- 認証方式に OAuth2 の client credentials を足す。管理画面から登録できる
- client credentials の接続だけを使わせる、名前付きのエントリポイントを足す
- redesign.md の「認証情報の持ち主はユーザーだけ」を、「管理者が登録する client credentials の接続先を除く」に改める
- あるとよい: 許可したクライアントを一覧して取り消す画面

ゲートウェイから本体への呼び出しは増やさない（スタンドの中継だけ）。呼び出しはいつも本体からゲートウェイへの一方向。

## 置き換えるもの

- 0015（手元の pull スクリプト）: この ADR の経路に置き換える。実データの記録を手元に置く案（0015 の 3）は、0016 の「本文と記録の扱い」で改めて決める
- 0006 の 2（ServiceClient principal）と 3（act-as）: 2 は「管理者が登録する client credentials と専用入口」、3 は「本体がゲートウェイの OAuth クライアントになる」に置き換わる

## 代案

- 手元のランナー（0015）: Webhook の管理を先送りするだけ
- Webhook の管理をゲートウェイに置く: ゲートウェイの性格が変わり、ゲートウェイから本体へ処理を投げ返すことになって密に結合する
- 権限を全部アプリに寄せる: 人が増えるたびに管理者の作業が要り、本人がつないだ記録が残らない
- 本体がアプリの資格情報を直接持つ: 「本体は上流のトークンを持たない」を崩す。ゲートウェイに置いても同じアカウントの中なので、守りの境界は変わらないが、資格情報の置き場所が 2 つに割れる
- ゲートウェイに独自の許可の機構（grant）を足す: OAuth の同意の作り直しになる

## 未決

1. 同意の取り消しのあとに残るサブスクリプション: 本体は Graph を呼べないので消せず、期限（最長 7 日弱）まで通知が届く。本体は無視する。これで割り切るか
2. ゲートウェイの同意を接続の単位に絞るか（当面は割り切る案）
3. Claude に送る本文の範囲（社外の人のメール）と、実データの記録の置き場所（0007「量の見通し」の 6）
4. 上流（Entra）向けの client secret をなくすか（証明書、またはゲートウェイの署名でのフェデレーション資格情報。Ed25519 を Entra が受け付けるか要確認）

## 実物で確かめること（設計の段取り S0）

- 委任の `reauthorizationRequired` の間隔
- delta で `uniqueBody` と In-Reply-To（`internetMessageHeaders`）が取れるか
- 下書き → 送信で `internetMessageId` が変わらないか（`sendMail` は Message-ID を返さないので、スタンドは下書き → 送信で送る。H5）
- Cloudflare の名前付きエントリポイントがインターネットに出ないこと

## 実装の記録（2026-10-30、個人の箱）

設計の段取り（Artifact「Murmur 外部コネクタ設計」）の S1（同期とサブスクリプションの部品）と S2（個人の箱をつなぐ）を実装した。共有の箱（S6）はまだ。S0（実物で確かめる）のうち delta の分は `docs/research/2026-10-30-graph-delta.md`（サブスクリプションと CIMD は dev にデプロイしてから）。ゲートウェイの変更はない。

- 経路: スタンドが `POST /api/connections/outlook` → 本体が PKCE と state を付けたゲートウェイの認可の URL を返す → 本人がゲートウェイで本体（CIMD の `client_name` は Murmur）を許可 → `/oauth/callback` でコードをトークンに換える → `list_credentials` で本人の `graph` の接続を選ぶ（複数なら `choose` を返し、スタンドが `credential_id` を付けて呼び直す）→ `issue_token` の短命トークンの `sub` が頼んだ本人と同じことを確かめてから同意を保管する → Graph の `/me` のアドレスでデータソースを作る → キューに `setup`
- データソースの実行時の作成は `connectMailbox`（`src/domain/connection.ts`、純関数）。2026-11-04 に main に載せ直したとき、0030 の個人のリスト（`createPersonalDataSource`）の上に作り直した: 主のアドレスをリストでのアイデンティティにし、エイリアスも本人の Contact に付け、読者は本人だけ。窓口のアドレスは持たない。別の人のアドレスが混じれば断る（`conflict`）。同じ本人・同じゲートウェイの接続なら作り直さない。`DataSource`（service）に `connector: { kind: 'graph-mail', mailbox: 'me', folders }` を足した（マスタの形の変更で、イベント型は変えていない）。マスタの書き換えは 0030 の `changeMaster`（差分を当てて変更の記録に残す）で、最初の実装の `MasterStore.append` はなくした
- 運用の状態（イベントにしない）: `gateway_grants`（リフレッシュトークンとアクセストークンを `TOKEN_KEY` の AES-GCM で包む。版の比較で書く）、`oauth_pending`（15 分、1 回きり）、`connector_sources`（フォルダごとの delta の位置・最後に取り込んだ受信時刻・`setup` / `ok` / `broken` / `disconnected`）、`graph_subscriptions`（clientState は SHA-256 だけ）。マイグレーションは `drizzle/0001_connectors.sql`
- 直列: ゲートウェイを呼ぶ仕事（`setup` / `sync` / `lifecycle` / `maintain` / `disconnect`）は全部 Cloudflare Queues（同時実行 1）に積む。Cron は 5 分ごとに `maintain` を積むだけで、サブスクリプションの手入れ（なければ作る、残り 48 時間で延ばす、延長が 404 なら作り直して取り直す）と 30 分ごとの保険の delta と broken の 1 時間ごとの試し直しは、計画の純関数（`planMaintenance`・`planLifecycle`）が決める。キューを通らないのは、`POST /api/connections/outlook` で同意が既にあるときの `list_credentials` / `issue_token` だけで、リフレッシュが重なれば負けた方は版が進むのを待って勝った方のトークンを使う（同じ isolate の中では 1 回にまとめる）
- delta: 初回は `$filter=receivedDateTime ge <つないだ時刻>` で過去分を取らない。1 回の仕事で 20 ページまで読み、超えたら続きを積む。cursor はページを取り込み終えてから進める。410 なら最後に取り込んだ受信時刻から取り直す。In-Reply-To は delta の `$select` に `internetMessageHeaders` を入れて取る（受信トレイ。送信済みにはヘッダーがない。`docs/research/2026-10-30-graph-delta.md`）。本文は `uniqueBody`、なければ引用の見出しから先を落とす
- 同意の問題（ゲートウェイの 403、トークンの `invalid_grant`、Graph の 401/403）は `broken`（理由つき）。それ以外の失敗はキューが試し直す（5 回まで）。`GET /api/connections` で本人に状態を出す
- 読み取りしかしないこと: Graph の呼び出しは `src/connectors/graph/api.ts` の `GraphApi` に集め、そこにあるのは読み取り（`/me`・delta）と購読の管理（サブスクリプションの作成・延長・削除）だけ
- Worker の設定（dev）: vars に `PUBLIC_URL`、secrets に `TOKEN_KEY`、キュー `murmur-dev-sync`（producer `SYNC_QUEUE` と consumer）。任意で `GATEWAY_URL`（なければ `IDENTITY_ISSUER`）、`GRAPH_SERVICE`（既定 `graph`）、`GATEWAY_WEB`（ゲートウェイのデフォルトの入口への Service Binding。workers.dev の Worker 同士の fetch が通らないときに使う）
- テスト: 偽の Graph（`test/helpers/fake-graph.ts`）と偽のゲートウェイで、つなぐ・本人の取り違え・state の期限・選ぶ・つなぎ直し・外す、通知 → delta、記録した送信との統合（H5）、ページの続き、410、サブスクリプションの消失、broken と戻り、リフレッシュの重なり。D1 の運用の状態とマスタの追記はメモリと Miniflare に同じ契約テスト

### 実装で決めた細部（直樹に見てもらう）

1. 外したデータソースはマスタから消さない（読者はそのまま過去のスレッドを読める）。つなぎ直すとその時点から取る（間の分は取らない）
2. broken からの戻りは、止まっていた間の分も取る（最後に取り込んだ受信時刻から）
3. 本人の確かめに、`issue_token` の短命トークンの `sub` を（署名を確かめずに）読む。ゲートウェイから TLS で直接受け取ったものなので
4. 未決 3（Claude に送る本文の範囲）は決めていない。いまの実装は、つないだ箱の受信の本文（`uniqueBody`）を区切りと「求めているか」の判断のために Claude に送る
