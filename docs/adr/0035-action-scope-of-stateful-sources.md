# 0035 状態を持つデータソースで「アクションが要る」のは、ソースでボールを持つ人に自分がいるものだけ。ほかは文脈として取り込み、範囲の外は取り込まない

- 状態: 採用（2026-11-04、直樹とのディスカッション。最初は Jira に限った書き方だったが、どのデータソースでも通用する原則なので、同じ日に汎用の書き方に直した）
- 関連: 0012（抽出と追跡。成功の定義の「網羅性・文脈同梱・Go 一発」）、0030（名寄せは人とスタンド）、0031（写しは決まった形。ソースでボールを持つ人 `holders`。ソースの状態が正）、0033（状態を持つデータソースは個人リスト）、0034（Jira のコネクタ）、0028（開発のシグナル。PR）、H8・H9

## 背景

0034 で Jira のコネクタを実装して実物で通したあと、Jira の担当者を変えたらどうなるかを考えるうちに、次の問いになった。

1. Murmur のマスタにいない担当者（アカウント）は Contact に解決できないので、写しの `holders` が効かず、誰の番が「なし」になる
2. 他の人が起票した課題で自分が担当から外れたら、追跡はどうなるか
3. 他の人の課題で担当を自分に変えられたら、取り込まれるか
4. メンションとウォッチをどう扱うか。特に、担当が別の人の課題で自分にメンションされた（質問された）とき、取り込みの条件で「自分がメンションされた」を書けない範囲の外のメンション

まとめると「状態を持つデータソースで自分が関わるものは、すべて Murmur に移さなければならないのか」。答えは No。
問いは Jira から始まったが、状態を持つデータソース（課題のトラッカー、PR、タスク管理ツール）に共通の話になる。

## Murmur の責務の確認

直樹の言い方では、Murmur の責務は 2 つ。

- **アクションが必要なタスクを識別する**
- **タスクの実行に必要なコンテキストを構造化して収集する**

0012 の定義（連絡から対応の要る用件を抽出し、その経過を追跡する）と、成功の定義（提示された用件に応えていくだけで仕事が進む。キューへの信頼 = 網羅性・文脈同梱・Go 一発）と突き合わせた。

| この ADR の言い方 | 0012 | 判定 |
| --- | --- | --- |
| アクションが必要なタスクを識別する | 抽出 | 同じ |
| 実行に必要なコンテキストを構造化して収集する | 文脈同梱、綴じる 3 種類（0012）、リンクとタイムライン（0014・0031） | 同じ |
| （上の 2 つに含める） | 追跡（ボールと期限をチャネルをまたいで追う） | ボールの在りかと期限は、次に動くための文脈として読める。矛盾しない |

0012 の定義文は変えない。この ADR の線引きで削れるのは「網羅性」の一部で、それを下の決定 3 の経路で補う。

## 決定

### 1. アクションが要るのは、ソースでボールを持つ人（`holders`）に自分がいるものだけ

- 状態を持つデータソースでは、誰がやるかをソースが決めている（0031 の `holders`。Jira は担当者、PR はレビュー待ちならまだレビューしていないレビュアー、変更を求められたら作者）。誰の番は、これまでどおりこの写しで決まる。ソースの状態が正
- 自分が `holders` にいないもの（Jira で起票しただけ・ウォッチしているだけの課題、自分が作者でレビュー待ちの PR など）は、取り込みの範囲に入れて**文脈として**取り込む。自分の番にはならない
- `holders` から外れても、Murmur で開いているスレッドは取り続ける（Jira は 0034 の決定 2 の `key in (...)`）。写しが追いかけて相手の番になり、片付けるかソースで完了するまで続く
- 自分が `holders` に入ったら（Jira で担当を自分に変えられたなど）、取り込みの範囲に入り、写しでスレッドができて自分の番になる。それ以前の経緯はシグナルにしない（つなぐ前の過去は取らない）。Jira では実物でまだ確かめていない

### 2. 範囲の中で自分宛てに話しかけられても、誰の番は `holders` のまま

- `holders` が別の人のスレッドで、コメントのメンションなどで自分に話しかけられても、誰の番は `holders` のまま。シグナルの宛先（ボールの保持者）は自分になるが、誰の番は写しが先に決める
- ソースが `holders` を 1 人しか持てない（Jira の担当者）など、話しかけで生じる部分的なタスクをソースの仕組みで表せないのは、そのソースの弱点。Murmur が話しかけを解釈して埋めることはしない（ソースの状態が正。0031）
- ボールを渡したいときは、ソースで `holders` を変える（担当を変える）。ユーザーが自分のタスクとして追いたければ、メモのスレッドで追う（0031）

### 3. 範囲の外の話しかけは取り込まない。気づくのはソースの通知、経緯を残すのはソースで範囲に入れること

- 取り込みの条件で書けないもの（Jira の JQL と Webhook の条件には「自分がメンションされた」がない）は、そのデータソースのコネクタでは取り込まない
- 気づく経路は、そのソース自身の通知。通知がメールなどで届き、それが取り込まれていれば（Outlook のリスト。0024）、「返事や対応を求めているか」が判定され、本文のキーで結び候補にもなる。網羅性はこの経路で保つ
- 経緯を Murmur に残したいときは、ソースの側で範囲に入れる（Jira ならウォッチするか担当にする）。スタンドはユーザーに頼まれたら、そのサービスのスキルで行う。次の差分から範囲に入る

### 4. 解決されていない登場人物は、スタンドが Contact を作る

- 本体は、Contact に解決できない `holders` を誰の番に使わない（今のまま）。埋めるのはスタンド（0030 の決定 8 の名寄せの流れ）
- スタンドは `GET /addresses/unresolved` で未解決のアカウントを見つけたら、そのサービスのスキルで表示名を引き、**新しい Contact を作る**（`POST /contacts`）。新しく作るだけなら取り違えがないので、ユーザーに確かめなくてよい
- **既にある Contact にアドレスを付ける・まとめる**のは、取り違えると過去のスレッドの相手と誰の番が変わるので、今までどおりユーザーに確かめてから
- Contact ができれば、写しの `holders` がその人の番として効く（過去のスレッドにも効く。0030）

## 代案

- **Murmur が範囲の外の話しかけも取り込む**（ソースの通知や本文の全文検索から自分宛てを探す）: ソースの弱点を Murmur の側で埋めることになり、コネクタがソースの通知の仕組みを作り直すことになる。通知のメールの経路で足りる
- **範囲の中の話しかけで自分の番にする**（`holders` より、自分宛ての新しい話しかけを先にする）: ソースの状態と Murmur の誰の番が食い違い、0031 の「ソースの状態が正」を崩す
- **解決できない `holders` をアドレスのまま相手の番にする**（本体で）: ボールの `addresses` と同じ扱いで一貫するが、`holders` が実はチームのメンバー（まだ名寄せしていない人）のとき、相手の番と出てしまう。スタンドが Contact を作るほうが、名前でも見えて分かりやすい

## 帰結

- スキル（novshi-tech/api-gateway-mcp の `api-gateway-murmur`）: この原則は特定のサービスに依らない書き方で足す（状態を持つデータソースの扱い、名寄せ）。サービスの API の使い方（Jira の accountId から表示名を引く、ウォッチを足す）は、そのサービスのスキル（`api-gateway-atlassian` の jira）に置き、Murmur のスキルからは「そのサービスのスキルで」と指すだけにする
- 本体のコードは変えない
- 確かめること: Jira で他の人の課題の担当を自分に変えられたときに、Webhook が届いて自分の番のスレッドができること（決定 1 の最後）

## 未決

1. 文脈として取り込むもの（Jira の起票・ウォッチの課題）を範囲の既定に入れておくか。文脈としては役に立つが、自分の番にならないスレッドが一覧に増える。試用（0016 の段階 5）で件数を見て決める
2. 新しい Contact を作るのを、スタンドが見回りのたびにやるか、ユーザーが一覧を見たときにやるか
