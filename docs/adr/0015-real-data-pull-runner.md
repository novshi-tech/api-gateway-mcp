# 0015 実データの試用は、手元の pull スクリプトがゲートウェイ経由で Gmail を読み、本体の Webhook に流す

- 状態: 提案（2026-10-21。直樹は「H7 は一回まわせればいい。それより外部コネクタを使った実データで評価できるようにしたい」。経路・データ・記録の置き場所は「こだわりなし」だったので、案を書いて確認を待つ）
- 関連: 0007（読み取り専用の実コネクタで Ingest から始める。v1 の API が前提なので、ここで v2 に読み替える）、0006（act-as は設計のみ）、0012（本体は外に書かない）、0014、計画 v2「並行トラック」、H6

## 背景

計画 v2 の並行トラック（0007 の試用）は「ステップ 2 が終われば、読み取り専用の実コネクタ（Gmail のメールボックス 1 つ、読者 1 人のデータソース）を回す」。
ステップ 5 まで済み、シナリオの H6 は 33/33 だが、Claude が作ったシナリオの数字にすぎない。実データでの区切りと「返事や対応を求めているか」を、人の訂正を正解の代わりにして測りたい。

詰まっているのは 2 点。

1. **本体は上流のトークンを持たない**（0003・0012）。Worker の Cron が「ユーザーとして」ゲートウェイを呼ぶ経路（0006 の act-as、または ServiceClient）はまだない
2. **実メールの本文が残る記録の置き場所**（0007「量の見通し」の 6）が決まっていない

## 決定（案）

### 1. 取り込みは手元の pull スクリプト

- `scripts/pull.ts`（Node 専用。Worker には入らない）を足す。`pnpm pull gmail --data-source <id> [--label <label>]`
- ゲートウェイのトークンは、Claude（Claude Code）が MCP の `issue_token` で発行して `GW_TOKEN` に渡す（15 分。試用の 1 回分には足りる）。スクリプトはゲートウェイの `gmail` サービスを読むだけ（`messages.list` / `messages.get`、`gmail.readonly` の資格情報）
- Gmail のメッセージを `InboundSignal` に正規化する（`dataSourceId`、from / to、件名、本文のテキスト、`messageId`・`inReplyTo`・Gmail の `threadId` は `threadKey` にしない（メールの区切りは In-Reply-To と AI に任せる。0014 の区切りの規則どおり）、添付は名前とハッシュだけ、`sourceRef` は `gmail:<id>`）。正規化は純関数にしてテストする
- 本体の Webhook（`POST /webhooks/dummy/{tenant}`、`WEBHOOK_SECRET` の署名）に流す。Webhook のパス名の `dummy` は残る（試用の間は名前だけの問題として据え置く）
- 取得位置（cursor）は手元に置く（`~/.local/state/murmur/cursor-<data source>.json`、最後に取った `internalDate` と id）。過去分は取らず、初回はつないだ時点から（0007）
- 取り込みの頻度は手で（または Claude に頼んで）回す。Cron には載せない。Worker の act-as は実業務を観察させる段階で 0006 として別に決める

これで本体とゲートウェイはほぼ変えずに済む。本体は「データソースの写し」を受け取るだけで、外には何も書かない。

### 2. 最初のデータソースは Gmail（nvt）の 1 ラベル

- seed に `ds_gmail_nose`（`kind: service`、`channel: email`、資格情報は直樹の個人の資格情報、読者は直樹 1 人、`selfAddressIds` は直樹のアドレス）を足した試用用の seed（`fixtures/trial-gmail/seed.json`）を作る。シナリオではないので `signals.jsonl` と `expected.json` は持たない
- ラベルを 1 つに絞る（何にするかは直樹が決める）。社外の人のメールが多いラベルは避ける

### 3. 実データの Claude の記録は手元だけ

- 本体（murmur-dev）の Ingest は記録せずに Claude を呼ぶ（今と同じ）。記録・再生は手元で行う
- pull スクリプトは、流したシグナル（正規化後）を手元の `~/.local/share/murmur/trial/<data source>/signals.jsonl` にも残す。プロンプトやモデルを変えたときは、これを手元の `pnpm scenario` 相当（メモリの本体に流して `--ai record` で記録）で再生して比べる。記録も同じ手元のディレクトリに置き、git には入れない
- Neon の dev ブランチには実データのイベントが残る。試用をやめるときは `pnpm seed` で空にする

### 4. 測り方（0007 の v2 への読み替え）

- 正解の代わりは人の訂正。区切りの誤りは `move_signal`、「求めているか」の誤りは `move_signal` の `needs_response`、要らないものは `dismiss_thread`
- 数えるもの: 取り込んだ件数、AI を呼んだ件数と区切りの根拠の内訳（anchor / awaiting / no_match / ai）、訂正の件数（移し替え・「求めているか」の直し）、片付けの件数。管理画面（`/admin`）か、スクリプトで events を集計する
- 計画 v2 の前提の指標（どこにも結ばれなかった観測された送信など）も、この試用で数える

### 5. H7 は止めて、あとで 1 回だけ回す

- 今の H7（absence を s01 まで）は止める。日付が「明日（17日）」のまま実時刻とずれる件は、回すときにその場で読み替える（直樹「一回まわせればいい」）
- H10 で繰り返すなら、そのときにシナリオを日付なしに直す

## 代案

- **ゲートウェイに act-as を足して Cron で取る**: 本番に近いが、ゲートウェイの設計（同意の記録、トークンの保管）が重い。試用で判断の質を見るのが先なので後回し
- **スタンドが gmail スキルで読んで、本体の新しい API に渡す**: 取り込みがスタンドの話しぶりに左右され、「取り込みはコネクタ」の形から外れる
- **記録を Neon に置く**: どこからでも再生できるが、社外の人の本文がクラウドに貯まる。手元だけに置く

## 未決

2. 実データで Claude に本文を送ってよい範囲（社外の人のメール）。ラベルで絞る前提で、直樹が判断する
