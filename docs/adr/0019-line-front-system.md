# 0019 LINE 公式アカウントのチャネルは Murmur の手前の別システムが持つ

- 状態: 採用（方向。2026-10-22、直樹）。システムの中身（ID の紐づけ・メニュー・API）の設計はまだ。作るのは 0016 の Outlook のあと
- 関連: 0008（業務の知識を持たない）、0012（外に書かない。本体はトークンを持たない）、0016（最初のデータソース）、`docs/research/2026-10-22-line-messaging-api.md`

## 背景

UBS の LINE 公式アカウントは、将来、利用者の属性でリッチメニューを出し分けたい（直樹）。
利用者は従業員だけでなく、採用前の応募者・顧客・管理物件の入居者もいる。誰が誰かを決める仕組み（LINE の userId と人の紐づけ）は、メニューにも Murmur の名寄せにも効く重要な部分になる。
一方で、Messaging API の Webhook URL は 1 アカウントに 1 つだけで、過去の会話は API で取れない（調べのメモ）。

## 決定

1. **LINE のチャネル（Webhook・シークレット・アクセストークン）は、Murmur の手前に置く別システム（UBS の LINE の受け口）が持つ。** Murmur はその利用者の 1 つ
2. 受け口の仕事: webhook を受けて全部貯める（唯一の原本）、利用者の属性でリッチメニューを出し分ける、LINE の userId と人（従業員・応募者・顧客・入居者）を紐づける、
   ゲートウェイの上流サービスとして送信・プロフィール・履歴の API を出す
3. Murmur は受け口から受信を受け取って Ingest するだけ（`/webhooks/*` に流してもらうか、pull する）。メニューの出し分けや利用者の区分は Murmur に入れない（0008）。
   スタンドが LINE で送るときは、受け口の送信 API をゲートウェイ経由で呼び、そのあと `record_sent` する（0012）
4. **受け口はある程度リッチにして、送信もサポートする（2026-10-22、直樹）。** 管理画面のチャットから返した分は webhook に来ないので、人の返事も受け口から送る形にする。
   受け口は自分が送った分も原本に貯め、Murmur には観測された送信として流す。これで LINE でも H5（観測と記録の統合）が効き、木村さんの返事でボールが相手に移る。
   送信は受け口の仕事で、Murmur 本体には送信の経路を足さない（0012 のまま）

## 帰結

- 受け口を作るまで LINE は取り込めないので、0016 の最初のデータソースは UBS の Outlook にする（軽い。pull で過去の分も取れ、自分の送信も観測できる）
- チーム全体をシミュレートするには LINE と Jira が要るので、Outlook のあと早めに入れる（直樹）
- 受け口は最初は受信を貯めて Murmur に流すだけで始め、送信（人の返事とスタンドの API）、メニュー、ID の紐づけを同じシステムに足していく順が無理がない。送信が入るまでは、管理画面で返した分は手で片付ける
- 人の返事を受け口から送るには、管理画面のチャットに代わる返信の画面が要る。どこまで作るか（返信だけか、チャットの一覧まで持つか）は受け口の設計で決める
- push は月の無料メッセージ数を消費する。reply（webhook の reply token で返す）は消費しないが、使える時間が短い。どちらで返すかも受け口の設計で決める
- リッチメニューの postback（「欠勤連絡」のボタンなど）で種類の付いた連絡が届けば、Ingest が本文から推測する部分が減る。区切りと「求めているか」の判定に効く見込み
- 受け口の利用者の紐づけは、Murmur の Party・Address（LINE の userId）の名寄せの出どころになりうる。どう渡すかは受け口の設計で決める
