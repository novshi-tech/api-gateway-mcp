# 0031 タスクは個人のメモのスレッドで追う。写しは Murmur が決めた小さな形にし、属性はメモだけのものにする

- 状態: 案（2026-11-03、直樹とのディスカッション）
- 関連: 0008（業務の知識を持たない）、0010（黒子。状態は正から片方向に写す）、0013（チームリストを持たない）、0014（スレッド 1 種類。写すか、書くか）、0016 の段取り 2・4（件名、写しが先に届く）、0027・0032（スタンドとエージェントの参加の仕方）、0028（PR をデータソースにする構想）、0030（Contact の解決はクエリ層）、H2、H8、H9

## 背景

属性の扱いを確かめたところ、次のことが分かった。

1. **`AttributeDef` が 2 つの役を兼ねている**: 外のサービスのスレッドの写し（`ThreadMirrored`）と、個人のメモのスレッドに本人が付ける属性（`ThreadAttributeSet`）の、両方の定義になっている。
   計画（`docs/PLAN.md` の AttributeDef の行）は「写しの属性はコネクタが持ち込む」としていたが、実装は写しにも seed の定義を求めている（`src/domain/mirror.ts`）
2. **定義を作る経路が seed しかない**: 実行時に作るデータソース（`ensureNotes`、`POST /data-sources`）には定義が付かない。実データでは、本人も属性を書けず、写しも「定義がない」で弾かれる
3. **写しの意味を誰が決めるのかが決まっていない**: Jira のフィールドは多く、カスタムフィールドもある。全部は写せない。何を写すか・その意味を決めるのは業務の知識で、0008 に照らすと Murmur もコネクタも持つべきでない
4. **スタンドにタスクを任せるときの作業状態**を属性で表したくなる。それには、個人のメモをタスクにどう使うかを先に決める必要がある
5. 0016 の段取り 2（件名を属性として畳む）と 4（写しが課題の作成より先に届く）が残っている。0028 の PR は、ボールを持つ人が 1 人とは限らない（レビュアーと作者）

議論の結論は、写しと属性は「意味を決めるのが誰か」が違う、だった。

| | 写し（外のサービスのスレッド） | 属性（個人のメモのスレッド） |
| --- | --- | --- |
| 意味を決める | Murmur（仕組みに要る分だけ） | 本人とスタンド（業務の意味はスキルの側） |
| 書く | コネクタだけ | 本人とスタンドだけ |
| 語彙 | 決まった小さな形 | 本人が持つ（定義はメモのデータソースに付く） |

## 決定（案）

### 1. 1 タスク = 1 メモスレッド。着手を決めたときにスタンドが作る

- 人が着手を決めたら、スタンドが個人のメモのスレッドを作り（`POST /notes`）、元の共有スレッド（Jira の課題など）と結ぶ（`POST /threads/:id/links`、経路 manual）
- その後の送信（PR を出す、課題にコメントする）は、`record_sent` の `source_thread_id` にメモスレッドを入れる。送ったスレッドとは経路 sent で結ばれ、PR のレビューが返ればメモスレッドの導出したボールに出る。**実装・レビュー・修正のループが 1 本のスレッドに綴じられる**
- 1 タスクが複数の課題にまたがっても、1 つの課題が複数のタスクに分かれてもよい（リンクは多対多）。タスクの親子は持たない
- 完了は片付け（`ThreadDismissed`）で表す。結んだ先が完了しても Murmur はメモスレッドを閉じない（0014）。スタンドが片付けを提案し、人が決める

### 2. 共有スレッドには、事実と構造の操作だけを書く

外のサービスのスレッド（チームで共有するリストも、個人の箱のリストも）に、スタンドが書いてよいのは次のものだけ。

- 送信の記録（`record_sent`。観測で裏付けられる事実）
- 持つ・手放す・引き継ぐ（`ThreadClaimed`。チームに誰の番かを見せる、H8）
- 結ぶ・外す（`ThreadLinked`。着手の手順と、その直し）
- 振り分けの直し（シグナルの移し替え）、片付け・開き直し（人が決めたことの中継）

属性・進捗・作業のメモは共有スレッドに書かない。メモスレッドに書く。外のサービスのスレッドの属性は今もコマンド層が断っている（`setAttribute`）ので、これを原則として明文化する。

### 3. メモのシグナルに書き手の印を足す。番には使わない

- 個人のメモのシグナルに `author` を足す: `{ kind: 'user' }`（人の言葉。スタンドが中継したものを含む）か `{ kind: 'agent', name }`（エージェント自身が書いたもの。`orchestrator`・`codex`・`claude-code` のように、参加者を見分けられる名前）
- 呼び出し元からは判別できない（人の書き込みもスタンド経由で、ゲートウェイの JWT は `sub` だけ）。スタンドの自己申告にする。メモスレッドの読者は本人だけで、守る境界がない
- **誰の番・ボール・可視性には使わない**。メモスレッドのボールは今のまま「本人（とその代理）がやること」で、レビューが返って本人の番になれば、それはエージェントへのきっかけでもある。エージェントがやるか人に回すかはスタンドが決める（0027 の「ボールは本人のまま」）
- 0027 の「エージェントの身元を足さない」は、書き手の印として足すところまで緩める（0032）

### 4. 属性はメモのスレッドだけのもの。標準は `due` だけ

- `AttributeDef` は個人のメモのデータソースだけに付ける。写し（決定 6）は使わない
- `ensureNotes` がメモのデータソースを作るとき、`due`（date、「タスクの期日」）の定義を一緒に作る。既存のメモのデータソースには、マスタの書き換え（0030 の 5）で足す
- 定義を足す・直す・消す API は、要る場面が出るまで作らない
- 委譲中かどうか・作業の段階は属性にしない。タイムラインと書き手の印で読める（オーケストレータはどのみちスレッドを 1 件ずつ読む）

### 5. 一覧の並びは、結んだ先も含めた最終更新の降順

- 一覧（`listThreads`）は、自分の `updatedAt` と、見える結んだ先の `updatedAt` の大きいほうの降順で並べる。クエリ層で計算し、fold は 1 段のまま（0014）。`since` の判定（`movedSince`）と同じ考え方
- 結んだ PR にレビューが返れば、エージェントがメモを書く前でもタスクが上に来る。エージェントが止まっても埋もれない

### 6. 写しは Murmur が決めた形にする

`ThreadMirrored` の `fields`（任意の名前と値）をやめ、次の形にする。どれも省略は「変わっていない」。

| フィールド | 型 | 意味 | Murmur の使い方 |
| --- | --- | --- | --- |
| `closed` | boolean | ソースで完了しているか | ボールを「なし」にする（今の `done`） |
| `holders` | string[] | ソースの上でボールを持っているアカウント（アドレスの値） | 誰の番（今の `assignee` を複数に広げる。Contact への解決はクエリ層、0030） |
| `title` | string | 件名（課題の要約、PR のタイトル） | スレッドの件名 |
| `statusLabel` | string \| null | ソースのステータスの表示名 | 見せるだけ |
| `due` | date \| null | ソースの期日 | 見せるだけ（期限の見回りには使わない） |

- 誰の番は、今の「担当者の写し」の規則を `holders` に広げる: 持ち主（`ThreadClaimed`）＞ `holders` ＞ シグナルのボール。`holders` のうち読者のユーザーがいればその人たちの番、いなければその相手（Contact）
- 優先度・カスタムフィールド・コメント数などは写さない。詳しく見るときは、スタンドがアンカーからゲートウェイ経由でソースを読む

### 7. コネクタは、そのサービスの標準の意味で写す

対応表（どのフィールドが完了・担当にあたるか）をデプロイの設定として持たない。サービスに最初からある概念で決める。

| | `closed` | `holders` | `title` | `statusLabel` | `due` |
| --- | --- | --- | --- | --- | --- |
| Jira の課題 | ステータスカテゴリが done | 担当者 | 要約 | ステータス名 | 期日 |
| PR（0028） | merged か closed（declined） | レビュー待ちなら、まだレビューしていないレビュアー。変更を求められたら作者 | タイトル | open / draft / approved など | なし |

標準の意味で足りない会社が出てきたら、そのときに対応表を足すかを決める。

### 8. 写しにスレッドを作らせる（0016 の段取り 4）

`title` を持つ写しが届き、課題キーのスレッドがまだなければ、写しでスレッドを作る（今は `no_thread` で捨てている）。Webhook の順番が保証されなくても、課題の作成の通知を待たずに済む。シグナルのないスレッドができるが、ボールは `holders` で決まる。

### 9. 件名（0016 の段取り 2）

- 共有スレッドの件名は、写しの `title` があればそれ、なければ Ingest が付けた件名
- 共有スレッドの件名を直す操作は作らない（決定 2）。読みやすい名前で追いたいものは、メモスレッドの件名で付ける

## やらないこと

- **エージェントの番**（メモスレッドの持ち主にエージェントを入れる）: 持ち主の型・`Turn`・API・スキルまで広がり、使い捨てのエージェントを同定する必要が出る。エージェントが返し忘れると、タスクが本人の「自分の番」から消えたまま誰も気づかない。得られる効果（委譲中を一覧から外す、見張る対象を絞る）は、オーケストレータが開いているメモスレッドを全部読むことで代わりがきく
- 任意のフィールドを写すこと、カスタムフィールドの対応表を持つこと
- 属性での絞り込み（要る場面が出てから）
- 写しの `due` で期限の見回りをすること（何を過ぎたら困るかは業務の判断）

## 代案

- **今の形（写しも `AttributeDef` で定義する）**: 何を写し、その意味を誰が決めるかが残る。全部写すと Jira の下位互換に近づく（0013 で退けた部分的なチームリストと同じ）
- **コネクタが定義を持ち込む**（計画の書き方）: カスタムフィールドの意味はコネクタのコードに書けない。結局、テナントごとの対応表が要る
- **作業状態を属性で持つ**（`stage: 未着手 / 委譲中 / 確認待ち / 完了` など）: 語彙をユーザーをまたいで揃える必要があり、Murmur かスキルが業務の段階を決めることになる。完了は片付けで足り、それ以外はタイムラインで読める
- **1 用件 = 1 メモスレッド**（複数のタスクを束ねる）: レビューのループが 1 本に綴じられない（boid の経験）。束ねたければメモスレッド同士を結べばよい

## 帰結

- イベント型が変わる: `ThreadMirrored` を決定 6 の形に、`SignalObserved` に `author`（任意）を足す。CLAUDE.md の約束どおり、zod・fold のテスト・リプレイテスト（H1）を同じ PR で直す。プロトタイプなので古い形を読む互換は持たず、fixture（development の `mirror` の行）と記録を作り直す。実データのデプロイには写しのイベントがまだない
- `comm.ts` の完了の判定（`fields.done`）と `turn.ts` の担当者（`assignee`）を、`closed` と `holders` に置き換える
- `setAttribute` は今のまま（外のサービスのスレッドは断る）。`AttributeDef` の説明と計画の表を「メモのスレッドの属性の定義」に直す
- 一覧の並びが変わる（決定 5）。管理画面とスキルの一覧の説明も合わせる
- メールなど写しを持たないスレッドの件名は Ingest のままで、直せない。一覧の読みやすさは、追うものをメモスレッドに起こすことで補う
- 0016 の段取り 2・4 はこの ADR で置き換える。0014 の未決（件名を属性として畳む）も同じ
- 仮説: H2（状態は属性と導出で足りる）は「メモの属性は `due` だけ、完了は片付け」で確かめる。H9（状態の写し）は決まった形の写しで確かめ直す
- 実装の順: 6・7（写しの形とダミーのコネクタ）→ 8・9 → 3（書き手の印）→ 4（`due` の標準の定義）→ 5（並び）。スキル（`docs/stand/skill-murmur.md`）に 1・2 の手順を書く

## 未決

1. メモスレッドで人が答えるべきもの（最後にエージェントが書き、人がまだ答えていない）を、クエリ層で出すか、スキルで判定するか
2. `record_sent` にも `author` を付けるか（エージェントが PR にコメントしたことを、送ったスレッドの側でも見分けたいか）
3. PR が承認されたあと（マージ待ち）の `holders`。作者とするか、空とするか
4. 写しでできたスレッド（決定 8）に、あとから作成の通知が届いたときの入り方（課題キーのアンカーで同じスレッドに入る見込み。実装で確かめる）
