# 0033 共有リストは共有の状態を持たないデータソースのためにある。リンクは両端を読める人にだけ見せる

- 状態: 採用（2026-11-04、直樹とのディスカッション。共有リスト同士は両方の `ListMember` に入っているときだけ、を直樹が確認）
- 関連: 0012（本体は外に書かない）、0013（チームの共有は既存のツールに任せる）、0014（スレッド 1 種類。H3 のリンクの可視性）、0020・0022（チームの境界を越えるときは要約のレベルを変える）、0024（個人の箱は本人の OAuth）、0030（誰の番はクエリ層で解決する）、0031（写しは決まった形。属性はメモだけ）、H3・H8・H9

## 背景

Jira のコネクタを設計するときに、Jira のプロジェクトを共有リスト（チームの資格情報、読者はチーム）にする前提で考え始めた。そこで次のことに気づいた。

1. **Jira は共有の状態を自分で持っている**: 担当者・ステータス・期日は Jira にあり、Murmur はそれを写すだけ（0010・0031）。誰の番も、担当者の写しが `ThreadClaimed` とほぼ同じ役をしている。Jira を共有リストにしても、Murmur が足せる共有の状態はほとんどない
2. **気軽に個人リストにしたい場面がある**: 自分の担当や見ている課題だけを、自分のリストとして追いたい。客先の Jira にゲストで入っているときのように、チームの資格情報では入れないものもある（0020）
3. **共有リストがいちばん効くのは、共有の状態を持たないデータソース**: LINE 公式アカウントは、チームで共有しているのに区切りも担当もない。Slack や Teams も、話題の区切りが緩く、誰が持っているかを表す場所がない。`ThreadClaimed` と誰の番の判定は、ここで初めて「ほかにない共有の状態」になる
4. **個人リストが増えると、リンクの可視性が問題になる**: 共有リストのスレッドを自分の受信トレイのメールや自分の Jira の課題と結ぶと、ほかの読者には「見えない何かと結んだ」ことだけが見える（今の H3 の挙動）。進みの証拠は個人リストにあり、共有リストからは読めない。受信トレイ（0024 の個人の箱）でも同じことが起きる

## 決定（案）

### 1. リストの性格は「共有の状態をどこが持つか」で決まる

- **データソースが共有の状態を持つ**（Jira・Asana・PR など）: Murmur は索引でよい。**個人リストを既定にする**。本人の資格情報で取り込み、取り込む範囲は本人が決める（Jira なら JQL）。チームの資格情報で共有リストにしてもよいが、既定にはしない
- **データソースが共有の状態を持たない**（LINE 公式アカウント・チャット・共有メールボックス）: 共有リストが共有の状態（持ち主・誰の番・片付け）の置き場になる。Murmur がいちばん価値を出すのはここ

同じ課題やメールが、個人リストの数だけ別のスレッドになることを受け入れる。共有の状態はデータソースの側にあるので、それぞれの写しで足りる。

### 2. Murmur は会話から生まれる最小限の状態だけを持つ

- 持つのは、区切り・ボール・持ち主・片付けと、写しの決まった形（0031）だけ。フィールドを増やしたり、問い合わせの言語を持ったりはしない（0008・0013 のとおり）
- タスクの説明は Notion や Drive などに置き、アンカーとリンクで結ぶ。まとめて見る画面はスタンドが目的に合わせて作る
- 目指すのは、Jira と同じ機能を持つことではない。分散した情報を結んで構造にし、チャットのようなコミュニケーションを構造化すること

### 3. リンクは、両端のスレッドを読める人にだけ見せる

- 「読める」は、そのスレッドのデータソースのリストの読者（`ListMember`）であること（個人のメモは持ち主）。共有リスト同士なら、両方のリストの `ListMember` に入っている人にだけ見える。個人リスト（個人のメモ・個人の資格情報のデータソース）のスレッドとのリンクは、その持ち主にだけ見える
- 片方でも読めないリンクは、リンクがあることも含めて見せない。スレッドのリンクの一覧、詳細の結んだ先、タイムラインの「結んだ・外した」、導出したボール（見えるリンクがなければ「リンクなし」と同じ `null`）のどれにも出さない
- リンクを外す操作も、両端を読める人だけができる（見えない辺は「結んでいない」と同じ扱い）
- リンクを張った事実（`ThreadLinked`）はイベントに残る。見せるかどうかはクエリ層で決める（fold は変えない）
- 運用者の管理画面（`TIMELINE_TOKEN`）は、今までどおりすべて見える

### 4. 共有したい情報は、スタンドが共有のデータソースに書く

- 個人リストで進んだこと（メールで先方に確かめた、Jira で直した）をチームに伝えたいときは、スタンドが共有のデータソースに書く（LINE で返す、Slack のスレッドに書く、課題にコメントする）。本体には `record_sent` で記録する（0012 のまま）
- これは、個人リストと共有リストの間で要約のレベルを変える作業になる。0020・0022 の「チームの境界を越えるときは要約のレベルを変える」と同じ形で、個人とチームの間がいちばん小さな境界になる。何をどの粒度で伝えるかは人とスタンドが決め、Murmur は自動では伝えない

## 代案

- **アンカーで、見る人の写しに読み替える**: リンクの先をソースの識別子（課題キー・Message-ID）でも持ち、見る人が自分の写しを持っていればそれを見せる。漏れはないが、リンクの解決が複雑になる。共有したい情報はデータソースに書けばよいので要らない
- **見えない先の浅い状態だけ見せる**（閉じたか・誰の番か・最終更新）: 結んだ人が同意する前提でも、何を見せてよいかの線引きが要り、件名のように中身に近いものの扱いで迷う。Murmur が要約のレベルを決めることになる
- **今のまま**（リンクは見えて、先の中身だけ隠す）: 「この人がこの件のメモや個人のやりとりを持っている」ことが漏れるうえに、ほかの読者には役に立たない
- **Jira を共有リストにするのを既定にする**: サービスアカウントと管理者の作業が要るわりに、Murmur が足せる共有の状態がない

## 帰結

- H3 の書き方を変える: 「持ち主と、他のスレッドへのリンクは、そのスレッドが見える人に見える（リンク先の中身は見えない）」→「持ち主はそのスレッドが見える人に見える。リンクは両端を読める人にだけ見える」（`docs/PLAN.md` の仮説の表、0014 に注記）
- クエリ層: スレッドの `links`、詳細の `linked`（`visible: false` の行をやめる）、タイムラインの `linked`・`unlinked` を、両端を読める人だけに絞る（`src/domain/visibility.ts`）。導出したボールは、見えるリンクがなければ `null`（`src/domain/turn.ts`）。最終更新・結んだ先が動いたか・結び候補は、もともと見えるスレッドだけで計算している
- 操作: `unlinkThreads` は相手のスレッドも読めることを求める（`src/domain/commands.ts`）
- 投影の要約（`summarizeThread`）と運用者の管理画面は、Viewer を持たないのですべてのリンクを持ったまま
- テスト: 見えないメモへのリンクを `visible: false` で返すことを確かめている箇所を、返さないことに直す（`test/domain/turn.test.ts`・`test/shell/http.test.ts`）。4 シナリオの expected はリンクの見え方を持っていないので変わらない見込み
- スキル: 「共有したい情報は共有のデータソースに書く」を、ゲートウェイの `api-gateway-murmur` のスキルの手順に足す。HTTP API の形は変わらない（返す行が減るだけ）
- Jira のコネクタは、個人リストを既定に設計する（別の ADR に書く）。0024 の個人の箱の経路（本体がゲートウェイの OAuth クライアントになる）に、ゲートウェイの `jira`（3LO）を載せる

## 実装の記録（2026-11-04）

- `visibleLinks`（`src/domain/visibility.ts`）で、スレッドの `links`・詳細の `linked`・タイムラインの `linked` / `unlinked` を絞った。`LinkView.visible` は HTTP API の形を変えないために残し、いつも `true`
- 導出したボールは、見えるリンクがなければ `null`（`src/domain/turn.ts`）。外すのは両端を読める人だけ（`src/domain/commands.ts`）
- シナリオの expected の 3 か所（repair-estimate・development・complaint）が「見えないリンク先の id が見える」ことを確かめていたので、見えないことを確かめる形に反転した。単体テストも同じ。読者の違う共有リスト同士のテストを足した（`test/domain/turn.test.ts`）
- 4 シナリオは expected と一致（`--ai replay`・`--db d1` も）。イベントと fold は変えていないので H1 のリプレイは変わらない

## 未決
