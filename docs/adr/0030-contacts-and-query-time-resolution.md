# 0030 Party を Contact に改める: 組織の概念を外し、読者は User で持ち、名寄せはクエリ層で後から人が付ける

- 状態: 案（2026-10-31、直樹とのディスカッション。方向は合意、実装は未着手）
- 関連: 0003（ゲートウェイから伝搬されるユーザー識別）、0008（業務の知識を持たない）、0013（個人の資格情報は読者 1 人のデータソースだけ）、0014（Murmur は候補を出すだけで、自分では結ばない）、0016 の段取り 1（相手を引く API）、0020・0021（1 デプロイ = 1 チーム）

## 背景

User・Party・Address はマスタで、作る経路は seed しかない。
実際につなぐときは `pnpm seed <scenario> --user u_kimura=<ゲートウェイの User ID>` で、seed の User をゲートウェイの ID に差し替えている。だから直樹が接続すると、seed の「木村」になる。
実データ（0016 の段階 5）では次の 3 つが困る。

1. **メンバーの Party を作れない**: ゲートウェイの JWT は `sub` しか持たない（`src/auth/claims.ts`）。
   `name`・`email` を足すことはできるが、IdP のメールと、Murmur が取り込む箱のアドレス（共有メールボックス・別名・LINE・Slack・Jira のアカウント）は一致しない
2. **外の相手（ゴースト Party）を作れない**: 知らないアドレスのシグナルは `fromPartyId: null` のまま入る
3. **後から付けても過去に効かない**: Ingest と `record_sent` は、取り込んだ時点の Directory で Party を解決して、イベント（`SignalObserved.fromPartyId`・`toPartyIds`）に焼き込んでいる（`src/domain/ingest.ts`・`outbound.ts`）。
   状態の写しの担当者も、写した時点で Party ID にしている（`mirror.ts`）。
   seed の投入では、マスタが変わればイベントは意味を失うとして、イベントごと消している

あわせて、Party の組織の概念（`kind: 'organization'`・`internal`）がどこで使われているかを確かめた。コードはどちらも読んでいない。seed では次の 3 つの役で出てくる。

- 自分のチーム（`internal: true`）: 共有のアドレス（`support@`・LINE 公式アカウント・Jira のサイト）の持ち主。Address は必ずどれかの Party に属するので、データソースの送信元（`selfAddressIds`）と資格情報の `addressId` の置き場になっている。送信か受信かの判定（`isSelfAddress`）はアドレスの値を比べるだけで、この Party は読んでいない
- 外の会社: 代表のアドレス（`ops@`）のゴースト
- ボット: Jira・Bitbucket の通知の送り主のゴースト

Murmur に組織が本当に出てくるのは Party ではなく、チーム（= このデプロイ）のほうだった。ボールの「こちら」（`ball.kind: 'us'`・仕分け待ち）、チームの資格情報（`CredentialRef.principal.kind: 'organization'`）、データソースの窓口のアドレス。
1 デプロイ = 1 チーム（0020）なので、チームはデプロイそのもので、マスタの行として持つ必要がない。

## 考え方

見えるかどうか（リストの読者）は User の話で、名寄せの話ではない。ゴーストが読者になることはないので、読者を Party で持つと誤解の余地が残る。
だから読者は User で持ち、名寄せのエンティティの責務は **名寄せと、ボールがどちらにあるかの判定**（データソースの送信元・宛先・担当者）だけにする。

そうすると、人と組織をまとめる Party という名前（Party パターン）は由来を失う。中身は人のこともあれば、会社の窓口やボットのこともある「アドレスを束ねた、連絡の相手」で、Outlook の連絡先と同じ形をしている。だから **Contact** と呼ぶ。
自分自身も Contact の 1 つで、User に結ばれている。User に結ばれていない Contact がゴースト。

ボールの判定は「そのリストの中で、自分はどのアイデンティティ（アドレス）か」が決まって初めて意味を持つ。
だから自分の Contact は、サインインのときではなく、リストに入るときにそのリストでのアイデンティティと一緒に決める。
名前はサインインのときには要らない。スタンドは、ユーザーをどう呼ぶかをたいてい自分で決めている。

Contact を作るいちばんの動機は名寄せ。名寄せが正確なほど、ほかのリストに入るときの手間が減る。だから、ユーザーは正確なゴーストを作ろうとすると期待できる。
それでも名寄せは間違えるので、まとめる操作と付け替える操作は持つ。

## 決定（案）

### 1. Party を Contact に改め、組織の概念を外す

- `Party` → `Contact`。`partyId` → `contactId`、ボールの `kind: 'party'` → 1 のとおりアドレスで持つ、HTTP API の `to_party_ids` → `to_contact_ids`、属性の型 `party` → `contact`、D1 のマスタの種類も同じく改める
- `Contact = { id, name, userId?, externalRefs }`。`kind`（person / organization）と `internal` は消す。人か会社か窓口かボットかは区別しない（名前でスタンドが分かる）
- 資格情報の主語 `Principal` の `organization` は `team` に改める（このデプロイのチーム。0013 の「共有のデータソースはチームの資格情報」の主語）
- データソースの窓口のアドレスは、データソースの設定として値で持つ: `selfAddressIds` → `selfAddresses: AddressRef[]`、`CredentialRef.addressId` → `address: AddressRef`。チームの Contact は作らない。窓口のアドレスを名寄せしたい人は、ゴーストとして付けてもよい
- 名前を変えるだけの変更を先に独立させて入れ、中身の変更（2 以降）の差分を読みやすくする。HTTP API が変わるので、スキルの API の表も同じ変更で直す（CLAUDE.md）
- 過去の ADR（0013・0014 など）は Party のまま残す。読み替えはこの ADR による

### 2. Contact の解決をクエリ層に寄せる

イベントと投影はアドレスだけを持ち、Contact には直さない。Contact への解決は、クエリ層がそのときのマスタで行う（シグナルの時刻で有効な Address、`validFrom`・`validTo`）。

- `SignalObserved` から `fromPartyId`・`toPartyIds` を外す（古いイベントに残っていても読まない）。`SignalRecord` も同じ
- スレッドのログとボールはアドレスで持つ: `ThreadLogEntry.toPartyIds` → `to`（AddressRef）、ボールの `{ kind: 'party', partyIds }` → `{ kind: 'counterpart', to }`、`Thread.counterpartPartyIds` → `counterparts`（AddressRef）
- クエリ層（`turn.ts`・`visibility.ts`）が、ボールの相手・相手の一覧・宛先による「自分の番」（`addressed`）を、読むたびに Contact に解決する。解決できないアドレスはアドレスのまま返す
- 状態の写しで型が `contact` の属性（担当者）は、ソースのアカウントを AddressRef で写す。Contact への解決と、担当者で決まる「誰の番」（`assigneeTurn`）はクエリ層で行う
- イベントに残る Contact ID（本人が付ける `contact` 属性）は、9 の別名でクエリ層が読み替える。イベントは書き換えない
- 個人のメモの `from` は `{ channel: 'note', value: <User ID> }` にする（4）
- `record_sent` の `to_contact_ids` は、今のとおり入力のときにアドレスに直す。イベントに残すのはアドレスだけ
- Ingest の判断は、もともとアドレスで比べている（区切りの「同じ相手」・`awaitingThread`）。その判断は今のまま `SignalThreaded` に残る
- fold はもともと Directory を読まない。これでイベントもマスタに依存しなくなり、マスタを変えてもイベントを消さずに済む

イベント型が変わるので、CLAUDE.md の約束どおり、zod スキーマ・fold の純関数テスト・リプレイテスト（H1）と fixtures の expected を同じ変更で直す。

### 3. 読者は User で持つ

- `ListMember = { listId, userId }`。見えるかどうかは User で決める（H3）。Viewer は User → ListMember → リストで導出し、Contact を通らない
- Contact と User の結びは `Contact.userId`（1 つの User に Contact は 1 つまで）。使うのはボールの判定だけ
- 「読者が 1 人なら、その人の番」（`turnOf` の reader）は読者の User から決める。宛先による「自分の番」（addressed）は、読者の User → その Contact → アドレスで引く。担当者（`assigneeTurn`）は、担当者のアドレス → Contact → User が読者か、で決める
- Contact をまとめたり、User との結びを外したりしても、見えるものは変わらない
- `seedProblems` の「読者がゴースト」の検査は「読者が User」に置き換わる。個人の資格情報の検査（読者 1 人がその本人）は User で比べる

### 4. 個人のメモは Contact に依存しない

- 個人のメモのデータソースは `ownerUserId` を持つ（`ownerPartyId` をやめる）。読者はその User だけ
- 本人が最初にメモを書くときに作る。Contact がなくても使える。読者は自分ひとりで自明なので、アイデンティティを選ぶ必要がない

### 5. マスタは動かしながら書き換える（イベントにはしない）

Contact・Address・データソース・リスト・ListMember は、動いているデプロイで足したり直したりできるようにする（`MasterStore` に足す。今は丸ごと入れ替える `replaceSeed` だけ）。
2 があるので、マスタの変更をイベントにしなくてもリプレイは決定的なまま（H1）。
ほかはイベントソーシングだが、マスタはその場で書き換えるので、そのままでは履歴が残らない。マスタをイベントにすると、クエリのたびの結合が重すぎる。
だから、誰がいつ何を変えたかを **変更の記録の表 1 つ**（誰・いつ・どのマスタの何を・前の値と後の値）に残す。後から名寄せの間違いを追うため。画面は当面作らない。

マスタの整合性（`seedProblems`）は、変更のたびに同じ規則で確かめる。違反する変更は `conflict` にする。加えて次の 2 つを守る。

- 1 つのアドレスは、ある時点で 1 つの Contact にしか付かない（期間の重なりを禁止する）
- 1 つの User に結ばれる Contact は 1 つだけ

### 6. サインインの直後は、sub だけの名無し

検証済みの `sub` の User がなければ、User の行だけを作る（`id` = `sub`、名前は空）。Contact は作らない。`GET /me` は `contact: null` を返し、読者のリストがなければ見えるものはない（H3）。
管理者は、サインイン済みの User を共有のリストの読者に足せる。
スタンドは、メモを使うか、リストを作るか、リストに入れてもらうように案内する。
JWT に `name` が来るようになっても、使うのは Contact を作るときの名前の初期値だけ。

### 7. 自分の Contact は、リストに入るときに、そのリストでのアイデンティティと一緒に決める

ボールの判定に本人のアドレスが要るリストに入る（ListMember を足す）ときに、そのリストでの本人のアイデンティティ（アドレス）を 1 つ選ぶ。そのアドレスで Contact を次のように決める。

| そのアドレスが付いている Contact | 本人がまだ Contact を持たない | 本人がすでに Contact を持つ |
| --- | --- | --- |
| ない | 新しい Contact を作り、アドレスを付けて sub に結ぶ | 本人の Contact にアドレスを付ける |
| ゴースト（User なし） | そのゴーストを sub に結ぶ。ほかのリストのアドレスも名寄せ済みなら、そのリストに入るときは選ばずに済む | 本人の Contact とゴーストをまとめる候補を出す（9）。まとめるのは確かめてから |
| 別の User の Contact | `conflict`（名寄せの間違いか、アイデンティティの選び間違い。付け替えは 9） | 同じ |

リストの種類ごとの違いは次のとおり。

- **個人のリスト**（個人の資格情報で取るデータソース。0013 で読者は本人だけ）: 本人がスタンドから API で作る（`POST /data-sources`）。
  資格情報は、ゲートウェイの本人の接続を `CredentialRef.gatewayCredentialId` で指す。スタンドはゲートウェイの接続の状態を見られるので、目的のサービスがつながっているかを先に確かめてから作る。選んだアイデンティティが、そのデータソースの送信元（`selfAddresses`）になる。
  個人の資格情報で取るので、そのアドレスが本人のものであることはコネクタで確かめられる（つないだアカウント = そのアドレス）。自己申告にはならないので、ゴーストを sub に結んでも他人を名乗ることにはならない
- **共有のリスト**: 共有のデータソースと ListMember を足すのは、当面は管理者だけ（読者にも許すかは、使ってみてから）。管理者が、User（sub）とそのリストでのアイデンティティを選ぶ。アイデンティティがすでにその人の Contact に名寄せ済みなら選ばずに済む。
  共有メールボックスのように、本人が自分のアドレスでは出てこないリストもある。そのときはアイデンティティを選ばずに入れる（Contact は要らない）

### 8. 名寄せ（ゴースト）は、スタンドが未解決のアドレスを探して付ける

Murmur は Contact を自分で作らず、アドレスを Contact に自動で付けない（0014 の「候補を出すだけ」と同じ）。スタンドが本人と確かめてから付ける。

- `GET /addresses/unresolved`: Viewer が読めるデータソースのシグナルに出てきたアドレスのうち、Contact に解決できないもの。チャネル・値・回数・最後に見た時刻・出てきたスレッドを返す。見えないデータソースの分は出さない（H3）
- `GET /contacts?q=`: Contact と Address を名前やアドレスで引く（0016 の段取り 1 と同じ）
- `POST /contacts`: ゴーストを作る（名前と最初のアドレス）
- `POST /contacts/:id/addresses`: アドレスを付ける。外すのは削除ではなく `validTo` で終わらせる
- `PATCH /contacts/:id`: 名前を直す

書けるのはチームのメンバー（サインインした User）全員。Contact はチームで共有する連絡先だから。
スキルには「未解決のアドレスを見つけたら、`GET /contacts?q=` で候補を出し、本人に確かめてから付ける」と書く。HTTP API の表もスキルに足す。

### 9. 直す操作: まとめる・付け替える・結びを外す

- **まとめる**（`POST /contacts/:id/merge`）: 2 つの Contact を 1 つにする。消える側のアドレスは残る側に移し、消える側の ID は残る側の別名としてマスタに残す。クエリ層は別名を読み替える。イベントは書き換えない。
  両方に User が結ばれているときはまとめない（`conflict`）
- **付け替える**: アドレスを別の Contact に移す。今の付け先を `validTo` で終わらせて、新しい付け先に付ける
- **User との結びを外す**: 見えるものは変わらない（3）。ボールの判定だけが変わる

## やらないこと

- 組織を表すエンティティや、人と会社の所属を持つこと。要るとしたら、チームの外との送り合い（0022）でチームの内か外かを分けたくなったとき（User に結ばれた Contact ならチームの中、とは言える）と、相手の会社ごとにまとめて一覧したくなったとき
- サインインのときに Contact を作ること（そのリストでのアイデンティティが分かるまで、Contact は意味を持たない）
- JWT のメールから Address を作ること（取り込む箱のアドレスと一致する保証がない）
- Ingest のときに、知らないアドレスからゴーストを自動で作ること（名寄せの間違いが、人の確かめなしに広がる）
- 表示名やドメインからの名寄せの推測を本体に持つこと（0008）。候補を出すのはスタンド

## 未決

1. **リストの「こちら」**: 共有のリストで、メンバーが自分のアカウントで書く（Slack のチャネル、Jira のコメント）と、それは観測された送信になる。今は development の seed で、メンバーの Jira のアカウントをデータソースの送信元に入れている。
   「こちら」を「データソースの窓口のアドレス + そのリストでの読者のアイデンティティ」と定義し、ListMember にアイデンティティを持たせる（`{ listId, userId, identity? }`）か。Murmur にサインインしていない同僚の発言は、当面は受信になる
2. **seed の位置づけ**: シナリオとテストでは今のまま使う。実データのデプロイは空で始める。`--user` の差し替えは、シナリオを実環境で回すとき（H7）のためだけに残す

## 帰結

- 先にゴーストとして名寄せされていた人が後からサインインしても、Contact は 2 つにならない。リストに入るときに選んだアイデンティティで、そのゴーストに結ばれる
- 名寄せを後から直すと、過去のスレッドの相手の名前と「誰の番」も直る（いまは取り込み直すしかない）
- クエリのたびに解決するので、一覧の計算が少し重くなる。アドレスから Contact への索引と別名の表を Directory に持てば足りる見込み
- 0016 の段取り 1（相手を引く API）は、この ADR の 8 に含める
- seed（4 シナリオ）の Contact・ListMember・個人のメモのデータソース・窓口のアドレスを書き直す
- 実装の順: 1（名前だけ）→ 2（イベント型）→ 3・4（読者を User に）→ 5 → 6〜9
