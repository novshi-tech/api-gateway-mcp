# 0017 複数の組織にまたがる認証と接続（論点のメモ）

- 状態: **結論が出た（0018、2026-10-22、直樹）: 1 人のユーザが複数の組織にまたがる対応はやらない。組織の切り替えはスタンドで行う。** 以下は 2026-10-21 時点の論点の記録（設計は行わない）
- 関連: 0003（ゲートウェイから伝搬されるユーザー識別）、0006（アカウントリンク・ServiceClient・act-as。設計のみ）、0013（共有のデータソースは組織の資格情報、個人の資格情報は読者 1 人のデータソースだけ）、0016（次の段階。「段階 5 に入る前に決めること」）

## なぜ早めに要るか

直樹は 2 社（UBS: Microsoft Entra、ノブシテック: Google Workspace）を経営し、顧客の環境でも作業する。
ふつうのツールなら後回しにできる「1 人が複数の組織にまたがる」「組織ごとに IdP が違う」が、直樹の使い方では最初から要る（直樹、2026-10-21）。

## いまの構成と穴（2026-10-21 に確かめた）

- Murmur のデータモデルはマルチテナント。Party・Address・イベントはテナントごとで、User は複数のテナントに Party を持てる（Viewer = User → 各テナントの Party → 読者のリスト）
- Murmur の User は、ゲートウェイ（api-gateway-mcp）のサインインの ID と 1 対 1（0003）。Murmur は 1 つのゲートウェイの JWKS だけを信頼する
- **ゲートウェイは 1 つのデプロイに IdP が 1 つ**（`IDP_TYPE` が entra か google。Entra はシングルテナントのアプリ、Google は `ALLOWED_DOMAINS`）。今のデプロイは UBS の Entra
- **ゲートウェイにテナントの概念はない。** 資格情報はサインインしたユーザーごとに登録され、ラベル（urban-b・nvt・quzilla など）で見分けているだけ。組織の資格情報（0013 の約束の前提）を置く場所がない
- Murmur の本体からゲートウェイを呼ぶ経路（0006 の ServiceClient・act-as）がない。取り込みはダミーだけ

結果として、使えるのは「UBS の Entra のアカウントを持つ人と、その人が持つ複数のテナント」まで。
ノブシテックの Google のアカウントだけを持つ人はサインインできない。直樹自身は UBS の Entra でサインインし、ノブシテックのサービスの資格情報も同じ User に登録して使っている。

## 設計で答えること

1. **誰がサインインするか**: 直樹、UBS の社員（Entra）、ノブシテックの社員（Google）、顧客の人。それぞれ、いつ要るか
2. **1 人の複数のアカウントをどう束ねるか**: 直樹の UBS の Entra・ノブシテックの Google・顧客の環境のアカウントを、Murmur の 1 人の User にするか（アカウントリンク）、組織ごとに別の User にするか
3. **顧客の環境はどういう形で入っているか**: 顧客が発行したアカウント（顧客の M365・Google・Slack・Jira）か、自社のアカウントでのゲスト参加（Entra のゲスト・Slack Connect・Jira の外部ユーザー）か。それをテナントにするか、自社のテナントのデータソースにするか
4. **見え方の要件**: 顧客ごとに隔てる必要があるか（顧客 A の環境のデータを、顧客 B の作業者に見せない）。自社の中なら見えてよいか。直樹個人の索引でよいか
5. **資格情報の持ち主**: 個人の資格情報と組織の資格情報を、ゲートウェイのどこに、どのテナントに結びつけて置くか。取り込み（Worker の Cron・Webhook・手元の pull）がどの資格情報で動くか
6. **ゲートウェイの構成**: 候補は次の 3 つ（組み合わせもありうる）
   - 1 つのゲートウェイを複数の IdP に対応させ、アカウントリンク（0006 の 1）を足す
   - 組織ごとにゲートウェイを立て、Murmur が複数の発行者を信頼する（発行者ごとに JWKS とテナントを対応させる）
   - テナントごとに Murmur を分ける

## 制約（これまでの決定）

- 本体は上流のトークンを持たず、外に何も書かない（0012）
- テナント境界は秘匿の境界。生のシグナルも名寄せの知識（Party）もテナントを越えない（設計メモ第 2 回、0013）
- 共有のデータソースは組織の資格情報で取り込む。個人の資格情報は読者 1 人（その本人）のデータソースにしか使わない（0013。`seedProblems` が検査する）
- スタンドはユーザーと同じ権限で働く（Viewer = ゲートウェイから伝搬された User）

## 次の段階（0016）との関係

0016 の段取り 1〜4 は、今の構成（UBS の Entra で直樹と木村さん）でも進められる。段階 5（実データの試用）で取り込みの経路と資格情報を決めるときには、この設計の答えが要る。
→ 答えは 0018。「1 つの接続 = 1 つの組織」を前提に、最初のデータソースの組織とそのゲートウェイを段階 5 の前に決める。
