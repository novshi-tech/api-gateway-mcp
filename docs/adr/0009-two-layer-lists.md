# 0009 リストを 2 層に分ける（会話の層 = データソース、用件の層 = 人とチーム）

- 状態: 提案（2026-10-17、直樹と議論中。データモデルを組み替えるので、ステップ 7 で Google Doc への書き戻しを判断する）
- 関連: 0008（有力案「1 データソース = 1 リスト」の具体化）、0005（ボールの所在、派生を起こすのはスタンド）、H2、H3、H4、H6、H7

## 背景

H7 で absence を実環境で回したところ、s02（伊藤さんの「大丈夫です、入れます！」）を AI が打診のタスクではなく元の欠勤タスクに付けた（confidence 0.6）。
原因は 3 つ重なっていた。

- 外部派生は派生先リスト（`l_dispatch`）にタスクを作るが、返事は LINE 公式アカウント（`@ubs-clean`）に届く。返事の届く受信箱と、打診のタスクのリストがずれている
- AI に渡す候補の履歴はシグナルだけで、送った派生の本文が入らない。打診のタスクは空に見えた
- LINE には返信先のアンカーがない

根にあるのは、今のモデルのタスクが事実上「1 人の相手との会話」になっていること。ボールの所在は 1 か所しか持てないので、相手が増えるたびに派生でタスクが分かれ、
用件（「山本さんの欠勤対応」）は TaskLink の束としてしか存在しない。派生は「リストをまたぐ受け渡し（見える人が変わる）」と「外への送信（組織の外に出る）」の 2 つを兼ねている。

0008 の有力案（リスト = データソース）なら Ingest は業務の知識を要らないが、「私が関心のあるタスク」を一覧する方法がなかった。

## 決定（案）

リストを 2 層に分ける。

| | 会話の層 | 用件の層 |
| --- | --- | --- |
| リストの単位 | データソース（機械的に作る） | 個人（ユーザーごとに 1 つ、自動で作る）とチーム（人が作る。例: 採用、勤怠） |
| メンバー | データソースを読める人（元のサービスの権限を写す） | 個人なら本人、チームなら人が決める |
| タスク | スレッド（シグナルの束） | 用件（人が追うもの。複数のスレッドを束ねる） |
| 持つもの | ボール（こちら / 相手）と、つながった用件 | 状態・カスタム属性・クローズ・導出したボール |
| 決めるもの | Ingest（業務の知識なし） | 昇格のルール、スタンド、人 |

### 会話の層

- データソースの単位: メールはメールボックス（個人で 1 つ、グループごとに 1 つ。だいたい宛先アドレスごと）、Slack・Teams はチャネル、Jira はスペース、LINE は公式アカウント
- 外部の相手（ゴースト Party）はリストのメンバーにせず、スレッドの相手として持つ
- Ingest が判断するのは「同じ会話の続きか、新しい会話か」と「受け手に返事や対応を求めているか」の 2 つだけ。どちらも業務の知識に依らないので、プロンプトを固定できる
- スレッドは open / closed とカスタム属性を持たない。ふだん人が見るのは用件の層なので、状態で絞り込めなくても困らない見込み。
  会話の層で要る一覧は「昇格していなくて、ボールがこちらにあるスレッド」（仕分け待ち）で、ボールと昇格の有無から導出できる
- ignore はなくす。すべてスレッドに記録し、昇格しないものが今の ignore にあたる。CI の成功通知・スタンプ・お礼はボールが動かないので昇格しない。
  H6 で ignore を選ばない問題（業務の知識が要る判断）は、「返事や対応を求めているか」（発話の種類の判断）に言い換わる

### 用件の層と昇格

スレッドを用件につなぐ（昇格する）経路は 3 種類。

1. 業務の知識なしで、Murmur の中で決まるもの
   - ボールが特定のユーザーに来た: 個人のメールボックス・DM なら本人、Slack の @メンションなら言及された人、Jira なら担当者、メンバーが 1 人のリストならその人
   - 用件から送ってできたスレッドは、最初からその用件につながる
   - アンカーの相互参照（Slack の本文の Jira キー、PR の本文の Jira キー、メールの件名のチケット番号）で既存の用件につなぐ。パターンはチャネルの種類で決まる
2. 業務の知識を持つが、データとして登録されているもの（振り分けルール）
   - データソースごとの既定の昇格先（例: LINE 公式アカウント → 勤怠、recruit@ → 採用）と、条件付きのルール
   - ルールはテナントが DB に登録し、Murmur は機械的に実行する。スタンドがパターンに気づいてルールを提案し、人が承認して登録する、という回し方を想定する。
     知識の出どころはスタンドと人のままで、日々の振り分けはスタンドが動いていなくても回る
   - 既定（ルールがないとき）の昇格先は、ボールを持つ人の個人リスト
3. 上で決まらないもの: スタンドか人がつなぐ。間違ったら直せるように、用件の統合・分割の操作が要る

共有メールボックスで宛先が決まらないもの（ボールが「こちら」の誰か決まらない）は、昇格先のチームリストに担当なしで置く。
誰かが返事をするか引き受けたら、その人を担当にする。

用件のボールは、つながったスレッドのボールから導出する（どれかがこちら → 用件の担当、全部が相手待ち → 返事待ち、期限は最も早いもの）。
相手が複数いる用件も 1 つのタスクで表せる。

### 送信と派生

- 送信: 用件から外へ出す。データソースのアドレスから送り、会話の層にスレッドができる（用件につながった状態で）。承認のゲートを通る
- 派生: 用件の層のリストの間の受け渡しだけ。見える人が変わるので要約を渡し、承認を通す
- 0008 の「外部派生の送信元は、派生先リストのデータソースのアドレスにする」は、送信が会話の層で起きることで自然に満たされる。返事は送ったスレッドに戻る

### 可視性

- スレッドの生の中身を見られるのは、会話の層のリスト（データソース）のメンバーだけ
- 用件のリストのメンバーでも、スレッドの元のリストのメンバーでなければ、用件に書かれた要約しか見えない
- 振り分けルールで、元のデータソースを読めない人のいるチームリストへ昇格させるなら、ルールの登録が「このデータソースの中身をこのチームに見せる」ことへの事前の承認にあたる（下の未決 2）

## シナリオへの当てはめ

| シナリオ | 会話の層 | 用件の層 | 確かめること |
| --- | --- | --- | --- |
| absence | LINE 公式アカウント（メンバーは木村） | 勤怠（チーム） | 伊藤さんへの打診は用件から送り、伊藤さんとのスレッドができる。返事は「伊藤さんの返事待ちのスレッド」に付くので、s02 の取り違えは構造上起きない。遅刻とスタンプは昇格しない |
| repair-estimate | support@（組織）、鈴木の個人メールボックス（今の資格情報 2 つと一致） | 佐藤の用件 → 派生 → 工事部の用件 | 協力会社の生のメールを佐藤が見ない境界は、鈴木のメールボックスのメンバーが鈴木だけであることで守られる |
| complaint | support@ | 顧客対応 → 清掃管理 → 協力会社 | 同上。期限超過は用件のボールの導出で出る |
| development | Slack のチャネルごと、Jira のスペース、Bitbucket | 能勢・加藤の個人、開発（チーム） | Jira キーと PR 番号で、Slack のスレッド・課題・PR が 1 つの用件にまとまる |

## 未決

1. 振り分けルールの条件の書き方。構造の条件（データソース、宛先アドレス、送り主の Party・ドメイン、件名のパターン）だけにするか、
   自然文の条件（「求人への応募」）を固定のプロンプトの AI に評価させるか。後者は知識がデータにありプロンプトは固定だが、精度がルールの書き方しだいで、誤りが境界の問題になる
2. 振り分けルールによる昇格が可視性を広げるときの扱い。ルールを登録できるのは元のデータソースのメンバーに限るか、
   チームリストのメンバーが元のリストのメンバーでなければ要約だけにするか（計画の「AI のリスク判断による自動承認」の議論と同じ線上にある）
3. 終わらない会話の区切り。LINE の 1:1 やメールの同じ相手は、会話がずっと続く。用件を閉じたあとに同じ相手から来た連絡を、
   続き（用件を開き直す）とするか新しいスレッドとするか
4. 用件の統合・分割、スレッドの付け替えの操作とイベント
5. Jira の課題のように、元のサービスの側がすでに用件の性格を持つものと、Murmur の用件の重複
6. イベントと投影の組み替え。Task・TaskLink・Derivation・IngestDecided、ボールの導出、H4・H6 の測り方、4 シナリオの fixtures の作り直し。
   どの順で、どこまでをプロトタイプで確かめるか

## 影響

- 計画のデータモデルと Ingest パイプラインを組み替える。PLAN.md と Google Doc の書き直しが要る
- H7 は、この形が固まるまで止める。absence は s02 まで回したところで止めた（dev の DB には s02 が欠勤タスクに付いた状態が残っている）
- 今日入れた修正（返事期待の期限を UTC にそろえる、訂正で打診の適用先に付けたら返事として紐づける）は、今のモデルのバグの修正なので残す

## 代案

- 1 層のまま、リスト = データソースにし、「私のタスク」はボールを持つ人でリストを横断して検索する（思考実験）。
  用件をまとめられず（Jira の課題と Slack のスレッドが別々に出る）、カスタム属性の置き場もない
- 1 層のまま今の形（リストを業務で設計し、Ingest の Claude がリストの説明を読んで置く）。0008 の問題（業務の知識が Ingest に入る、置き間違いが境界を破る）が残る
- 同じタスクから外へ送る操作だけを足す（今日の議論の案 C）。absence は 1 タスクで済むが、Ingest の置き先の問題（0008）と「私のタスク」の問題は残る
