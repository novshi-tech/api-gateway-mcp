# 0007 上流の API を MCP のツールからも呼べるようにする

- 状態: 採用(2026-11-07、直樹とのディスカッション)。同じ日に実装した
- 関連: [concept.md](../concept.md)(「全体像」と「採用しなかった案」)、[0005](0005-murmur-as-a-feature.md)(決定 3「MCP のツールは 2 つのまま」を改める)

## 背景

これまで、上流の API はすべて「`issue_token` でトークンを受け取り、サンドボックスのスクリプトから REST を呼ぶ」形で呼んでいた。一覧の全件取得やファイルの受け渡しにはこれが合っているが、1 件の取得や 1 回の登録のような小さい呼び出しでも、毎回コード実行の環境を立ち上げて、トークンを環境変数に入れてスクリプトを書く手間がかかり、遅い。

また、Team / Enterprise の Cowork では、サンドボックスから外への通信を組織の管理者が許可しないと、ゲートウェイに届かない。

## 決定

1. **MCP のツールを 2 つ足す。** `api_get`(GET)と `api_request`(POST・PUT・PATCH・DELETE)。引数は認証情報の ID・上流のパス・クエリ・ヘッダー・ボディ(`json` か `text`)・返すボディの長さの上限(`max_chars`)。サービスは認証情報の ID から決まる
2. **読み取りと書き込みでツールを分ける。** `api_get` は `readOnlyHint: true` で、クライアントは確認なしで呼べる。`api_request` は `destructiveHint: true` で、呼ぶたびにユーザーの確認を求められる。1 つのツールにまとめると、読み取りまで毎回確認が出るか、「常に許可」で書き込みまで素通りになる。メソッドごとに分けても、確認の扱いは 2 通りしかないので意味がない
   - GraphQL の query や検索の API のように、読み取りでも POST のものは `api_request` で呼ぶ(確認が出る)。特別扱いはしない
3. **中身は REST の中継と同じ道を通る。** ツールは寿命 60 秒のゲートウェイのトークンを自分で作り、`/api/<service>/...` と同じリクエストを組み立てて中継(`handleProxy`)に渡す。認証情報の注入・更新、機能(Murmur)への振り分け、操作ログは REST と同じ。操作ログには入口(`via`: `rest` か `mcp`)を足した
   - パスは URL として解決したあとで `/api/<service>` の下にあることを確かめる(`..` やそのエンコードで別のサービスに出られない)
4. **会話に返すのはテキストだけ。** ツールの結果は会話に入るので、
   - ボディは JSON なら詰めて返し、`max_chars`(既定 5 万文字、最大 10 万文字)を超えたら切り詰めて `truncated` を付ける
   - バイナリ(PDF・画像などテキストでない Content-Type、または UTF-8 として読めないもの)は返さず、スクリプトで扱うよう案内する。「ファイル本体は会話を通さない」は変えない
   - リダイレクトは追わずに、ステータスと `Location` を返す
   - 上流が 400 以上を返したら、ツールの結果をエラーにする(ボディは返す)
5. **スクリプトの道は残す。** 大量の呼び出し、全件取得や集計、ファイルの受け渡しは、これまでどおり `issue_token` とスクリプトで行う。使い分けは `heddleway` スキルに書く

## 採用しなかった案

| 案 | 理由 |
|---|---|
| 1 つのツールで全メソッドを扱う | 上の決定 2。読み取りの確認をなくせない |
| メソッドごとに 1 つずつ(5 つ) | 確認の扱いは読み取りと書き込みの 2 通りしかなく、ツールが増えるだけ |
| ツールの中で `forward` を直接呼ぶ(トークンを作らない) | 機能(Murmur)はトークンを口でもう一度確かめるので、別の道が要る。トークンの署名と検証は軽いので、同じ道を通すほうが単純 |
| サービスの API 仕様からツールを作る | concept.md で Code Mode や Executor を採らなかったのと同じ理由。ゲートウェイは API の仕様を知らない素通しの中継のままにする |

## 影響

- Team / Enterprise でサンドボックスの外への通信が許可されていなくても、MCP のツールで読み書きできる(ファイルと大量のデータはスクリプトが要る)
- 上流の応答が会話に入る量が増える。切り詰めの上限と、スキルの使い分けで抑える
