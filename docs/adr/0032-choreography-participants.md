# 0032 エージェントの参加の仕方は 2 つ: オーケストレータの下で動くか、メモスレッドに直接参加するか（0027 を改める）

- 状態: 採用（2026-11-03、直樹とのディスカッション）。0027 を改める。Murmur の本体への影響は 0031 の書き手の印だけ
- 関連: 0027（オーケストレータのスタンド）、0031（タスクのメモスレッド・書き手の印）、0008（判断と文章はスタンド）、0012（本体は外に書かない）、0013（購読を持たない）、0014（個人のメモ）、H7、H8

## 背景

0027 は、オーケストレータが実行のスタンド（boid の job など）を束ね、実行のスタンドは Murmur を読み書きしない形にした。代案の「実行のスタンドが直接 Murmur を読み書きする」は、スタンドごとに Murmur の接続とスキルが要るとして採らなかった。

0031 で 1 タスク = 1 メモスレッドにしたあと、次の 2 つの場面を考えた。

1. **boid を使わないとき**: オーケストレータはクラウドセッションで別のセッションを起こすことになる。セッションの状態は見られる（セッションの API）が、オーケストレータもそのツールを持つ場所で動いている必要がある。それより、サブエージェントで済ませたほうが簡単
2. **boid を使わない人が Codex に PR をレビューさせるとき**: Codex が PR を見張り、メモスレッドで意図と経緯を読みながら PR にコメントする。オーケストレータを介さない。メモを Codex と共有できること自体に価値がある（PR の説明より文脈が厚い）

2 は 0027 で退けた代案にあたる。ただ、0027 の制約の中身は「Murmur に触れない」ではなく、**オーケストレータの管理下にあるエージェントが直接書かないほうが、責務の分担としてきれい**ということだった。boid の job にしても、Murmur は見えている。

## 決定（案）

### 1. 次の一手を決める者が書く

Murmur のメモスレッドに書くのは、次の一手を自分で決める参加者だけ。決めない参加者は結果を返すだけにする。

| 参加の仕方 | 例 | Murmur とのかかわり |
| --- | --- | --- |
| **オーケストレータの下で動く**（オーケストレーション） | boid の job、サブエージェント、オーケストレータが起こした別セッション | 書かない（読むのはかまわない）。結果をオーケストレータに返し、オーケストレータが judge してメモスレッドに綴じる |
| **直接の参加者**（コレオグラフィ） | オーケストレータ自身、PR を見張ってレビューする Codex | 自分のきっかけで読み書きする。書き手の印（0031 の 3）を付ける |

オーケストレータは、直接の参加者の 1 人という扱いになる。0027 の「実行のスタンドは Murmur を知らない」は、つながれないからではなく、責務を分けるための約束として読み直す。

### 2. メモスレッドがタスクの黒板で、ループの状態を持つ

- タスクの経過（指示・結果・judge・人のフィードバック・レビュー）はメモスレッドに綴じる（0031 の 1）。0027 の未決 1（人がいないときの質問の置き場）と未決 2（実行の結果の綴じ先）は、どちらもメモスレッドに決まる
- 状態がメモスレッドにあるので、実行する側を長生きさせなくてよい。オーケストレータは、きっかけ（人がメモを書いた・結んだ先が動いた・実行が終わった）のたびに起こし直せばよく、メモスレッドを読めば続きができる

### 3. boid を使わないときは、サブエージェントを基本にする

- 1 回分の作業（実装・修正・レビュー対応）はサブエージェントで済ませ、結果をオーケストレータが綴じて終わる
- 別のセッションを起こすのは、別のリポジトリや環境が要るとき、並列で走らせたいとき、1 回の起動に収まらない長い作業のときだけ

### 4. 直接の参加者の約束（スキルに書く。Murmur は持たない）

- 書いたものに書き手の印を付ける。参加者は互いの書き込みを読んで反応する
- 外に送ったもの（PR へのコメント）は `record_sent` で記録し、`source_thread_id` にメモスレッドを入れる（0031 の 1）
- ループの止め方を決めておく（例: レビューと修正が何周したら人に回す、承認したら止まる）。参加者が互いに反応し続けないようにする
- きっかけは、Murmur をポーリングする（`since`）か、外のサービスのきっかけ（PR のイベントなど）で受ける。Murmur は参加者に通知しない（購読を持たない、0013）

### 5. 共有できるのは本人のエージェントまで

メモスレッドの読者は本人だけ（0014）。直接の参加者は本人の代理（本人の接続でゲートウェイを通る）に限られる。チームの別の人やそのエージェントがレビューするときは、メモは見えない。その人に渡すものは、外のサービス（PR・課題）に書く。

### 6. 0027 のうち変わらないもの

- ボールは本人のまま。スタンドは本人の代理で、エージェントの番は持たない（0031 のやらないこと）
- 外に送ったものは、送ったスタンドが `record_sent` で記録する（0012）
- オーケストレータは新しいプロダクトではなく、スキルで実現する

## 本体への影響

- 0031 の書き手の印（`SignalObserved.author`）だけ。ほかは変えない
- スキル（`docs/stand/skill-murmur.md`）に、参加の 2 つの形と決定 4 の約束を書く

## 代案

- **すべてオーケストレータを介す（0027 のまま）**: Codex のように、別のハーネスで自分のきっかけで動く参加者を、オーケストレータの下に組み込む必要がある。メモを直接読めないと、レビューにタスクの文脈が渡らない
- **実行のエージェントも全員直接書く**: 誰が次の一手を決めたのかが散り、judge が二重になる。オーケストレータの下では、書くのはオーケストレータ 1 か所にまとめる
- **boid を使わないときも別セッションを基本にする**: オーケストレータがセッションを見張るツールを持つ場所に縛られ、セッションの状態とメモスレッドの状態が二重になる

## 帰結

- 0027 の状態を「0032 で改めた」にし、代案の「実行のスタンドが直接 Murmur を読み書きする」は、直接の参加者としてなら採る、と読み替える
- Codex など Claude 以外の参加者は、ゲートウェイの MCP（またはその REST）で Murmur に届く必要がある。接続の手順（`docs/stand/connect.md`）とスキルを、そのハーネス向けにも用意する
