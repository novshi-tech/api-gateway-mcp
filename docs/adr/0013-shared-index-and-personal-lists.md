# 0013 チームの共有は既存のツールに任せる。Murmur は、テナントで共有する外部リストと、各自のマイリストになる

- 状態: 採用。**同日の 2026-10-20 に `docs/adr/0014` で一部を置き換えた**: 2 層の構成（2）・つなぎ（5）・fold の依存（4）・言葉（8）は 0014 のとおり（エンティティはスレッドの 1 種類、マイリスト・用件は個人のメモのデータソースのスレッド、結ぶのは人とスタンド）。チームの共有は既存のツール（1）、持ち主とリンクは共有の層の事実（3）、権限（6）、外すもの（7）はそのまま生きる。未決 2 は 0014 で解消。
  **2026-10-23: 0020・0021 で 1 デプロイ = 1 チームにし、マルチテナントの概念を外す方向にした。この ADR の「テナント」は「デプロイ（チーム）」と読む（テナント境界は秘匿の境界 → デプロイの境界は秘匿の境界）**
- 関連: 0009（2 層のリスト。用件の層をここで作り直す。会話の層は残る）、0010（黒子）、0012（判断の台帳、外には書かない。定義文を書き直す）、0008（業務の知識を持たない）、
  boid の card と identity 索引（0012「boid からの系譜」）

## 背景

計画 v2 を直樹がレビューし、「設計が煮詰まっていない。このままでは実装に進みたいと思えない」と止めた。違和感の出どころは次のとおり。

- リストを 2 層に分けたことで複雑になり、汎用性が落ちている。会話の層と用件の層の分け方も恣意的で、実態と合っていない。
  Jira にもコメント（会話）はあり、メールにもスレッド（用件のまとまり）はあり、Gmail のスターはスレッドに付く属性にあたる。
  ソースごとに持てる範囲は違っても、**用件は時系列のイベントと属性のかたまり**という概念はどのソースでも同じ。0009 の表は「層 = ソースの種類」になっていて、Jira だけ会話の層を飛ばして用件の層に直結させているのが、層の定義が破れている証拠
- 黒子（0010）と「外には何も書かない」（0012）を決めた時点で、「チームリスト」の役割は既存のデータソース（Jira、グループメール、Slack）が引き続き担えるようになっていた。
  だが 0009 のチームリスト・購読・派生の一式は、その前提で見直されていなかった。特に派生（用件のリスト間の受け渡し）は、本体が送らないと決めた後では「内部版の送信」で、
  スタンドが外のチャネルで渡して `record_sent` するのと二重になっている
- こう整理すると、Murmur は boid の自然な延長で、各自のタスク管理をすればよい。boid との差分は、要約レベルの違い（LINE の生の会話と Jira の課題）とツールの垣根を越える役割を持たせるところ

一番難しいのは LINE 公式アカウントのようなソース。メタデータが少なく「誰宛」がなく、読者が複数いるので、誰がボールを持つのかが最初は決まらない。
チームで共有したければ Jira に起票することになるが、「誰がそのリンクを作るのか」が決まらないと、皆が LINE の用件を Jira にミラーして同じチケットが沢山できる。
「LINE だけ Murmur 内のチームリストを正にする」案は、チーム内の共有としては Jira より機能が限られ、Jira の下位互換を作ることになる。

## 決定

### 1. チームの共有は既存のツールに任せる

- Murmur はチームリストを持たない。人と人の間の共有は、データソース（Jira、グループメール、Slack のチャネル）の側で行う。
  既存のツールに「特定の境界の中のビュー」の役割を負わせる（チームの課題はすべて Jira で見る、など）
- 受け皿のないソース（LINE の勤怠連絡、メールの問い合わせ）に来た用件をチームで共有したければ、誰かがスタンド経由で外の受け皿（Jira など）に起票し、`record_sent` で記録する。
  これは「送ったら記録する」（0012）と同じ種類の運用の約束で、守られているかは同じやり方で測る（外の受け皿へのリンクのない課題の件数、誰も拾わないまま古くなったスレッドの件数。0007 の試用で）
- 0010 の代案「完全な黒子: 受け皿のない用件を置く場所がない」への答えは、「置く場所は各自のマイリストだけ。チームで持ちたければ外に受け皿を作る」

### 2. 構成: テナントで共有する外部リスト（ソースのミラー）と、各自のマイリスト

層は 2 つのまま。変わるのは 2 層目の中身で、「チームと振り分け」ではなく「各自のもの」だけになる。

| | 外部リスト（共有の層） | マイリスト（個人の層） |
| --- | --- | --- |
| 単位 | データソースごとに 1 つ。テナントで 1 つの共有の実体（人ごとのコピーは作らない） | ユーザーごとに 1 つ |
| 見える人 | そのデータソースを読める人（取り込みの設定で決まる。0009 の会話の層のメンバーと同じ） | 本人だけ。ただし持ち主と外へのリンクは共有の層にある（下の 3） |
| 中身 | スレッド。ソース固有の粒度（メールのスレッド、Slack のスレッド、Jira の課題、LINE の区切り）と、ソースが持つ属性の写し（ステータス・担当者・スター） | 項目。複数のスレッドを参照して 1 つの用件にまとめる |
| 持つもの | シグナルの列、ボール（こちら / 特定のユーザー / 相手 / なし）、アンカー（外の受け皿へのリンクを含む）、持ち主、片付け、属性の写し | 自前の open / closed、カスタム属性、メモ、スタンドとのやりとり（前回見てからの差分、決めたこと）、参照するスレッド、導出したボール |
| 決めるもの | Ingest（区切り、返事や対応を求めているか。業務の知識なし）、人とスタンドの操作（持ち主、片付け、移し替え） | 本人とスタンド |

- 「外部リスト」は 0009 の「外部のリスト」（元のサービスのプロジェクトを用件の層のリストとしてつなぐ）とは別物。0013 以降は、データソースの写し全部を外部リストと呼ぶ
- 元のサービスの側が用件の粒度を持つもの（Jira の課題、bm-next の業務）は、**会話の層を飛ばす 0009 の「外部のリスト」ではなく、粒度を元から持つデータソース**として外部リストに入る。
  1 課題 = 1 スレッド、状態の写し（0010 の `MatterMirrored`）はスレッドの属性になる。正はそのサービス（0010）のまま
- 区切りのないソース（LINE の 1:1、Slack のチャネル直下、返信でないメール）に粒度を与えるのが Ingest の仕事で、0009 の会話の層と計画 v2 のステップ 2 のまま
- 1 本のスレッドを参照できる項目は、1 人のマイリストの中では多くても 1 つ。別の人の項目が同じスレッドを参照するのはよい（木村は代務の手配、事務は bm-next への登録、のように同じ連絡を別の仕事として追う）
- **「自分に関連する」ビュー**: 共有の層の投影に対するクエリ層の純関数。宛先・CC・@メンション・Jira の担当者と報告者・スレッドの参加者・読者が 1 人のソース・持ち主。
  自然文の条件は持ち込まない（持ち込んだ瞬間に購読が戻ってくる入り口になる）

### 3. 持ち主と外の受け皿へのリンクは、共有の層の事実

- **持ち主**: 共有のスレッドに付くイベント `ThreadClaimed { threadId, userId | null, by, reason }`。ボールを「特定のユーザー」へ明示の操作で動かす。null で手放す、別の人で引き継ぐ。
  0009 のスレッドのボールにある「特定のユーザー」を、宛先や @メンションからの導出だけでなく、操作でも動かせるようにしただけ。
  LINE 公式に「誰宛」がない問題への答えは、ボールを人に付ける操作そのもの。Jira の「自分に割り当て」、Front や HelpScout の assign にあたる、共有受信箱に要る唯一のチーム機能
- **外の受け皿へのリンク**: `record_sent` の `sent_ref`（Jira の課題キーなど）がスレッドのアンカーになる。リンクを作るのは起票した人で、起票の副作用として付くので、別の手間として割り振らない。
  起票の前にスタンドが共有のスレッドを見れば、もう誰かが持っていてリンクも付いていると分かるので、同じチケットは増えにくい
- どちらも**マイリストから導出しない**。共有の層は個人の層の存在を知らない。「これを自分で持つ」というスタンドの操作は、シェルが `ThreadClaimed` の追記とマイリストの項目の作成を並べて呼ぶだけで、コアの中ではつながっていない。
  持つけどマイリストには入れない、マイリストに入れるが持ち主は別の人、も表せる
- 「対応済みか」も項目の開閉から導出しない。共有の層で分かるのは、ボールが相手に移ったか、片付けたか、だけ。電話で済ませて LINE では返事しなかった、は `ThreadDismissed` に理由を残す（0012「Murmur が判断するのはボールが動いたかだけ」）

### 4. fold の依存の向き

- 共有の層の fold は、共有の層のイベントだけ読む
- マイリストの fold の入力は、**自分の層のイベント + 共有の層の投影**。共有の層のイベントそのものは読まない。読むのはスレッドの投影の、ボール、`reply_expected_by` と overdue、`last_inbound_at` / `last_outbound_at`、アンカー。
  項目の導出したボール（参照するスレッドのどれかがこちら → 担当、全部が相手待ち → 返事待ち、期限は最も早いもの）はここから出る（0009 の用件のボールの導出と同じ）
- 項目のタイムライン（参照するスレッドのシグナルと、項目のイベントとメモを時刻順に並べ、`since` で絞る）は投影として持たず、クエリ層で 2 つの投影を合わせて作る
- H1（決定性）は 2 段で確かめる。共有の層を先に畳み、その投影を渡して自分の層を畳む。全部をイベントから作り直して同じ結果になること

### 5. 項目にスレッドをつなぐ（0009 の昇格の後継）

上から順に当てる。購読（0009 の 2）がなくなる。

1. 項目から送ってできたスレッドは、最初からその項目を参照している（経路 sent）
2. ボールが特定のユーザーに来た（個人のメールボックス・DM なら本人、@メンションなら言及された人、Jira なら担当者、読者が 1 人のソースならその人、`ThreadClaimed` で持った人）
   → その人のマイリストに項目を作る（経路 ball）。0012「誰も見ていない夜中に届いたメールも、朝には用件になっていなければならない」はこれで満たす
3. アンカーの相互参照（Jira キー・PR 番号・チケット番号・`sent_ref`）で、その人の既存の項目が見つかった → つなぐ（経路 anchor）
4. どれでもない → データソースの仕分け待ち（ボールが「こちら」= 組織のまま、持ち主なし。そのデータソースの読者に見える）。人かスタンドが持つか、片付ける

直す操作（シグナルの移し替え、項目へのつなぎ替え、項目の統合、片付け）は 0009 のまま。項目の分割は、新しい項目を作ってスレッドの参照を付け替える。

### 6. 権限

- 共有の実体の可視性は「そのデータソースを読める人」で決まり、誰が読めるかは取り込みの設定（資格情報が組織のものか個人のものか、読者を誰にするか）で決まる。モデルに新しい権限の仕組みは要らない
- 約束: **共有のデータソースは組織の資格情報で取り込む。個人の資格情報は読者 1 人のデータソースにしか使わない**。0007 の実データの試用（個人の Gmail 1 つ）はこれと矛盾しない
- 既知の単純化: Jira のプロジェクトを「読者 = プロジェクトのメンバー」で共有すると、人ごとの課題の権限差は写らない。プロトタイプでは扱わない

### 7. 外すもの

| 外すもの | 理由 |
| --- | --- |
| チームリスト、リストの種類 team / external | チームの共有は既存のツール。Jira はデータソース |
| Subscription（購読）と、自然文の条件の分類器 | 振り分けは持ち主の操作と構造の導出で足りる。Claude の呼び出しは Ingest の 1 か所だけになる |
| 派生（DerivationProposed / Approved / Rejected / Replied）と、本体の承認 | 受け渡しは外のチャネルで送って `record_sent`。本体に承認を要するものが残らない |
| `MatterMirrored` | スレッドの属性の写しになる（名前は実装時に決める） |
| H8（購読だけで振り分けが回る） | 購読がない。代わりに「構造だけで『自分に関連する』と持ち主が決まる」ことと、起票の運用の約束の指標を見る |

残るもの: 0012 の「綴じる 3 種類」（観測・行動・メモ）、`record_sent` と `OutboundRecorded`、観測された送信の統合（H5）、期限の見回り、`MatterNoted`、`MatterMerged`（項目の統合）、直す操作。

### 8. 言葉: 「外部リスト」と「マイリスト」。何であるかの名詞は立てない

- 2 層の名前は**外部リスト**（データソースの写し。テナントで共有）と**マイリスト**（各自の用件・メモ・属性）。機能を名前に込めすぎると収拾がつかなくなるので、平易な語にとどめる（直樹、2026-10-20）
- 「共有の台帳」（0012）が合わなくなった理由は、共有されるものと個人のものが分かれたから。人と人の共有の役割は既存のデータソースに残り、Murmur の中で共有されるのは外部リスト（連絡の記録と、スレッド・用件・外の受け皿のキー・持ち主の対応づけ）だけ。
  これは boid の identity 索引（外部キー → task、多対一）をテナント全員で持つ形。マイリストは boid の card
- Murmur が何であるかは名詞を立てず、何をするか（連絡から対応の要る用件を抽出し、その経過を追跡する）と何から成るか（外部リストとマイリスト）で書く。0012 の定義文と `CLAUDE.md` の冒頭はそう書き直した
- boid との差分は、要約レベルの違い（LINE の生の会話と Jira の課題）とツールの垣根を越えて同じ用件を結び、どちらからも辿れるようにする外部リストの側の役割。要約を書くのはスタンド（0008）で、Murmur は両方のレベルを 1 か所から届くようにする
- 名前の良さの基準: 0012 の「スタンドが聞く 4 つ」。「ボールがこちらにある自分の用件」「この相手との開いている用件」は外部リストへの問い、「前回見てから何があったか」「以前何を決めたか」はマイリストへの問い
- コードの `List.kind` は `external` / `personal`

## 代案

- **0009 のまま（チームリスト + 購読 + 派生）**: 黒子と「外には書かない」の後では派生が送信と二重になり、購読の条件に業務の知識がデータとして入り、分類器の Claude 呼び出しが残る
- **部分的なチームリスト（LINE だけ Murmur 内を正にする）**: チーム内の共有として Jira より機能が限られ、属性と状態のワークフローを持ち始めた瞬間に Jira の下位互換になる。Murmur が正なのは「LINE 側の会話とそのボール」だけでよい（0010）
- **人ごとにミラーのコピーを持つ（メモの時点のイメージ）**: 同じ Jira 課題や LINE のスレッドが人数分に割れ、アンカーも持ち主も分かれて、起票前に「もう誰かが持っている」と分からない。コピーの問題のほうが権限の問題より深刻。「自分に関連する部分」は共有の実体の上の絞り込みで作る
- **持ち主をマイリストの項目から導出する**: 下の層が上の層を読むことになり、層の依存が逆転する。共有の層の事実（`ThreadClaimed`）として直接記録する

## 影響（計画 v2 と `CLAUDE.md` に 2026-10-20 に反映した）

- **ステップ 2（会話の層）は無傷**。DataSource、スレッド、区切り、「返事や対応を求めているか」、片付け、移し替えはそのまま
- **ステップ 3** は「マイリスト、`ThreadClaimed`、『自分に関連する』ビュー、項目へのつなぎ（上の 5）、項目のボールの導出、統合、メモ」。チームリスト・購読・H8 が落ちる
- **ステップ 4** は `record_sent`・期限の見回り・観測された送信の統合だけ。派生の 4 イベントが落ちる
- **ステップ 5（API）**: `propose_derivation` / `list_proposals` / `approve` / `reject` / `reply_derivation` / `register_subscription` / `list_subscriptions` が消え、`claim_thread`（手放す・引き継ぐも）と「自分に関連する」一覧が入る。スキルの API 表も直す
- **ステップ 7**: Jira は属性の写しを持つデータソース。起票は `record_sent` でリンクが付く
- **仮説**: H2（項目の状態は自前の open / closed と属性、ボールは参照するスレッドから導出）、H3（可視性はソースの読者と本人のマイリストだけ。持ち主とリンクはソースの読者に見える）、
  H4（記録 → 返事が送ったスレッドに戻る → 期限超過。`ThreadClaimed` でボールが人に移る）、H8（構造だけで『自分に関連する』と持ち主が決まる。自然文の条件なし）、H9（Jira はデータソース、起票のリンク）を書き直す。
  H1 は 2 段のリプレイ。0010 で挙げた三つめの価値「境界で守る」は、ソースの権限を写すだけになるので小さくなる。これは認める
- **0009**: 用件の層はここで作り直し。会話の層はそのまま。**0012**: 未決 1（チームの用件への自分だけのメモ）は、共有のスレッドを参照する自分の項目がそれにあたるので解消。定義文を書き直した
- **CLAUDE.md**: 冒頭と「約束事」（チームリスト・購読・派生を足さない、fold の依存は一方向）を直した
