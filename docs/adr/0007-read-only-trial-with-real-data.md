# 0007 実データでの試用は読み取り専用のコネクタで、Ingest から始める

- 状態: 採用（2026-10-16、方針。下の「量の見通し」の対応は未着手）
- 関連: H6、H7、0008（新規シグナルの置き先の未決。この試用で材料を取る）、計画「スコープ外: 本物のコネクタ（メール・Slack・LINE・Jira・Bitbucket）とその OAuth 設定」、0004、0005

## 背景

H6 の一致率（全体 91.7%、AI のみ 85.7%）は、Claude が作ったシナリオに対する数字。
実データのシグナルで、外側のタスクを識別して追えるかは確かめていない。また H6 の記録では AI が ignore を一度も選ばず、
閾値やプロンプトを詰める材料（実データでの判断と、その訂正）がない。

このプロトタイプは捨てずに次へ進める前提で、段階的に進めている。計画は本物のコネクタをスコープ外にしているが、それは外部接続なしで
データモデルとアーキテクチャを確かめる段階の範囲であって、コネクタを作らないという決定ではない。実データでの試用は、その次の段階として行う。

## 決定

デプロイ（`docs/HANDOFF.md` の残作業 2）が通ったら、読み取り専用の実コネクタをつないで、まず Ingest だけを実データで回す。
目的は、実データでの判断と訂正を貯めて、プロンプト・閾値・モデルを調整できるようにすること。

### 書き込まない

- 実コネクタは `pull` だけを実装し、`send` は必ずエラーにする
- ゲートウェイに登録する資格情報は読み取りの権限だけにする（Gmail なら `gmail.readonly`）
- スタンドは派生の提案（`propose_derivation`）までは動かしてよい。外部派生の承認は、上の 2 つで送信に至らない
  （送信の失敗で approved のまま止まるのは既知の制約。試用の間は外部派生を承認しない運用にする）
- 内部派生は承認しても Murmur の中で適用されるだけなので、承認まで試してよい

### 範囲を絞る

- データソースは 1 つから始める（メールボックス 1 つ、できればラベルかフォルダ 1 つ）
- 過去分は取り込まず、つないだ時点から取る

### 測り方

実データには正解ラベルがないので、人の訂正を正解の代わりにする。

- `timeline.html` で振り分けを見て、誤りは `correct_ingest`（`POST /api/signals/:id/correct`）で直す。訂正の件数が誤りの件数
- ignore は全件 IgnoreLog に残るので、`GET /api/ignores` で拾い漏れを見る
- Claude の判断は `RecordReplayLlm` で記録する。貯まった実シグナルを再生して、プロンプトを変えたときの差や、
  Haiku で取り直したときの一致率を Sonnet と比べる（モデルは当面 `claude-sonnet-5-5`。量が増えるので、いずれ Haiku で足りるかを見たい）

### つなぐ前にやること

- H6 で ignore を選ばない問題（`docs/HANDOFF.md`「H6 の記録で分かったこと」）への手当て。ignore の例をプロンプトに足し、
  `--ai rerecord` で取り直す。実データには自動通知やお知らせが多く、このままだとタスクが増えすぎる
- 下の「量の見通し」の 1（取得位置の保存）。これがないと実コネクタは毎回全件を取り直す

## 量の見通し

実データは、つないですぐにシナリオの何桁も上の量になる。今の実装で効いてくる順に並べる。

1. **取得位置（cursor）を保存していない**。`pollConnectors` は毎回 `pull(principal, null)` を呼び、返ってきた cursor を捨てている
   （ダミーコネクタは全件を返すので問題にならなかった）。実コネクタでは毎回最初から取り直し、重複排除で捨てるだけになる。
   資格情報ごとに cursor を保存して次の `pull` に渡す
2. **シグナル 1 件ごとにテナントの投影を丸ごと読み書きしている**（0004）。`run` は投影を全部読み、fold して、全テーブルを消して入れ直す。
   シグナルには本文が JSONB で入るので、件数 N に対して 1 件の取り込みが O(N)、溜まると全体で O(N²) になる。
   0004 のトレードオフに書いた差分の upsert に替える。量の問題のうち、最初に詰まるのはここの見込み
3. **Cron の 1 回で全部を順番に処理している**。シグナルごとに Claude を呼び（送信なら返事期限の推定でもう 1 回）、投影を読み書きする。
   Workers の Cron の時間・CPU の上限に当たりうる。1 回の取り込み件数に上限を設け、残りは次の Cron に回す
4. **候補タスクは更新の新しい open タスク 20 件だけ**（`CANDIDATE_LIMIT`）。タスクが増えると正しい attach 先が候補から落ち、
   new に倒れて同じ用件のタスクが重複する。量では落ちないが、精度が静かに下がる。アンカーで決まらないシグナルの比率と、
   重複タスクの訂正件数を見て、候補の選び方（送り主・宛先の Party で絞るなど）を見直す
5. **Claude の呼び出し回数と費用**。アンカーで決まらないシグナルは全部 Claude に行く。取り込み件数・Claude の呼び出し件数・
   アンカーで決まった比率をログに出して、Haiku に替える判断の材料にする
6. **本文の置き場所**。実メールの本文が Claude API に送られ、投影・イベント・記録にも残る。社外の人のメールが入るなら、
   記録（`recordings`）をどこに置くかを決めてから記録モードにする

1 と、ignore の手当ては試用の前にやる。2〜5 は試用しながら、ログで詰まり具合を見て順に手を入れる。

## 代案

- いきなりスタンドで H7 を完走させる: 実データで Ingest が追えているかを切り分けられないので、先に Ingest だけを見る
- 書き込みも含めて試す: 誤った派生が外部に出たときに取り消せない。承認ゲートだけに頼らず、コネクタと資格情報で塞ぐ
