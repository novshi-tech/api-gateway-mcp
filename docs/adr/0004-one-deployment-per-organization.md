# 0004 組織はデプロイで分ける。同じ実装の複数のデプロイを、Claude に並べてつなぐ

- 状態: 採用(2026-10-30、直樹とのディスカッション)。実装(組織名の設定、スキルの「コネクタの選び方」、マルチアカウントの文言)はこれから
- 関連: README の「デプロイ」(1 つの clone で複数のデプロイ)、novshi-tech/murmur の `docs/adr/0018`(1 人のユーザが複数の組織にまたがる対応はしない。1 つの接続 = 1 つの組織)・`0020`(Murmur はゲートウェイと 1 対 1)

## 背景

ゲートウェイは、1 つのサービスについて 1 人のユーザーが複数の認証情報を登録できる(登録画面の「名前(複数のアカウントを見分けるため)」)。一方で、組織ごとにデプロイを分けることもできる(`deployments/<名前>.jsonc`)。使ってみると、この 2 つが混在していて分かりづらい。

- Google Workspace や Microsoft 365 のアカウントは、基本的にテナントの境界をまたがない。1 つのデプロイで別の組織のアカウントをつなぐには、OAuth のクライアントを外部向けにしてテストユーザーに招待する、といった無理が要る
- 1 つのデプロイに複数の組織の認証情報を束ねると、組織の境界はラベル(ユーザーの自己申告)にしかならず、ゲートウェイは強制できない(murmur の 0018 の決定 1 と同じ理由)
- 複数の組織で仕事をする人(複数の会社の経営、顧客の環境での作業)は、組織の数だけ接続先を持つ。どう管理するかの答えが要る

murmur の 0018 は「1 つの接続 = 1 つの組織」とし、組織の使い分けはスタンドの側で**切り替える**とした。ただ、Cowork(claude.ai のコネクタ)では切り替えの手段がなく、1 つの組織に固定するしかなかった。

## 決定

### 1. 組織の境界はデプロイ。1 つのデプロイ = 1 つの組織

- デプロイは、IdP・OAuth のクライアント・KV・暗号鍵を 1 組ずつ持つ。これがそのまま組織の境界になる
- OAuth のクライアントは、その組織の中だけで使える形で作る。Google は「内部」、Entra はシングルテナント。他の組織のアカウントは、そもそもつなげない。境界をゲートウェイ(と上流の IdP)が強制できる
- 別の組織を使うときは、同じ実装の別のデプロイを立てる。ゲートウェイに、組織の切り替え・アカウントリンク・テナントの概念は足さない

### 2. 複数のデプロイを、別々のコネクタとして Claude に並べてつなぐ

- 同じ実装でも、デプロイが違えば URL が違うので、Claude には別のコネクタとして追加できる。サインイン(OAuth)もトークンもコネクタごとに別になる
- ツール名はコネクタ名で区別される(`mcp__<コネクタ名>__issue_token`)。コネクタには組織が分かる名前を付ける
- ツールは `list_credentials` と `issue_token` の 2 つだけなので、並べてもツールの数はほとんど増えない
- スキル(プラグイン)は 1 回入れれば、すべてのコネクタで使い回す。**スキルは「同じゲートウェイのコネクタが複数つながっている」ことを普通の状況として書く**
- murmur の 0018 の「切り替える」は「並べる」になる。「1 つの接続 = 1 つの組織」はそのまま

### 3. ゲートウェイは自分がどの組織のものかを名乗る

ツールの説明文がどのデプロイでも同じだと、Claude がどのコネクタを使うかの手がかりがコネクタ名しかない。

- デプロイの設定に組織名を足す(`vars` の `ORGANIZATION_NAME` など。名前は実装で決める)
- MCP の instructions、ツールの説明、`list_credentials` の結果に、組織名(と IdP の種類)を載せる

### 4. スキルの「コネクタの選び方」

共通の `api-gateway` スキルに節を 1 つ作り、サービス別のスキルはそこを参照する。

- 依頼から組織が分かれば(会社名、メールのドメイン、組織専用のプラグインから呼ばれたなど)、その組織のコネクタを使う
- 分からず、そのサービスを持つコネクタが 2 つ以上あれば、ユーザーに聞く。推測で選ばない
- 1 回の作業は 1 つの組織で完結させる。ある組織で読んだものを別の組織に書く(送る・起票する・アップロードする)ときは、ユーザーに確認する
- `GW_TOKEN` / `GW_BASE_URL` は 1 組しかない。組織をまたぐと上書きで取り違えやすいので、上の「1 回の作業は 1 組織」で避ける

### 5. マルチアカウントは残すが、組織を分けるためには使わない

- 同じ組織の中で、1 つのサービスに複数のアカウントを使う正当な用途はある(個人のメールボックスと共有のメールボックスなど)。機能は残す
- 「組織を分けるのには使わない。組織はデプロイで分ける」を README と登録画面の文言で明示する。登録画面のラベル欄の説明(「複数のアカウントを見分けるため」)は、組織を分ける使い方に誘わない言い方に直す

### 6. どの Claude にどのゲートウェイをつなぐかは、使う側が決める

コネクタを通ったデータは、そのコネクタをつないだ Claude のアカウント(組織の契約)に入る。ゲートウェイでは強制できないので、使う側の責任とする。推奨する整理:

- 組織が契約している Claude(Team / Enterprise)には、その組織のゲートウェイだけをつなぐ
- 個人の Claude には、自分の組織と、個人(自分の組織)として受けている顧客のゲートウェイをつなぐ
- 組織の契約の Claude に、別の組織のゲートウェイを足さない

## 条件・リスク

- **会話の中で組織が混ざる**のは防げない。あるコネクタで読んだものを、別のコネクタで書くことは技術的にできる。これは murmur の 0018 でもスタンドの責任にした範囲で、スキルの約束(決定 4)とユーザーの確認で抑える
- Claude がコネクタを取り違える。組織名を名乗ること(決定 3)とスキルの約束(決定 4)で減らす
- Team / Enterprise のコード実行では、ネットワークの許可にゲートウェイのドメインが 1 つずつ要る。組織の契約の Claude にはその組織のゲートウェイだけをつなぐので(決定 6)、1 つの組織で増えるのは 1 つ
- デプロイが増えると、版を上げる手間が増える(deploy スキルの「新しい版に上げるとき」をデプロイの数だけ回す)

## 代案

- **1 つのデプロイのマルチアカウントで組織を分ける**: 境界がラベルにしかならない。Google / Microsoft の OAuth のクライアントに無理が要る。採らない
- **1 つのデプロイを複数の IdP に対応させ、アカウントリンクを足す**: murmur の 0018 で採らないとした
- **スタンドの側で接続先を切り替える(murmur の 0018 の 3)**: Claude Code ではできるが、Cowork では手段がない。切り替え忘れの事故もある。並べるほうが簡単で、境界はデプロイで守られる
