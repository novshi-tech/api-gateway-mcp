# 0034 Jira のコネクタ: 個人リストとして、本人の権限と本人の JQL で取り込む

- 状態: 案（2026-11-04、直樹とのディスカッション）
- 関連: 0010（黒子。状態は正から片方向に写す）、0012（本体は外に書かない）、0024（取り込みの経路。個人の箱は本人の OAuth、通知はヒントで正は差分、同期は直列）、0030（イベントはアドレスだけ、Contact はクエリ層）、0031（写しは決まった形）、0033（状態を持つデータソースは個人リストを既定にする。リンクは両端を読める人にだけ見せる）、H5・H8・H9

## 背景

0033 で、Jira のように共有の状態（担当者・ステータス・期日）を自分で持つデータソースは、個人リストを既定にすると決めた。共有の状態は Jira にあり、Murmur は本人の索引になればよい。

Outlook の個人の箱（0024）を main に載せ直し、実物で取り込めた（2026-11-04）。本人がゲートウェイで本体を許可した同意（ゲートウェイの OAuth のリフレッシュトークン）、取り込みの運用の状態のテーブル、直列のキューはそろっている。Jira はこの土台に載せる。

状態の写しの形（0031）・写しの判断（`planMirror`）・記録した起票やコメントとの統合（H5）は、ダミーコネクタと development のシナリオで確かめてある。コネクタが新しくやるのは、Jira の応答を `InboundItem` に直すことと、差分を取ってくることだけ。

## 決定（案）

### 1. 個人リストとして、本人の権限で取り込む

- ゲートウェイの `jira`（Atlassian の OAuth 2.0 3LO）の、本人の接続を使う。本体がゲートウェイから受けている同意（0024 の決定 3）はそのまま使い、Jira のための同意は増やさない
- つなぐ: スタンドが `POST /connections/jira` を呼ぶ（Outlook の `POST /connections/outlook` と同じ形）。同意がなければ `authorize`、ゲートウェイに Jira の接続が複数なら `choose`、なければ `no_credential`。接続が複数のサイト（`accessible-resources`）に届くなら、サイトを選んでもらう（`choose_site`）
- データソースは 0030 の個人のリスト（`createPersonalDataSource`）で作る。読者は本人だけ。リストでのアイデンティティは本人の Jira の accountId（`/rest/api/3/myself`）で、本人の Contact に `jira` のアドレスとして付く。窓口のアドレスは持たない
- 同じ本人・同じゲートウェイの接続・同じサイトなら作り直さない（Outlook と同じ）
- チームの資格情報（サービスアカウント、Background の入口）で共有リストにする経路は、要るチームが出てくるまで作らない

### 2. 取り込む範囲は本人の JQL

- つなぐときに `jql` を渡せる。省けば `assignee = currentUser() OR reporter = currentUser() OR watcher = currentUser()`（担当・起票・ウォッチ。Jira の自動ウォッチは本人の設定で、起票やコメントした課題に付く）
- 範囲は本人が後から変えられる（`PATCH /connections/{data_source}` の `jql`）。変えても過去のスレッドは消さない
- 範囲から外れた課題の続きを取りこぼさないよう、Murmur が開いているスレッドを持つ課題も取る: `(<本人の JQL>) OR key in (<開いているスレッドの課題キー>)`。キーが多いときは分けて引く

### 3. 差分は JQL で取る。通知はヒント

- Jira には Graph の delta にあたるものがないので、`updated` で取る: `(<範囲>) AND updated >= -<N>m ORDER BY updated ASC`
  - 時刻は相対（`-<N>m`）で書く。JQL の絶対時刻は本人のプロフィールのタイムゾーンで読まれるため、ずれる
  - `N` は前回の同期からの分数に重なり（5 分）を足したもの。二重に取った分は `sourceRef` の重複排除で落ちる
- 位置（前回の同期の時刻）は取り込みの運用の状態に置き、取り込みが終わってから進める（0024 の決定 2 のまま。イベントにしない）
- 通知は Outlook と同じく、つないだときに Jira の動的 Webhook（`POST /rest/api/3/webhook`、スコープ `manage:jira-webhook`。ゲートウェイの `jira` に付いている）を登録して受ける。中身は使わず、受けたらそのデータソースの範囲を JQL で取り直す（0024 の決定 2 のまま、通知はヒント）
- 保険の同期は Cron（Outlook と同じ `maintain`）。通知を取りこぼしても、次の Cron で追いつく
- 寿命（30 日）の延長（`PUT /rest/api/3/webhook/refresh`）・作り直し・削除は、購読の管理として本体が持つ（0024 の決定 1）。計画は Graph のサブスクリプションと同じく純関数にする（`planMaintenance` の Jira 版）

#### 受け口の守り方

- Graph の通知は、登録のときに本体が決めた秘密（`clientState`）が本文に入って返ってくるので、本体が照合できる。Jira の動的 Webhook の登録には、この秘密を渡す欄がない
- Jira の動的 Webhook には署名の JWT（`Authorization` ヘッダー）が付くが、署名の鍵は Webhook を登録した OAuth のアプリのもの（クライアントシークレット）。この経路では、アプリはゲートウェイの Atlassian のアプリで、シークレットはゲートウェイだけが持つ（本体は上流の資格情報を持たない。0024）。だから本体だけでは検証できない（鍵が何かは S0 で確かめる）
- そこで、Graph の `clientState` と同じ強さの守りを、受け口の URL に入れた秘密で作る: `<PUBLIC_URL>/webhooks/jira/<本人ごとの秘密>`。秘密は最初に Jira をつないだときに本体が作り、平文は持たずに SHA-256 だけ置く。合わなければ捨てる。どちらも「登録した本人しか知らない文字列が返ってくるか」を見るだけで、強さは同じ（S0 で、パスの秘密のまま届くことを確かめた）
- Jira は REST で登録する Webhook の URL を **本人ごとに 1 つ** しか許さない（S0）。だから秘密はデータソースごとではなく本人ごとに持つ。通知が来たら、その本人の Jira のデータソースを取り直す（通知はヒントなので、多めに取り直しても台帳は変わらない）
- Webhook の `jqlFilter` では `watcher` が使えない（S0）。範囲の JQL をそのまま渡せないときは、使える節だけの広めの条件（`assignee = currentUser() OR reporter = currentUser()`、`project IN (...)` など）で登録し、取り直しの JQL で絞る。`watcher` でしか拾えない課題は Cron の差分で拾う
- 中身は使わないので、偽の通知が通っても起きるのは、その本人の差分の取り直しだけ（読み取りの量が増えるだけで、台帳は変わらない）
- JWT まで検証したくなったら、ゲートウェイの Background の入口に検証の口（本体から JWT を渡して、ゲートウェイがシークレットで確かめる）を足す。呼び出しは本体からゲートウェイへの一方向のまま（0024 の決定 5）。最初の版ではやらない

### 4. 写像

更新された課題 1 件から、写しとシグナルを作る。

| Jira | Murmur | 中身 |
| --- | --- | --- |
| 課題の今の状態 | `InboundMirror` | 0031 の形: `closed` = ステータスカテゴリが `done`、`holders` = 担当者の accountId（いなければ空）、`title` = 要約、`statusLabel` = ステータス名、`due` = 期日。`sourceRef` は `jira:<課題キー>@<updated>`。変わっていない項目は `planMirror` が捨てる |
| 起票 | シグナル | from = 起票した人、to = 担当者（いなければ空）、subject = `[<課題キー>] <要約>`、body = 説明（ADF をテキストに）。`threadKey` と `messageId` は課題キー（スタンドが記録した起票の `sent_ref` と統合する。H5） |
| コメント | シグナル | from = 書いた人、to = メンションした人。いなければ担当者、それもいなければ起票した人（書いた本人は除く）。`messageId`・`sourceRef` は `<課題キー>#c<コメント ID>`（記録したコメントの `sent_ref` と同じ形）。`threadKey` は課題キー |
| ステータス・担当者・期日などの変更 | 写しだけ | シグナルにしない（ボールの判断も AI の呼び出しも要らない。誰の番は担当者の写しで決まる。0031） |

- アドレスは `jira` チャネルの accountId。表示名は持たない（名寄せはスタンドがゲートウェイの Jira で表示名を引いて、本人に確かめて付ける。0030）
- 本文中の課題キーと PR は `jiraKeys`・`prRefs` に拾う（結び候補。区切りには使わない）
- 並びは写しが先、シグナルが後。写しが先でもスレッドはできる（0031 の 8）
- 最初の版では、コメントの編集・削除、添付、課題の削除・移動は追わない

### 5. 読み取りしかしない

- コネクタが呼べるのは、決まった読み取りの口だけ（`GET`: 課題の検索・課題・コメント・`myself`・`accessible-resources`）。許可の一覧に固定し、テストで確かめる
- 書き込みの口は、Webhook の登録・延長・削除（購読の管理、0024）だけ
- 起票・コメント・状態の変更は、これまでどおりスタンドがゲートウェイの Jira で行い、本体には `record_sent` で記録する

### 6. 取り込みの土台を Outlook と共有する

- 本人の同意（`gateway_grants`）・認可の途中（`oauth_pending`）・キュー・`maintain` は共有する
- データソースの取り込みの経路（`DataSource.connector`）に `{ kind: 'jira', cloudId, site, jql }` を足す
- 取り込みの運用の状態（`connector_sources`）の位置を、経路ごとの形にする（Graph はフォルダごとの delta、Jira は前回の同期の時刻）。行は JSON なので、テーブルの形は変えずに型だけ分ける
- `src/connectors/jira/` に、写像（純関数）・Jira の API（シェル）・同期（キューの仕事）を置く。Graph と同じ分け方

## 代案

- **チームの資格情報で共有リストにする**（サービスアカウント、client credentials、Background の入口）: 0033 のとおり既定にしない。Murmur が足せる共有の状態がないうえ、管理者の作業が要る
- **範囲を JQL ではなくプロジェクトで決める**: 気軽さが落ちる。プロジェクトで絞りたければ JQL に書ける
- **状態の変更もシグナルにする**: ボールと誰の番は写しで足り、AI の呼び出しとタイムラインの雑音が増える
- **Webhook の中身を使う**: 取りこぼしと順番の入れ替わりがあり、署名も本体だけでは検証できない。0024 の「通知はヒント」に合わせる
- **Webhook をやめて Cron の差分だけにする**: 動くが、取り込みが最大 5 分遅れる。Outlook と同じ速さにそろえる
