# 0030 Party の作り方: メンバーは初回の接続で作り、名寄せはクエリ層で後から人が付ける

- 状態: 案（2026-10-31、直樹とのディスカッション。方向は合意、実装は未着手）
- 関連: 0003（ゲートウェイから伝搬されるユーザー識別）、0008（業務の知識を持たない）、0013・0014（Murmur は候補を出すだけで、自分では結ばない）、0016 の段取り 1（相手を引く API）、0020・0021（1 デプロイ = 1 チーム）

## 背景

User・Party・Address はマスタで、作る経路は seed しかない。
実際につなぐときは `pnpm seed <scenario> --user u_kimura=<ゲートウェイの User ID>` で、seed の User をゲートウェイの ID に差し替えている。だから直樹が接続すると、seed の「木村」になる。
実データ（0016 の段階 5）では次の 3 つが困る。

1. **メンバーを作れない**: ゲートウェイの JWT は `sub` しか持たない（`src/auth/claims.ts`）。本体には名前もメールも来ない。
   ゲートウェイに `name`・`email` を足すことはできるが、IdP のメールと、Murmur が取り込む箱のアドレス（共有メールボックス・別名・LINE・Slack）は一致しない。だから JWT から Address までは作れない
2. **外の相手（ゴースト Party）を作れない**: 知らないアドレスのシグナルは `fromPartyId: null` のまま入る
3. **後から付けても過去に効かない**: Ingest と `record_sent` は、取り込んだ時点の Directory で Party を解決して、イベント（`SignalObserved.fromPartyId`・`toPartyIds`）に焼き込んでいる（`src/domain/ingest.ts`・`outbound.ts`）。
   状態の写しの担当者も、写した時点で Party ID にしている（`mirror.ts`）。
   seed の投入では、マスタが変わればイベントは意味を失うとして、イベントごと消している

## 決定（案）

### 1. Party の解決をクエリ層に寄せる

イベントと投影はアドレスだけを持ち、Party には直さない。Party への解決は、クエリ層がそのときのマスタで行う（シグナルの時刻で有効な Address、`validFrom`・`validTo`）。

- `SignalObserved` から `fromPartyId`・`toPartyIds` を外す（古いイベントに残っていても読まない）。`SignalRecord` も同じ
- スレッドのログとボールはアドレスで持つ: `ThreadLogEntry.toPartyIds` → `to`（AddressRef）、ボールの `{ kind: 'party', partyIds }` → `{ kind: 'counterpart', to }`、`Thread.counterpartPartyIds` → `counterparts`（AddressRef）
- クエリ層（`turn.ts`・`visibility.ts`）が、ボールの相手・相手の一覧・宛先による「自分の番」（`addressed`）を、読むたびに Party に解決する。解決できないアドレスはアドレスのまま返す
- 状態の写しで型が `party` の属性（担当者）は、ソースのアカウントを AddressRef で写す。Party への解決と担当者で決まる「誰の番」（`assigneeTurn`）はクエリ層で行う。本人が付ける `party` 属性（メモのスレッド）は、今のとおり Party ID のまま
- `record_sent` の `to_party_ids` は、今のとおり入力のときにアドレスに直す。イベントに残すのはアドレスだけ
- Ingest の判断は、もともとアドレスで比べている（区切りの「同じ相手」・`awaitingThread`）。その判断は今のまま `SignalThreaded` に残る
- fold はもともと Directory を読まない。これでイベントもマスタに依存しなくなり、マスタを変えてもイベントを消さずに済む

イベント型が変わるので、CLAUDE.md の約束どおり、zod スキーマ・fold の純関数テスト・リプレイテスト（H1）と fixtures の expected を同じ変更で直す。

### 2. マスタは動かしながら書き換える（イベントにはしない）

Party・Address は、動いているデプロイで足したり直したりできるようにする（`MasterStore` に足す。今は丸ごと入れ替える `replaceSeed` だけ）。
1 があるので、マスタの変更をイベントにしなくてもリプレイは決定的なまま（H1）。
誰がいつ何を変えたかは、イベントとは別の変更の記録に残す（後から名寄せの間違いを追うため）。

マスタの整合性（`seedProblems`）は、変更のたびに同じ規則で確かめる。違反する変更は `conflict` にする。
加えて、**1 つのアドレスは、ある時点で 1 つの Party にしか付かない**（期間の重なりを禁止する）。

### 3. メンバーは初回の接続で作る

検証済みの `sub` に User がなければ、最初の API 呼び出しで次を作る。

- User（`id` = `sub`）と、その Party（`kind: person`、`internal: true`、`userId`）
- 個人のメモのデータソースとそのリスト。読者は本人だけ

名前は空のまま作る。`GET /me` が名前のないことを返したら、スタンドが本人に聞いて付ける（`PATCH /me`）。
JWT に `name` を足すかは、ゲートウェイの側の都合で決める（足しても初期値にするだけ）。
自分のアドレスも自動では付けない。下の 4 でスタンドが付ける。

1 ゲートウェイ = 1 チーム（0020）なので、サインインできる人はチームのメンバーとみなしてよい。
自動で作られた Party が見えるのは自分のメモだけ。共有のデータソースの読者（ListMember）にはならない。だから自動で作っても境界は崩れない（H3）。

### 4. 名寄せはスタンドが未解決のアドレスを探して付ける（Murmur は付けない）

Murmur は Party を自分で作らず、アドレスを Party に自動で付けない（0014 の「候補を出すだけ」と同じ）。スタンドが本人と確かめてから付ける。

- `GET /addresses/unresolved`: Viewer が読めるデータソースのシグナルに出てきたアドレスのうち、Party に解決できないもの。チャネル・値・回数・最後に見た時刻・出てきたスレッドを返す。見えないデータソースの分は出さない（H3）
- `GET /parties?q=`: Party と Address を名前やアドレスで引く（0016 の段取り 1 と同じ）
- `POST /parties`: ゴースト Party を作る（名前・`kind`、最初のアドレス）
- `POST /parties/:id/addresses`: アドレスを付ける（自分の Party にも）。外すのは削除ではなく `validTo` で終わらせる
- `PATCH /parties/:id`: 名前を直す

書けるのはチームのメンバー（Party を持つ User）全員。Party の知識はチームで共有するマスタだから。
スキルには「未解決のアドレスを見つけたら、`GET /parties?q=` で候補を出し、本人に確かめてから付ける」と書く。HTTP API の表もスキルに足す。

## やらないこと

- Ingest のときに、知らないアドレスからゴースト Party を自動で作ること（名寄せの間違いが、人の確かめなしに広がる）
- 表示名やドメインからの名寄せの推測を本体に持つこと（0008）。候補を出すのはスタンド
- JWT のメールから Address を作ること（取り込む箱のアドレスと一致する保証がない）

## 未決

1. **先にゴーストとして作られた人が、後からサインインしたとき**: 3 は新しい Party を作るので、同じ人の Party が 2 つになる。
   案 A: ゴーストの Party に User を結ぶ操作（「この Party は私」）を足す。案 B: 2 つの Party をまとめる操作（アドレスを付け替え、本人が付けた `party` 属性を直す）。
   A は他人のゴーストを名乗れてしまう。名乗っても読めるものは増えない（読者になるのは ListMember だけ）が、宛先による「自分の番」は変わる。だから結ぶのは本人の申告 + 別のメンバーの確認、か管理者だけにするか
2. **共有のデータソース・リスト・読者（ListMember）の登録**: この ADR の範囲の外。当面は seed か管理者のスクリプトで入れる。実コネクタ（0024・0025）を入れるときに決める
3. **変更の記録の形**: 表 1 つ（誰・いつ・何を・前の値）でよいか。管理画面（`/admin`）で見せるか
4. **seed の位置づけ**: シナリオとテストでは今のまま使う。実データのデプロイは空で始め、データソースだけを入れる。`--user` の差し替えは、シナリオを実環境で回すとき（H7）のためだけに残す

## 帰結

- 名寄せを後から直すと、過去のスレッドの相手の名前と「誰の番」も直る（いまは取り込み直すしかない）
- クエリのたびに解決するので、一覧の計算が少し重くなる。アドレスから Party への索引を Directory に持てば足りる見込み
- 0016 の段取り 1（相手を引く API）は、この ADR の 4 に含める
