# 0012 Murmur は「人とエージェントが共有する判断の台帳」。外には何も書かない

- 状態: 採用（2026-10-17、直樹と合意。計画 v2（`docs/PLAN.md`）と `CLAUDE.md` に反映した）。
  **2026-10-20: 0013 でチームリスト・購読・派生を外し、「共有の台帳」の定義文は書き直しになった（単語は直樹が練る）。未決 1 は 0013 で解消。同日 0014 で定義文は「連絡から対応の要る件を拾い、その経過を追跡する。エンティティはスレッドの 1 種類」になった。「綴じる 3 種類」はそのまま**
- 関連: 0008（業務の知識を持たない）、0009（2 層のリスト）、0010（黒子、正は外）、0005（派生を起こすのはスタンド）、0006（ゲートウェイの拡張）、0007（実データの試用）、
  boid の計画（novshi-tech/boid の `docs/plans/`。特に `cross-project-issue-triage.md`、`ingestion-identity.md`、`card-next-step-and-timeline.md`、`card-model-cleanup.md`）

## 背景

計画 v2 を書いたあと、「外部への送信をすべてスタンドに任せ、本体は Ingest の振り分けに集中したほうがシンプルではないか」という問いから議論を始めた。
議論は送信の置き場所にとどまらず、Murmur が一体何なのかに及んだ。

- 設計メモの出発点は「AI ネイティブ タスク管理ツール」だった。だが 0008〜0010 を経て、Murmur は業務の知識を持たず、正は受け皿のあるサービスにあり、
  人向けの UI もスタンドに任せる、と決めてきた。「タスク管理ツール」という言葉は、もう作るものを指していない
- 送信の議論で分かったこと: 受信のメタデータ（Message-ID、LINE のユーザー ID、直近の用件との照合）だけでは、**こちらから第三者に新しく話しかけた件の返事**は追えない。
  4 シナリオで、スタンドが送ったものへの返事 6 件のうち 3 件（complaint s02、repair-estimate s02、absence s02）がこれにあたる。
  紐付けがうまくいっても、送った事実を知らなければボールは「こちら」に残り続け、「相手待ち」と期限超過（H4 の半分）は出せない。
  つまり **送信の実行は本体に要らないが、送った事実の記録は要る**
- 「分断されたチャネルを統合するビュー」と言いかけたが、ビューは読むだけのもので、「どのデータソースにも属さない作業ログを書き込む」が入らない。
  Murmur は読み書きされる記録簿であって、ビューではない
- 直樹が個人で使っているパーソナルオーケストレータ boid には、すでに同じ構造がある（card = 判断の台帳、signal inbox、identity 索引、イベントソーシング、canonical source）。
  boid の API ゲートウェイの機能を切り出して Cowork やチャットからも呼べるようにしたところ効果が大きく、boid の成果をローカルに閉じ込めている意味がなくなった。
  Murmur はその発想から来ている。「前例がない」のではなく、前例は boid にある

## 決定

### 定義

**2026-10-20（0013）の改訂**: チームの共有を既存のツールに任せ、Murmur の中で共有されるのはデータソースの写しだけになったので、「人とエージェントが共有する判断の台帳」という名詞は立てない。定義文は次のとおり。

> Murmur は、連絡から対応の要る用件を抽出し、その経過を追跡する。
> 外部リスト（データソースの写し。テナントで 1 つの共有の実体で、見えるのはそのデータソースを読める人）と、マイリスト（各自の用件・メモ・属性。本人だけのもの）から成る。
> 綴じるのは、連絡（観測）、人とエージェントの行動（送った・持った・決めた・付け替えた）、用件に宛てたメモの 3 種類。
> Murmur が判断するのは「どこに綴じるか」と「ボールが動いたか」だけ。何をするかは判断しないし、何も実行しない。外には何も書かない。チームの共有は既存のツールに任せる。

以下は 2026-10-17 の元の定義（経緯として残す。「用件は個人のリストかチームのリストに属し」の部分は 0013 で変わった）。

> Murmur は、連絡から対応の要る用件を抽出し、その経過を追跡する、**人とエージェントが共有する判断の台帳**。
>
> boid の card（判断の台帳）と signal inbox を、一人のマシンからテナントの皆が届く場所へ持ち出し、ソースを開発者宛ての通知からメール・LINE・Slack の連絡全般へ広げたもの。
> どのモデル・どのハーネス（Cowork、Claude Code、boid、他社のモデル）からも、ゲートウェイ経由の同じ API で読み書きできる。
>
> 綴じるのは、連絡（観測）、人とエージェントの行動（送った・決めた・付け替えた）、用件に宛てたメモの 3 種類。
> 用件は個人のリストかチームのリストに属し、見えるのはそのリストのメンバーだけ。個人リストに綴じたものは本人だけのもの。
>
> Murmur が判断するのは「どこに綴じるか」と「ボールが動いたか」だけ。何をするかは判断しないし、何も実行しない。外には何も書かない。
> 実行はスタンドと人、用件の正は受け皿のあるサービスにあり、Murmur が正なのは受け皿のない用件だけ。
>
> 成功の定義は boid と同じ。「提示された用件に応えていくだけで仕事が進む」。

### 抽出と追跡

雑多な連絡から対応の要るものを抽出して追跡するのがタスク管理の本質で、既存のツールは追跡しかしない（抽出は人の頭と、チケットを切る手に任されている）。
Murmur は抽出の側に立つ。これが既存のツールとの差のすべてで、「タスク管理ツール」と呼ばない理由でもある。

- **抽出**: 連絡から対応の要る用件を取り出す。Ingest（スレッドの区切り、返事や対応を求めているか）と昇格（購読）。用件に綴じられなかったスレッドは雑多なまま、台帳の外
- **追跡**: 用件のボールと期限を、チャネルをまたいで追う

綴じる単位は用件だけ（0009 の「スレッドと用件は 1 対 1 以下」と整合）。

### 綴じる 3 種類

| 種類 | 何か | イベント |
| --- | --- | --- |
| 観測 | 外から来た事実 | `SignalReceived`、`SignalObservedSent` |
| 行動 | 人とエージェントがしたこと（構造化） | 送った（下の「送信」）、属性の変更、クローズ、つなぎ替え、統合、片付け、派生 |
| メモ | 用件に宛てた自由記述。次にこの用件を開く人（自分の次のセッション、同僚、引き継ぎ先）が知るべきこと | `MatterNoted { matterId, by, text, refs? }`（新設） |

メモは、電話や対面のようにデータソースのないチャネルの記録と、判断の記録（H7 で「明日（17 日）」を 18 日の誤記と読み替えた判断は、LINE にも属性にも残らず申し送りにだけある）の置き場になる。
fold は用件のタイムラインに並べるだけで、Murmur はメモの中身を解釈しない（boid の「daemon が opaque blob から読むキーは closed set」と同じ）。

### 外には何も書かない。送信はスタンドが実行し、本体は事実を記録する

- 外への送信（メッセージ・起票・コメント）は、スタンドがユーザーの確認を取り、ゲートウェイ経由で実行する。承認のゲートは本体からスタンドとの会話（とゲートウェイの資格情報の権限）へ移る
- スタンドは送った直後に本体へ記録する: 用件、データソース、宛先（Party か Address）、`sent_ref`（メールの Message-ID、Slack の ts、LINE の `sentMessages[].id`）、本文、返事期待（省略可）。
  本体はこれをイベント（`OutboundRecorded`。v2 の `OutboundSent` の後継）として綴じ、用件につながったスレッドを作り（経路 `sent`）、ボールを相手に移す。
  本文は必須（0009 の背景「打診のタスクが空に見えた」を繰り返さない）
- 観測された送信（`SignalObservedSent`）は保険。`sent_ref` が一致すれば 1 本に統合する（H5）。観測が記録より先に届く順も扱う
- 記録のない送信（スタンドを通さず送ったもの）は、観測で拾えても用件に結びつかず、送った本人の仕分け待ちに出る。管理したい用件はスタンド経由で送る、が運用の約束
- **前提の指標**: 「外には何も書かない」が成り立つかは、**用件に結びつかなかった観測送信の件数**で測る（0007 の実データの試用で、訂正の件数と並べて数える）。
  多すぎれば、まずスキルで「送ったら記録する」を徹底し、それでも足りなければゲートウェイが送信を本体に通知する形（0006 の延長）に寄せる。本体が外に書く方向には戻らない
- 派生（用件のリスト間の受け渡し）は外に出ないので、これまでどおり本体の中で完結する。承認もそのまま

### Murmur が判断するもの

基準: **綴じるために要る判断は本体、何をするかの判断はスタンド**。
抽出は Murmur の本質なので、スタンドに任せて任意にはできない（誰も見ていない夜中に届いたメールも、朝には用件になっていなければならない）。

| 判断 | 綴じるために要るか | 扱い |
| --- | --- | --- |
| スレッドの区切り（どこに綴じるか） | 要る | 本体 |
| 返事や対応を求めているか（ボールが動くか） | 要る。抽出そのもの | 本体 |
| 購読の自然文の条件（どのリストに綴じるか） | 要る | 本体。構造の条件で足りる場面が多い見込みで、最初に消える候補 |
| 観測された送信の返事期待の推定 | 要らない（スタンドが記録すれば明示される） | **外す**。記録のない送信は返事期待なしで綴じる |
| 何をするか、誰に何を渡すか、本文 | — | スタンド（0008） |

本体に残した判断の精度が実務に耐えるかは、0007 の実データの試用で判断の種類ごとに訂正の件数を数えて見る。訂正の操作（0009 の「直す操作」）が先に揃っている必要がある。

### 可視性はリストだけ

- メモにも行動にも個別の可視性は持たせない。用件のリストが可視性のすべて。個人リストの用件に綴じたメモは本人だけのもの、チームに見せたいものはチームの用件に綴じる
- 正が外にある用件（Jira の課題）のメモが Jira を見る人に見えないのは、それでいい。Jira に書くべきことなら、スタンドが Jira のコメントとして書き、それは「送った」として綴じられる。
  boid でも「正は外のサービス + ローカルなメモ」で回っていて、むしろ良い点が多かった
- スタンドの記憶（個人の知恵、作業中の考え、やりかけ）は本人のもので、Murmur は吸収しない

### 何でないか

- タスク管理ツールではない。ボードもスプリントも、自前の状態ワークフローも持たない。状態は受け皿のあるサービスにある
- ビューではない。読み書きされる記録簿
- エージェントではない。次の一手を判断しない。判断するのは綴じ方だけ
- 連携基盤ではない。メッセージを配送しない。外に書かない
- 受信箱ではない。綴じる単位は用件で、スレッドは用件の材料

### スタンドの読み方

台帳なら、スタンドが聞くことは次の 4 つ。後の 2 つは今の API 表になく、セッションが切れるエージェントには本質的なので足す。

1. 自分の用件で、ボールがこちらにあるものは（`list_my_matters`）
2. この相手との開いている用件は
3. **この用件で、前回見てから何があったか**（`get_matter` に `since` を足す）
4. **この件で以前何を決めたか**（メモ。`MatterNoted` を `get_matter` のタイムラインに含める）

## boid からの系譜

### 引き継ぐもの

| boid | Murmur |
| --- | --- |
| 成功の定義「提示された課題に応えていくだけで仕事が進む」。queue への信頼 = 網羅性・文脈同梱・Go 一発 | 同じ |
| 「アクショナブルになる前の層に置き場がない」→ card = 判断の台帳 | 用件 |
| signal inbox、identity 索引（外部キー → task、多対一） | シグナル、アンカー |
| 決定 13: イベントソーシング。決定 14: 状態の正は 1 つ | append-only のイベント列 + fold、H1 |
| 決定 16: triaged 以降は canonical source を必ず持つ。決定 15: `source_closed` で done に自動落ち | 0010 の「正は外」、`MatterMirrored` |
| 決定 3 改: 境界を越えてよい範囲は開示ポリシーが決める | リストの可視性 |
| daemon が opaque blob から読むキーは closed set | 通信状態は事前定義属性だけから導出。メモは解釈しない |
| 命名の経緯: card → triage task → card。dossier は「口頭で重い」で不採用 | 「判断の台帳」を採る。カルテ・dossier は採らない |

### 変わるもの

| | boid | Murmur |
| --- | --- | --- |
| 誰のものか | 一人 | テナントの人たち。個人リストとチームリスト |
| どこにあるか | 自分のマシンの daemon（SQLite） | 皆が届くところ（Worker + Neon） |
| 誰が読み書きするか | boid の CLI と Web UI、サンドボックスの shim | ゲートウェイ経由の HTTP API。どのハーネス・どのモデルからでも |
| シグナルの出どころ | Slack のメンション・Jira の担当課題・PR コメント（開発者宛て） | メール・LINE・Slack の会話全般。相手は社外のゴースト Party も |
| 実行 | daemon が hook をサンドボックスで走らせる | **何も実行しない** |
| 篩い（抽出） | workspace の ingestion job（LLM は task の中。決定 12「daemon は判断しない」） | **本体の Claude 呼び出し**（記録・再生） |

最後の行だけが boid の決定 12 からの意図的な逸脱。boid は一人の workspace が常に動いているから篩いを task に任せられるが、
Murmur はスタンドが起きていなくても綴じられなければならず、篩いを人ごとのスタンドに任せると可視性の判断が各自でばらつく。
逸脱は抽出に要る判断（上の表）に限り、それ以外の判断は boid と同じく本体に置かない。

### 着地

boid の card と signal inbox は Murmur に移り、boid 自身は「開発タスクを実行するスタンド」の 1 つになる。Cowork は事務のスタンド、boid は開発のスタンド。どちらも同じ台帳を読み書きする。
boid の「次の一手を考え、実行し、結果を受けてまた考える場所」（card-next-step）は、台帳が Murmur に移っても boid の中で成り立つ。

## 外したもの

- **後回しと再浮上**（boid の決定 9）: boid でも必ずしも効果的に機能していない部分なので、v2 には入れない
- **起票ルール**（0010）: 本体が外に書かないので、本体が機械的に起票することもない。業務の知識として登録するなら、スタンドが実行するルールになる。H9 からも外す
- **観測された送信の返事期待の推定**: 上の表
- **承認の件数の計測**（計画 v2「承認の件数と種類をシナリオごとに計測」）: 承認が本体を通らないので測れない。スタンド側のログで見るか、諦める

## 計画 v2 への影響（2026-10-17 に反映した）

- 冒頭: 「AI ネイティブ タスク管理ツールのプロトタイプ」を「人とエージェントが共有する判断の台帳のプロトタイプ」に。`CLAUDE.md` の冒頭も
- データモデル: `OutboundProposed / Approved / Rejected` と宛先 Address の凍結、`Connector.send`、`FilingRule` を消す。`OutboundSent` → `OutboundRecorded`（スタンドが出す）。`MatterNoted` を足す
- Ingest・昇格: 変更なし。観測された送信の返事期待の推定を外す（Claude の呼び出しは 3 か所から 2 か所に）
- 送信・派生・承認・観測: 「人の承認が外への唯一のゲート」→「外への送信はスタンドが実行し、本体は事実を記録する」。派生はそのまま
- 正が外にある用件: 起票ルールを外す。起票はスタンドが行い、`OutboundRecorded` で綴じる
- API: `propose_send / approve / reject`（送信側）→ `record_sent`。`add_note` を足す。`get_matter` に `since`。スキルの API 表も直す
- コネクタ: `send` を消す。ダミーの `echoObserved` は「スタンドの記録に対応する観測が次の pull で返る」に読み替える
- 仮説: H4 は「記録した送信 → 返事が送ったスレッドに戻る → 期限超過」と派生。H5 は「記録 → 観測」「観測 → 記録」の両順で 1 本に統合。H9 から起票ルールを外す。
  **H10（新）: 台帳があるほうがスタンドは良い一手を出せる** — 同じ absence を、台帳なし（LINE・Gmail の MCP だけ渡したスタンド）と台帳ありで回し、
  完走できたか・ユーザーへの確認の回数・ツール呼び出しの回数・取り違えの件数・セッションが切れた後に続きから入れるかを比べる。モデルが良くなれば「なし」が追い上げるので、定期的に回し直す
- ステップ: 4 の送信の半分と 7 の起票ルールが落ちる。3（用件の層）は個人リストを先に通し、チームリストと購読をその上に積む（出発点は一人の個人リスト = boid の形）
- 並行トラック（0007）: 計測に「用件に結びつかなかった観測送信の件数」を足す

## 未決

1. チームの用件について、自分だけのメモを持ちたいとき。(a) 個人リストにチームの用件を参照する用件を作る、(b) スタンドの記憶に置く（Murmur の外）、(c) 用件に個人リストからの参照を持たせる。まず (b) で進め、必要が出たら (a)
2. LINE の Messaging API は、自分で push したメッセージを webhook で返さないはず（未確認）。そうなら LINE の観測送信はなく、スタンドの記録だけが頼りになる。確認する
   → 2026-10-22 に WebSearch で調べた（`docs/research/2026-10-22-line-messaging-api.md`）: 返さない見込み。管理画面のチャットから返した分も webhook に来ない（外部連携ツールのドキュメント。公式の明記は未発見）。実物で確かめるまで未決のまま
3. 観測が記録より先に届いたとき、その間の投影の形（用件につながらないスレッド、ボールは相手）と、記録が来たときの付け替えの経路名
4. カスタム属性（`AttributeDef`）とメモの線引き。正が Murmur にある用件には型付きの属性が要るのか、メモで代用できるのか。absence の `kind / shift_date / substitute` で見る
5. H10 の「台帳なし」の条件のそろえ方（同じモデル、同じスキル、同じ MCP）

## 代案

- 統合ビュー（読むだけ）: 行動とメモを書き込めず、「送った事実」も「決めたこと」も残らない。送信の議論で要ることが分かった
- 台帳をスタンド側（boid のまま、各自のローカル）に置く: 人をまたいで共有できず、スタンドが起きていないと綴じられず、ハーネスごとに台帳が分かれる。Murmur を発想した理由そのもの
- 本体が送信も行う（計画 v2 の形）: ゲートウェイの act-as / ServiceClient（0006、未実装）が前提になり、試用（0007）では send をエラーにする特別扱いが要る。本体の価値「出入りを守る」の「出」は、ゲートウェイの資格情報の権限とスタンドの確認で代替できる
- 送信の記録を観測だけで賄う（スタンドは報告しない）: 用件との紐付けが AI の判断になり、返事期待が推定値になり、LINE に穴が残る。知っている側（スタンド）が黙って、知らない側に推理させる形
