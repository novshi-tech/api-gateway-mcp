## 3. v2 で分かったこと

### データモデル

- **スレッド 1 種類で足りた。** データソースの写し・個人のメモ・Jira の課題が同じ形で扱え、違いは「区切りと状態をソースが持つか」だけだった（0014 の見立てのとおり）。用件（Matter）を別に持つ必要はなかった
- **fold は 1 段、合わせるのはクエリ層**、が実装を単純にした。誰の番・リンク先から導出したボール・結び候補はどれもクエリ層の純関数で、投影の作り直し（H1）に影響しない
- **件名は直せる必要がある**（H7）。Ingest が付けた件名に日付の誤り（「明日(17日)」）が残り、LINE は本文の頭が件名になる。直樹の方向は「件名は属性の 1 つとして畳めるべき」（0014 の未決 2）。Jira の要約の変更も同じ仕組みで写せる
- **状態を持つソースでは、担当者が誰の番を決める**（ステップ 7）。持ち主 ＞ 担当者 ＞ シグナルのボール、の順にした。担当者がコメントで相手にボールを渡しても、担当者を変えないかぎり担当者の番になる（Jira が正）。これでよいかは実データで見る

### Ingest

- **返事待ちが 1 本だけ、の規則が効いた。** v1 で起きた「承諾が欠勤のスレッドに付く」取り違えは、シナリオでも実環境（H7）でも起きなかった
- **業務の知識を持たない判断でも、区切りと「求めているか」は 34/34 当たった**（シナリオ）。ただしシナリオは Claude が書いたもので、実データの数字ではない
- 遅刻の連絡のような「知らせ」は「求めていない」が正しい（2026-10-21 に直した）。そのうえで、業務上の食い違い（伊藤さんと山本さんが二人とも明日入れる）に気づくのはスタンドの仕事で、H7 のスタンドは結んだ先まで読んで気づいた

### スタンドとの分担

- **「本体は外に書かない」は成り立った。** スタンドはスキルどおり、送ってから記録し、送れないものは記録しなかった（H7）
- **スタンドは Murmur の外にも手を伸ばす。** H7 で、次の一手としてビルメンNEXT の割当を付け替えようとした。本物につながったスキルがある環境でテストのシナリオを回すときは、最初に「外に書かない」と伝える必要がある。Jira も同じで、ステップ 7 をスタンドで回さなかった理由の 1 つ
- **スタンドは Murmur の意味を取り違えて説明する。** 「片付けたあと何か来たら開き直って上がってくる」と言った（実際は開き直さない）。スキルの文面が足りないところは、スタンドが推測で埋める
- **スタンドは受信時刻と本文の日付の食い違いに気づかなかった**（H7。v1 と同じ）。Murmur は本文の日付を読まないので、スタンドの側の注意になる
- **やりとりのない相手の宛先を引けない**（H7）。推測で入れずに止まったのは正しいが、スタンドだけでは完走できなかった唯一の箇所

### 運用

- Claude の記録（`recordings/`）はプロンプトに入るスレッドの id をキーに含むので、AI 判断の前に ID を使う操作を足すとキーが変わる。写し（ThreadMirrored）のように ID を使わない行は、どこに足しても記録を取り直さずに済んだ
- `--ai rerecord` は使わなくなった記録を消さない。取り直す前に最新のコードを pull する（古いコードで取り直すと外れが並ぶ）
- Neon はブランチごとにエンドポイントが違う。`dev.env` が `main` ブランチを指していて seed が落ちた

## 4. 次の段階へ持ち越すもの

計画 v2 の範囲を出るので、着手するなら ADR に案を書いてから。

1. **相手を引く API**（H7）: 自分のテナントの Party と Address を名前で引く（例: `GET /parties?q=伊藤`）。やりとりのない相手への送信を記録するのに要る。名寄せの運用（未知の人物・訂正のイベント）とつながる
2. **件名を属性として畳む**（0014 の未決 2）: Ingest の件名を初期値にし、本人やスタンドが直せる。ソースの写し（Jira の要約）もここに入れる
3. **スキルの片付けの説明**（H7）: 片付けたあとに動いても開き直さない。`activeSinceDismissed` が立つだけで、自分の番にも仕分け待ちにも出ない（`filter=all` か `since` で見える）
4. **写しが課題のスレッドより先に届いたとき**（ステップ 7）: 今は写さない。実物の Jira につなぐなら、作成の通知を先に流すか、写しからスレッドを作る
5. **実データの試用**（0007・0015）: 判定 7・10 と前提の指標（判定 6）はここで測る。経路は手元の pull スクリプトの案（0015、提案）
6. **LINE が自分の push を webhook で返すか**（0012 の未決 2）: 実物で確かめる
7. ~~テスト環境と本物のスキルの分離~~: やらない（直樹、2026-10-21）
