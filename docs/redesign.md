# 運用開始後の設計の見直し

更新日: 2026-10-28(管理画面の実装に合わせて改訂)

構想: [concept.md](concept.md)
認可の設計: [auth-design.md](auth-design.md)

運用を始めて見えてきた課題(下の 5 つ)をまとめて片付けるための設計。課題と決定の経過は課題帳(Artifact「ゲートウェイ運用課題帳」)にある。

1. 接続先の設定が多すぎる
2. 自社専用の接続先を管理画面から登録したい
3. 接続の画面を普通のリストと画面遷移にする
4. 複数のデプロイを 1 つの clone で管理したい
5. プラグインを提供元ごとに分けたい

## concept.md の決定事項から変わること

- **決定事項 1「管理者という役割も要らない」を改める。** 接続先の定義を画面から登録するために、管理者を置く。ただし管理者が扱うのは接続先の定義と OAuth のクライアントだけで、ほかのユーザーの認証情報には触れない。「認証情報の持ち主はユーザーだけ」は変えない。
- **決定事項 4「OAuth のクライアントはデプロイするときに `wrangler secret` で設定する」を広げる。** 画面から登録した接続先は、クライアントも画面から登録し、暗号化して保管する。
- 決定事項 2(短命トークン)、3(UserVault)、5(操作ログ)は変えない。

## 接続先の定義

### 3 つの出どころを 1 つの窓口で引く

接続先の定義は、次の 3 か所から集めて重ねる。同じ名前があれば設定(`SERVICES`)が勝つ。管理画面ではカタログと同じ名前は使えない(全員の Google などの鍵の向き先を、画面から変えられないようにするため)。

| 出どころ | 中身 | 変え方 |
| --- | --- | --- |
| カタログ(`src/catalog.ts`) | 汎用の接続先: freee、Microsoft Graph、Google 系、gBizINFO、Serper、board | ソースを変えて PR を出す |
| 設定(`SERVICES`) | Service Binding や identity を使う接続先(murmur)と、移行中の互換 | デプロイの設定を変えて出し直す |
| 管理画面 | 自社専用の接続先(ubs-apps、bm-next など) | 管理者が画面で登録する |

設定から管理画面へ移すときは、先に管理画面に同じ名前で登録してから(設定が勝つので、この時点では何も変わらない)、設定から消してデプロイする。

- いまは `parseServices(env.SERVICES)` を ui、mcp、proxy、vault の 10 か所で直接呼んでいる。これを `getServices(env)` と `getService(env, name)` の窓口 1 つにまとめ、呼ぶ側はすべてここを通す。
- 管理画面の定義は保管場所から読むので、窓口は非同期になる。
- 検証(名前の形、https 必須、認証方式ごとの必須項目)は出どころによらず同じものを通す。
- identity と Service Binding は設定でしか書けない。どちらも murmur しか使わず、Service Binding は wrangler の設定で宣言するものなので、画面から増やせない。

### カタログで使えるものだけを出す

- カタログの OAuth の接続先は、そのクライアント(後述)が登録されているときだけ有効にする。クライアントがない接続先は、画面にも `list_credentials` にも出さない。
- ヘッダー型の接続先(gBizINFO、Serper、board)は常に出す。ユーザーが鍵を登録しない限り何も起きない。

### 管理画面の定義の保管

- 全体で 1 つの Durable Object(`Registry`)に置く。管理画面での読み書きは強い整合性がほしいので KV にはしない。
- プロキシはリクエストのたびに定義を引くので、Worker のメモリに短く(30 秒ほど)キャッシュする。管理画面での変更は、長くてもこの時間で全体に効く。
- 管理者の操作(登録、変更、削除)は、プロキシの操作ログと同じく Workers Logs に残す。記録するのは日時、管理者、操作、対象の名前、変わった項目の名前。シークレットの値は残さない。

## OAuth のクライアント

- クライアントは接続先ではなくプロバイダーの単位で持つ。カタログの各接続先は、どのクライアントを使うか(`client: "google"` など)だけを書く。
  - Google 系の 6 件は 1 組のクライアントを共有する。いまは同じ値のシークレットを 12 個登録している。
  - Microsoft Graph のテナント ID は、URL に直接書かずに変数(`MICROSOFT_TENANT_ID`)から組み立てる。
- カタログのクライアントは、これまでどおり `wrangler secret` で入れる: `OAUTH_<CLIENT>_CLIENT_ID` / `_CLIENT_SECRET`(例: `OAUTH_GOOGLE_CLIENT_ID`)。
- 移行のあいだは、接続先ごとの古い名前(`OAUTH_GMAIL_CLIENT_ID` など)も読んでいた。自社の移行が済んだので、読むのをやめた。
- 管理画面で登録した OAuth の接続先のクライアントは、接続先ごとに 1 つ、その接続先の画面で入れる。`Registry` に `ENCRYPTION_KEY` で暗号化して保管する。シークレットは画面に二度と表示しない。

## 認証情報と向き先の結び付け

管理者がベース URL を別のホストに書き換えると、ユーザーが登録した鍵がそのホストへ送られてしまう。登録したあとで変えられるようにした以上、これを防ぐ。

- 全ユーザーの認証情報をたどって「再接続が必要」にする方法はない。UserVault はユーザーごとの Durable Object で、一覧する手段がない。
- そこで、認証情報を作るときに、その時点の向き先を一緒に記録する(ベース URL のオリジン。OAuth ならトークンの URL とクライアント ID も)。
- 鍵を使うたびに、今の定義と記録を見比べる。違っていれば鍵を注入せず、その認証情報を「再接続が必要」にする。使われた時点で止まるので、全員をたどる必要がない。
- この記録がない既存の認証情報は、最初に使ったときに今の定義で記録を書き足す。

### UserVault から接続先の知識を抜く

- いまの UserVault は自分で `parseServices` を呼んでいる。これをやめ、呼ぶ側(プロキシや画面)が窓口で引いた定義を引数で渡す。
- UserVault の役目は、暗号化と保管、ヘッダーの組み立て、リフレッシュ、向き先の照合だけになる。`Registry` を直接読まないので、Durable Object どうしの呼び出しも増えない。

## 管理者

- 設定に `ADMINS` としてユーザー ID を並べる(`entra_<tid>_<oid>`、`google_<sub>`)。メールアドレスは変わりうるうえ、IdP をまたぐと同じアドレスが別人になりうるので使わない。
- 画面に自分のユーザー ID を表示して、コピーしやすくする。
- 管理者の画面のヘッダーに「接続先の管理」へのリンクを出す。管理者でない人がそのパスを開いたら 404 を返す。

## 画面

### 画面遷移

一般ユーザー向けは、普通の「一覧 → 追加 → 戻る」の形にする。鍵の札のデザインはやめる。

| パス | 画面 |
| --- | --- |
| `/` | つないだ接続の一覧。サービス名、ラベル、状態(再接続が必要など)、操作(つなぎ直す、削除)。右上に「接続を追加」 |
| `/connections/new` | サービスの選択。提供元ごと(Google、Microsoft、freee、その他、自社)にまとめ、絞り込みの検索を付ける |
| `/connections/new/<service>` | 認証。OAuth はラベルを入れて「サインインしてつなぐ」、ヘッダー型はキーの入力欄。作ったら一覧に戻って「○○を追加しました」と出す |
| `/admin/services` | 接続先の一覧(出どころも出す。カタログと設定のものは読み取り専用) |
| `/admin/services/new`、`/admin/services/<name>` | 接続先の登録と編集(OAuth のクライアントもここで入れる) |
| `/admin/services/<name>/delete` | 接続先の削除の確認 |

- フォームの送り先(`/credentials`、`/connect`、OAuth のコールバック)と処理は、いまのものを使い回す。
- 一覧に戻ったときの通知は、リダイレクト先のクエリ(`/?added=<id>`)で渡す。

### 作り

- いまの `src/ui.ts` は、セッション、ルーティング、HTML の組み立てが 1 ファイルに入っている。画面が増えるので分ける。
  - `src/web/session.ts`: クッキー、セッション、同一オリジンの確認、サインインとサインアウト
  - `src/web/connections.ts`: 一般ユーザーの画面
  - `src/web/admin.ts`: 管理者の画面
  - `src/web/layout.ts`: 共通のレイアウトとスタイル(いまの `src/html.ts`)
- `src/index.ts` の if の連続は、小さなルート表(メソッドとパスのパターン → ハンドラー)にする。Hono などのライブラリは入れない。
- HTML は、埋め込んだ値を自動でエスケープするタグ付きテンプレート(`` html`...` ``)で組む。管理者が入れた表示名などが画面に出るようになるので、エスケープの漏れを仕組みで防ぐ。
- JavaScript は、画面が良くなるところ(絞り込みの検索、削除の確認)にだけ、ライブラリなしで少し使う。JavaScript が動かなくても、フォームとしては使えるようにしておく。

## デプロイ

- デプロイごとの設定は `deployments/<名前>.jsonc` に置き、`deployments/` は gitignore する。リポジトリの直下には `wrangler.jsonc` を置かない。
- 設定ファイルは deploy スキルで Claude が生成する。共通部分(互換日付、Durable Object の宣言、migrations など)の書き方は、スキルと `wrangler.example.jsonc` に書いておく。合成の仕組みは作らない。
- 共通部分が変わったとき(Durable Object のクラスや migration を足したときなど)は、deploy スキルが `deployments/` の全ファイルをひな形と照らし合わせて直す。
- ラッパーを用意する: `npm run deploy -- <名前>`、`npm run secret -- <名前> <KEY>`、`npm run tail -- <名前>`。中で `-c deployments/<名前>.jsonc` を渡す。名前のない素の `wrangler deploy` は、設定ファイルがないので失敗する。
- この見直しで `Registry` の Durable Object が増えるので、migration を 1 つ足す。

## プラグイン

- 共通の `api-gateway` は、ほかのプラグインの前提条件にする。中身は共通の手順、`gw_request.py`、gwlib と、小さい接続先のスキル(gBizINFO、Serper、board)。
- 大きい提供元は分ける: `api-gateway-google`、`api-gateway-microsoft`、`api-gateway-freee`。
- スクリプトはいま、同じプラグインの中の `api-gateway` スキルから gwlib を探している。分けると届かないので、各プラグインに gwlib のコピーを同梱し、`tools/sync-gwlib.py` で同期する(nvt-api-gateway と同じやり方)。コピーがずれていたらテストで落とす。
- 提供元に固有のスクリプト(`google_paging.py` など)は、その提供元のプラグインに移す。
- board のスキルは非公開の nvt-api-gateway-skills から移す。移す前に、自社固有の情報が入っていないかを確かめる。
- 配り方は、Cowork でもプラグインマーケットプレイスからの同期にもう一度挑戦する。だめなら当面は、プラグインごとの zip(まとめて作れるようにする)を手で上げる。

## 進める順番

1. **下ごしらえ**: 接続先の窓口(`getServices`)、UserVault に定義を渡す形への変更、画面のファイル分け、ルート表、タグ付きテンプレート。動きは変えない。
2. **画面の作り直し**(課題 3)。
3. **カタログとプロバイダー単位のクライアント**(課題 1)。自社のデプロイを新しいシークレット名に移す。
4. **管理者と管理画面、`Registry`、向き先の記録**(課題 2)。自社専用の接続先を設定から画面へ移す。
5. **複数デプロイの形**(課題 4)。自社の `wrangler.jsonc` を `deployments/` へ移す。
6. **プラグインの分割とマーケットプレイス**(課題 5)。コードとは独立しているので、ほかと並行してよい。

下ごしらえを先にするのは、窓口が非同期になる前に画面を書くと、すぐに書き直しになるため。
